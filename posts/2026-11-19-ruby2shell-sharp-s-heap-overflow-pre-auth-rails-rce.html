Ruby2ßhell：一个德语字母打崩 Rails——21 个 ß 触发的预认证 RCE

2026-11-19
  • 漏洞分析
  • Ruby
  • Rails
  • 内存安全

Ruby 3.3.14、3.4.13、4.0.10 在 2026 年 11 月 18 日同时发布，修了七个漏洞。其中最扎眼的一个叫 GHSA-34m4-m9fh-gqp5，研究员给它起了个念不出来的名字：Ruby2ßhell。这个名字来自德语字母 ß（sharp s，读作 "eszett"），因为触发这个漏洞的最小输入就是一串 ß。

问题的严重性不在名字上。它是网络可达、无需认证的堆溢出，默认配置的 Rails 应用就能打。一个 rails new 生成的空项目，没有写任何业务代码，照样能被这个漏洞打穿。

根因：只检查了一个字节的空间

出问题的是 Ruby 里单字节编码的 case_map 函数。以 enc/iso_8859_1.c 为例，打补丁前的代码如下：

while (*pp < end && to < to_end) {   /* 只保证还剩 1 字节空间 */
    code = *(*pp)++;
    if (code == SHARP_s) {
        if (flags & ONIGENC_CASE_UPCASE) {
            flags |= ONIGENC_CASE_MODIFIED;
            *to++ = 'S';                 /* 先把最后一个字节吃掉 */
            code = (flags & ONIGENC_CASE_TITLECASE) ? 's' : 'S';
        }
        else if (flags & ONIGENC_CASE_FOLD) {
            flags |= ONIGENC_CASE_MODIFIED;
            *to++ = 's';
            code = 's';
        }
    }
    /* ... */
    *to++ = code;                        /* 这里可能写越界 1 字节 */
}

循环条件的 to < to_end 保证目标缓冲区还剩至少一个字节。但 ß 的特殊之处在于它没有对应的大写形式：ISO-8859-1 这类编码里根本没有 ẞ 这个字符，所以 upcase 只能把它映射成两个字节 SS。函数先写一个 S，再写第二个 S，第二次写入已经越过了缓冲区末尾。

这就是一个典型的一对二映射问题：缓冲区按一对一分身，实际写入却是一对二。这个循环里的每次写入都是 *to++ = code，看起来人畜无害，但它假设了一个字符换一个字符。

受影响的编码一共 14 个，都是单字节编码：ISO-8859-1、2、3、4、9、10、13、14、15、16，以及 Windows-1250、1252、1254、1257。UTF-8 走的是另一条代码路径，不受影响。

为什么是 21 个 ß

缓冲区不是紧贴着分配的。rb_str_casemap 里这段代码决定了留多少余量：

#define CASE_MAPPING_ADDITIONAL_LENGTH 20   /* 注释还写着 16 should be long enough */

size_t capa = (size_t)(source_end - source_current) * ++buffer_count
              + CASE_MAPPING_ADDITIONAL_LENGTH;

输入长度加上 20 字节的余量。每个 ß 让输出多出一个字节，所以要溢出这 20 字节的缓冲，需要 21 个 ß。第 21 个 ß 写出的第二个 S 正好落在缓冲区之后。

这个宏上方那行注释值得单独看一眼：它写着「16 应该足够吸收任何单字符长度增长」，但常量已经被改成 20。说明这块余量以前因为类似的溢出问题被调大过一次，而这次遇到的又是同一类问题，只是换了个字符。余量从 16 提到 20 治的是症状，不是病根，病根是循环条件没有为「一个字符可能变成两个」留位置。

我在本机 Ruby 2.6.10 上跑了一遍验证：

s = ("\xDF".b * 21).force_encoding("ISO-8859-1")
s.upcase    # => "SSSSSSSSSSSSSSSSSSSSSSSSSSSSSSSSSSSSSSSSSS"（42 字节）

输出是 42 字节，输入是 21 字节，差值 21。缓冲区容量是 21 + 20 = 41 字节，结果 42 字节，多出来的那 1 个字节就是越界写。这个 bug 从 Ruby 2.4.0 就存在，一直到 3.3.13 才修掉。也就是说它在代码库里躺了大约十年，没人发现，因为没人会拿一串 ß 去做 upcase。

顺带说一句，Ruby 2.6.10 上触发这个漏洞没被 ASan 抓到崩溃，说明这是一次安静的堆破坏：它不会立刻崩，而是把 0x53 或 0x73 这两个字节的其中一个写进相邻的堆块。真正危险的正是这种「不崩」的溢出，因为它给了攻击者操作堆布局的空间。

一个字节怎么变成执行流

写越界一个字节，听起来离 RCE 很远。中间这一步是整条链里最需要解释的部分，因为它决定了这个漏洞到底是「能让进程崩」还是「能执行任意代码」。

关键在于 Ruby 的字符串是 RString 结构体加一段堆上的字符数据。case_map 的越界写落在 current_buffer->space 之后，而这块 mapping_buffer 是用 xmalloc 从 Ruby 自己的堆（或者系统 malloc 的堆，取决于编译配置）上分配的。越界的那一个字节落在下一个堆块的元数据或者内容上。

rb_str_casemap 里紧接着的这段代码把破坏变成了可利用的条件：

target_length += current_buffer->used = buffer_length_or_invalid;
/* ... */
target = rb_str_new((const char*)current_buffer->space, target_length);

buffer_length_or_invalid 是 case_map 的返回值，也就是它自以为写了多少字节。被越界写坏的那个字节不属于这个计数范围，所以 Ruby 会按「正确」的 target_length 去 memcpy，把相邻堆块里被污染的内容一起复制进新字符串。溢出本身不直接给攻击者写原语，它给的是一个长度和内容的错位：新字符串里会多出本不属于它的字节。

要把它变成可控的读或写，需要控制溢出位置后面是什么对象。这就是堆布局的工作：通过在请求里附带若干个大小可控的 multipart 字段，让 Rack 在解析过程中分配一批大小已知的字符串，把 mapping_buffer 挤到某个特定对象旁边。当被写坏的那个字节落在相邻 RString 的长度字段或指针字段上，后续的字符串操作就会读到一个被修改过的长度或者指针，标准的堆利用路径从这里接上。

研究员在披露里给出的时间线可以反推这条路的难度：玩具应用上的端到端利用 10 月 26 日就完成了（三天），但针对真实应用、并且要在 jemalloc 和默认 glibc 两种分配器下都稳定，一直做到 11 月 5 日到 6 日。这也说明一件事：glibc 和 jemalloc 下的堆布局完全不同，同一份输入在两种分配器上的相邻对象不一样。写 PoC 的人和做防御的人都要意识到这一点。

我不打算在这篇文章里给出完整的利用代码。原因是这个漏洞的补丁已经在 11 月 18 日发布，官方明确说 PoC 会推迟一周公布，而目前还有大量未升级的 GitLab、GitHub Enterprise、Chatwoot 实例在线。原理讲到能把补丁看懂的程度就够了，具体怎么摆堆，等升级完之后自己研究也来得及。

从 ß 到 RCE：Rack 的两处设计各贡献了一半

单看这个 bug，读者可能觉得「也就是一个字节，能有多大危害」。真正的杀伤力来自它落在了一个预认证就能触发的代码路径上。

Rack 的 MethodOverride 中间件允许客户端用表单字段覆盖 HTTP 方法。lib/rack/method_override.rb 里：

def method_override(env)
  req = Request.new(env)
  method = method_override_param(req) ||
    env[HTTP_METHOD_OVERRIDE_HEADER]
  begin
    method.to_s.upcase          # 攻击者控制的字符串进了 upcase
  rescue ArgumentError
    env[RACK_ERRORS].puts "Invalid string for method"
  end
end

任何 POST 请求只要带上 _method 字段，这个值就会被 .upcase。这是第一半。

但光能传任意字符串还不够，还得让它以 ISO-8859-1 的编码身份进入 Ruby，否则 Ruby 会按 UTF-8 处理，走安全的那条路径。这就轮到了 Rack 的第二个设计：multipart 解析器允许客户端在字段的 Content-Type 里指定 charset。lib/rack/multipart/parser.rb 的 tag_multipart_encoding：

def tag_multipart_encoding(filename, content_type, name, body)
  name = name.to_s
  encoding = Encoding::UTF_8          # 默认 UTF-8
  # ...
  content_type.split(';').each do |part|
    # ...
    if k == "charset"
      encoding = find_encoding(v)     # 客户端说了算
    end
  end
  name.force_encoding(encoding)
  body.force_encoding(encoding)       # 整个 body 被强制成攻击者选的编码
end

find_encoding 后面还有一行注释写着「因为 enc 是用户提交的，可能无效」，可见维护者知道这个输入不可信，但只考虑了「无效」这一种情况，没考虑「有效但危险」。

两处合起来，攻击载荷就是一个平平无奇的 multipart 表单：

Content-Disposition: form-data; name="_method"
Content-Type: text/plain; charset=ISO-8859-1

21 个 ß，不需要认证，不需要登录，不需要任何业务逻辑。这就是为什么 rails new 的空项目也中招：MethodOverride 是默认中间件栈的一部分，它在你写的任何控制器之前就执行了。

第二个 bug：整数溢出变成 4GB 越界写

同一批披露里还有个更夸张的，GHSA-87fm-7w84-j2px。rb_str_casemap 里缓冲区长度和 target_length 的类型不一致：

int target_length = 0;                  /* 注意：int */
/* ... */
target_length += current_buffer->used = buffer_length_or_invalid;
/* 最后 */
target = rb_str_new((const char*)current_buffer->space, target_length);

capa 是 size_t，用来分配缓冲；target_length 却是 int。32 位绕回时，rb_str_new 会按一个「合法但极小」的长度分配目标字符串，然后把整块 size_t 大小的数据 memcpy 进去。

触发它需要找一个「输入短、输出长」的码点。U+0390 就是其中一个：输入 2 字节，大小写转换后变成 3 个码点共 6 字节。取最小的、超过 2 的 32 次方且是 6 的倍数的长度，也就是 715,827,883 个：

source = "\u0390" * 715_827_883
source.upcase

输出会绕回成 2 字节的缓冲区，实际写入约 4GB。这个在原理上比第一个更暴力，但实用性差一些：Rack 3.2.2 给 multipart 字段加了大小限制，挡住了这种载荷。所以它能打的是钉在 Rack 3.2.1 及更早版本的应用。

时间线读起来比技术细节更值得琢磨

研究员 Moritz Sanft 在 2026 年 10 月 23 日开始看 Ruby 的预认证攻击面，10 月 26 日就打穿了玩具 Rails 应用。真正完整可用的 RCE 是 OpenAI 的 Sylvie 在 11 月 5 日做出来的，针对普通 rails new 应用，11 月 6 日又用默认 glibc 分配器复现了一遍。

值得记一笔的是发现方式：研究员让 Codex 去梳理 CRuby 从 Rails 可达的预认证攻击面，然后自己筛查 Codex 给出的结果、把方向拨到有意思的那些上。不到 24 小时就出了一批漏洞。这和「AI 自动挖洞」的宣传口径不太一样。AI 干的是穷举和覆盖面，人干的是判断哪条线值得深挖。这个组合目前看起来是有效的。

再一个细节：Ruby 官方提交里写着 Co-Authored-By: Claude Mythos 5.1。修复补丁本身也有 AI 参与。

修了什么

补丁小得离谱。14 个编码文件，每个改一行：

-  while (*pp < end && to < to_end) {
+  while (*pp < end && to_end - to > 1) {

从「至少剩 1 字节」改成「至少剩 2 字节」。如果只剩 1 字节，循环直接退出，不再尝试写入那个可能变成两个字节的字符。同时补了回归测试，覆盖全部 14 个编码 × 1 到 64 个 ß 的组合，把 upcase、downcase(:fold)、swapcase、capitalize、casecmp? 五个入口全测了。

修复不是暴力把余量从 20 提到 40，而是改判断条件本身。这是正确的修法：余量只把触发阈值往后推，改条件才消除「一对二映射撞上一对一假设」这个根因。

影响面：不止 Rails

除了 Rails 和 Sinatra（classic 写法），还有一批自托管软件打包了受影响的 Ruby。按研究员披露时的版本：

软件 打包的 Ruby 状态
GitLab 19.6.0 3.3.13 受影响
GitHub Enterprise Server 3.22.5 4.0.9 受影响
Chatwoot 4.20.0 3.4.4 受影响
Mastodon 4.7.6 4.0.10 已修复
OpenProject 17.9.8 4.0.10 已修复
Discourse 基础镜像 4.0.10 已修复

GitHub 和 GitLab 受影响是这两家自己发公告确认的。这也解释了为什么 OpenAI 在披露前后主动联系了 WAF 厂商：单靠升级 Ruby 版本，很多团队要排期，WAF 拦一层能争取时间。

一个开发者的应对清单

先查版本，一秒钟的事：

ruby -v
# 3.3.x < 3.3.14、3.4.x < 3.4.13、4.0.x < 4.0.10 都是受影响的

如果版本落在受影响区间，别只盯着 Gemfile.lock 里的 rails 版本看。这是 Ruby 解释器本身的漏洞，bundle update 解决不了。得升 Ruby：

# 用 ruby-build / rbenv 的话
rbenv install 3.4.13 && rbenv global 3.4.13

# 或者 asdf
asdf install ruby 3.4.13

容器化的项目改基础镜像的 tag 更快。另外注意 3.2 及更早分支已经 EOL，官方不给修，回退到 2.4.0 都有这个问题，只能升到还在维护的分支。

如果短期内升不了级，可以临时把 MethodOverride 中间件从栈里摘掉。绝大多数 API 应用根本不需要它：

# config/application.rb
config.middleware.delete Rack::MethodOverride

代价是前端不能再通过表单的 _method 字段发 PUT/DELETE 了。如果确实需要这个能力，折中方案是在反向代理层把 _method 字段的值长度限制到 20 字节以内。溢出需要 21 个 ß，20 字节的输入加上 20 字节余量正好不越界。这只是缓解，不是修复，别把它当最终方案。

WAF 侧可以拦 Content-Type 里带 charset=ISO-8859 或 charset=windows-125 的 multipart 请求。正常浏览器的表单提交不会这么写，误杀率极低。

排查存量比升级更容易被忽略。跑着一堆 Ruby 服务的团队，难点通常不在「不知道要升级」，而在「不知道哪些实例受影响」。一条命令能扫完：

# 已知的容器镜像里，逐个查 Ruby 版本
for img in $(kubectl get pods -A -o jsonpath='{range .items[*]}{.spec.containers[*].image}{"\n"}{end}' | sort -u); do
  ver=$(docker run --rm --entrypoint ruby "$img" -e 'print RUBY_VERSION' 2>/dev/null)
  case "$ver" in
    3.3.1[0-3]|3.4.[0-9]|3.4.1[0-2]|4.0.[0-9]) echo "VULN  $img  ruby $ver" ;;
  esac
done

日志侧也能加检测。攻击载荷的特征足够明显：multipart 请求体的某个字段里出现连续的 \xDF 字节，或者 _method 字段的值不是标准 HTTP 方法名。Nginx 侧用 $request_body 做子串匹配会误判二进制上传，更稳的做法是在应用层加一个中间件，对 _method 的值做白名单：

# 放在 MethodOverride 之前
class StrictMethodOverride
  VALID = %w[GET HEAD PUT POST DELETE OPTIONS PATCH LINK UNLINK QUERY].freeze

  def initialize(app)
    @app = app
  end

  def call(env)
    if (m = env["rack.request.form_hash"]&.dig("_method"))
      unless VALID.include?(m.to_s.upcase)
        return [400, { "content-type" => "text/plain" }, ["bad method"]]
      end
    end
    @app.call(env)
  end
end

这个中间件同时挡住了这个漏洞和以后任何针对 _method 的注入。长度白名单比编码白名单更耐用，因为合法方法名都很短。

最后一点

这个漏洞最值得记住的地方在发现路径，不在杀伤力。一个从 Ruby 2.4 就存在、横跨 14 个编码文件、潜伏了十年的 bug，本质上是「一个字符可能映射成两个字符」这个再普通不过的语言学事实，撞上了「一对一的缓冲区分配」这个再普通不过的优化假设。

补丁只有一行。发现它却需要一个 AI 把所有可达路径铺开，再一个人判断哪条值得往下钻。

如果你手上还有跑着 3.3.13 以下 Ruby 的服务，今晚就升级。这类漏洞通常不会在披露当天就被利用，但它的利用门槛低到只有一个 multipart 表单。不需要编译器，不需要内存布局技巧，不需要绕过什么。
