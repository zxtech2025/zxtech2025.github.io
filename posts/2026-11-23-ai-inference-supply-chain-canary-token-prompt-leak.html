两百万条诱饵提示词：AI 推理供应链到底把你的 prompt 送去了哪

2026-11-23
  • 供应链安全
  • LLM 基础设施
  • 威胁情报
  • 数据泄露
  • 云安全

HD Moore 的团队花了五个月，往各家 AI 服务里塞了大约 200 万条带追踪标记的提示词，然后就看这些标记什么时候、从哪里被触发。结论不太好看：三家托管厂商正在被入侵而自己不知道，一个市场型平台的卖家靠"低价接单 + 开日志"就拿到了客户 prompt，还有一批供应商在 ZDR（零数据保留）标志下照样抓取、照样转手。

这件事有价值的地方不在于"AI 不安全"这个结论，而在于它给了一条能自己复现的方法：用不会被人合法触碰的凭据当诱饵，把"数据去哪了"从信仰问题变成可观测问题。

诱饵怎么设计

Canary token 是老技术，Thinkst 那套大家都会用。难点在于把这个思路适配到 LLM 场景：一条 prompt 经过路由器、市场、托管厂商、最终推理服务，每一跳都能看到全文，你没法靠单点日志判断泄露源。

他们的做法是每条 prompt 都注入一组互相关联的诱饵，由同一个 seed 派生：

  • 一个真实可用的 AWS access key，挂在一个空账号下，开着完整的 CloudTrail
  • 一个从未在任何地方出现过的域名
  • 一组 URL，指向他们自己的 DNS / web / git / SSH / 数据库 / mail 服务
  • 一个图片 URL，用来记录是哪台机器来取的

因为所有组件都能反推回父 seed，拿到任何一个触发点，就能定位到具体是哪条 prompt、哪个模型、哪条路由、当时带的是什么隐私设置。DNS 查询走的哪个解析器、TLS SNI 是什么、HTTP Host 头是什么，全部留痕。

这套东西 7 月起步，第一批 token 几天内就开始响了，到 11 月还在响。

发现一：三家厂商正在被入侵

最严重的那组不是策略问题，是入侵。约两百个 AWS key，每一个只发过一次、只发给一家厂商，集中在 10 月末的几个短窗口里，这些窗口内发出的请求全部被盗。

这里面有个细节很有意思：部分被盗的 key 来自那些在模型跑起来之前就被厂商拒掉的请求。这说明 attacker 在厂商的入口处复制请求，不是深入到推理栈里面去拿的。这个位置判断直接决定了你该在哪里布防：入口网关的流量镜像和请求日志，比推理进程内部的内存审计更有效。

拿到凭据之后的路径很标准：

  1. 先验证 key 是否可用，有时在请求发出后几小时内就试
  2. 列 S3 bucket，翻 Secrets Manager 和 Parameter Store
  3. 在 Bedrock 里启用托管模型、创建 Bedrock API key、加自己的 IAM 用户维持访问

诱饵 key 累计被用来打了数万个 AWS API 调用。有一条 10 月 21 日种下的 key，第二天就被用，三周后还在用。

更值得注意的是 attacker 的工具演化。同一个对手同时打了两家厂商，两组凭据几乎立刻从同一台租来的服务器上一起使用。三周内它的工具链换了三茬：先是伪装成 Windows 上 Chrome 的脚本，然后切到 OrbStack 里的 Boto3，后来又换到 Kali 上的 AWS CLI。11 月 1 日它加了一个叫 ARTEX 的 LLM 驱动的渗透框架。

对防守方的好消息是这些工具会自报家门，Kali 和 ARTEX 都出现在 AWS CloudTrail 记录的 user agent 里。坏消息是这个自报只占流量的一小部分。ARTEX 发出的两个 user agent 字符串，artex-agent 和 artex-judge-r121，在公开的检测规则库里一个都搜不到，值得直接加进自己的规则集。

发现二：卖家不需要漏洞

第二组发现完全不需要打洞。被抓到的市场卖家只做了三件事：把一个模型标成最低价、打开请求日志、等。

其中一个案例：两条 prompt 经过某个卖家的报价，大约一天半之后，有人在家庭宽带连接上打开浏览器访问了那两个秘密 URL，开始在登录页猜用户名。同一模型走另一个卖家的 prompt 从未被碰过。泄露跟着卖家走，不跟着平台走。

另一个案例是一台位于西欧住宅宽带后的 Mac，从两条 prompt 里取走密码，手工通过 SSH 试 root 登录。两分钟内同一个密码试了四次，路由追踪显示这条 prompt 经过了两个路由器。同一台 Mac 后来在一个会话里试了多个 AWS key。

这条案例还牵出一个隐藏跳数：大部分 key 是走市场发出去的，但有一个走的是完全不同的路由器。查下去发现那个路由器在悄悄把自己的部分流量转发给市场。

这就是市场价格战的直接后果。卖家要压价，可以走无计量消费级订阅，可以走 startup credits，可以走更黑的路径：用盗来的 AWS 凭据或消费级 API key 结账。如果卖家的真实目的是拿数据，最优策略恰好就是低价接单、自己补差价、从平台日志里收割。 低价在这里不是不健康的商业行为，而是一个攻击面的选择器。

发现三：ZDR 标志只约束第一跳

第三组发现里没人用凭据。秘密 URL 被反复抓取，指向的 git 仓库被尝试 clone，全部来自本不该看到 prompt 的机构，而且经常和请求上的隐私设置直接冲突。

最清楚的例子是一个实验室：它的系统抓取了 7 月到 10 月间发往其模型的一半以上 prompt 里的秘密 URL，其中包括大约三分之二标记为"不收集数据"或 ZDR 的请求。抓取器通常在请求发出后两三天出现。

关键在这里：这不限于直接发给该实验室的请求。 几家境外托管厂商转售该实验室的模型，发给这些托管厂商的 prompt 触发了完全相同的抓取器，请求流回了实验室。一个特意选了异地托管、想把数据留在某个司法辖区内的客户，并没有得到他付费买的东西。

后来还有一台其他云上的 git 客户端开始尝试 clone prompt 里引用的私有仓库，但只针对用了该实验室模型的那些 prompt。

大厂自己的问题也不少。有一家在我们只调用过一次搜索端点之后，两个月零几天还在爬那个秘密 URL。另一家不管我们走哪个路由器过去，都有一个抓取器在每次请求后几天回来一趟。

最离谱的一个：一条发给某厂商的 prompt，其中的秘密链接在 24 天后被发进了一个企业内部 IM 群，两分钟内从六个终端上被打开：三个桌面端、三个手机端。而研究者对该厂商的通报里只给了那个链接的前 8 个字符，所以转发的人读的是一份存下来的完整 prompt 副本，在请求发出三周多之后。这个请求当时是带着 ZDR 标志发给该厂商的。

追踪路由：给推理链路做 traceroute

Canary 能告诉你 prompt 泄露了，但告诉不了你在哪一跳泄露的，因为路由器一般只上报一个上游厂商，而那个厂商往往又是一个路由器。

他们的解法分两步。第一步简单：在请求里放一个指向自己服务器的图片 URL，任何去取它的系统都会暴露 IP、HTTP 客户端和时间戳。第二步利用了这类服务的堆叠特性：发一些小的、略微畸形的请求，每一层路由都会用它自己的格式包装下一层的错误，所以一个响应里可能嵌着三四层"信封"。把每一层拿去和签名库比对，就能还原跳数、每跳的软件、所用网络以及运营方。

到目前追了大约两千条路由。其中几百条里有一个识别不出来的系统，少数几条把图片发给了一家根本不在宣称路径上的公司。追踪还挖出了路径里从未提及的中间层：一个市场卖家往每条 prompt 里悄悄加了一千个左右的隐藏 token，另一个通过共享的消费级订阅账号去取图片。

三起事件的根因

同样的诱饵在真实入侵里捞出了三个非常不同的故障模式，这三个才是对工程团队最有价值的部分。

其一，AI 编码助手把凭据提交进了公开仓库。 一家厂商在做常规软件测试时收集了一批授权使用的 prompt 样本，存在一个私有 Hugging Face 仓库里。样本来自 M3、GLM-5.2、K2.6 三个模型，主要集中在 6 月 24 日、7 月 4 日、7 月 8 日和 7 月 14 日。在开发它那个公开 GitHub 仓库时，一个 AI 编码 agent 把一个能访问该私有 HF 仓库的凭据提交了上去。自动扫描发现了，提交也 revert 了，但在暴露窗口里凭据已经被拿走，对方用凭据下载了全部样本，然后开始在样本里搜其他服务的凭据并逐个验证有效性。

这里有个链路值得记清楚：样本里含客户的真实 prompt，真实 prompt 里含客户自己的凭据，所以 prompt 样本库本身就是一个凭据金矿。 为了"测试"而收集的 prompt 语料，其敏感等级应当等同于生产凭据库，而不是当成测试数据。他们的整改也印证了这一点：改用 scoped 或短期凭据、支持 keyless 的地方就用 keyless、所有 PR 检查凭据、新账号默认开 ZDR、并"更新了使用 AI 编码 agent 的开发流程"。

其二，信任 loopback 的管理接口。 另一家厂商 11 月 5 日在单台服务器上发现未授权活动。攻击者把两个东西串了起来。一个是遗留的互联网可访问服务，另一个是一组管理接口，这组接口靠 loopback 访问来做信任判断，不独立认证调用方。组合结果是攻击者能创建未授权的 CVM 并拿到应用凭据。11 月 6 日轮换了 KMS 根密钥，11 月 8 日收到第三方研究员给的证据，追到一台新 GPU 服务器上的推理部署：它在承载生产流量，但没有跑完整的生产安全加固。攻击者用类似的访问方式控制了这个推理 VM，使得请求数据在处理过程中可见。

这个模式在容器和虚拟化平台上反复出现：127.0.0.1 被当成身份，而不是被当成位置。任何管理面只要"从本地来就放行"，就等于把同主机上任何一个能发本地请求的东西都提升成了管理员。

其三，市场卖家的静默数据收割，前面已经说过，不需要漏洞。

为什么要自己做这个检查

厂商侧的响应是有的。平台方下架了三家供应商，把 125 个端点从 ZDR 资格里移除，包括研究者点名的那批以及一批预防性移除的。同时在把研究者的测试方法产品化，准备常态化跑这些检查，并开始对网络路径做技术验证，看请求和响应有没有被转发给第三方。

但有个结构性问题绕不过去：你没法验证别人有没有遵守 ZDR，你只能选择相信。 市场上有人调侃说攻击者花五分钟就能写个过滤器绕开 canary URL 的抓取，这说法对长期监控是成立的，但 canary 的价值不止于 URL。AWS 凭据诱饵、DNS 诱饵、SSH 诱饵都能留痕，而且任何对攻击者有价值的东西都能做成 canary。

实际能落地的做法，按投入排序：

自己种 canary。 在 agent 和数据处理管道已经在发送的上下文里塞一个假凭据，任何一次被使用都当成安全事件处理。Thinkst 的免费 Canarytoken 足够起步，但更好的做法是自己派生一组：DNS 名、URL、AWS key 各一份，用同一个 seed 关联，这样触发时能反推回是哪条请求。

自己挑上游。 用路由器的时候手动指定上游厂商，不要接受默认池子。然后实际验证一下隐私设置有没有改变请求的去向，这需要 canary，光看控制台是做不了的。市场型的转售池尽量避开。

按"prompt 会泄露"来设计。 这是最根本的一条。既然 prompt 会流经多个组织、会被存下来、会被进日志、会被人读到，那么往 prompt 里放明文凭据就是一个明确的架构错误。让 agent 用短期凭据、让工具输出经过密钥过滤、让模型永远看不到长期凭据。

入口日志比想象中重要。 那家厂商的泄露发生在被拒绝的请求上，也就是模型根本没跑。如果你的检测只盯着推理进程或模型输出，这类泄露完全不可见。

一个开发者的视角

我觉得这篇研究最有价值的一句话是：a privacy flag only binds the first hop。隐私标志只约束第一跳。后面每一层的策略、日志、转发、转售，都在标志的作用域之外。

这对做 AI 应用的团队有两件事要说清。第一，评估供应商时"是否支持 ZDR"不是个可用于决策的信息，能问的问题只有"请求在几跳之内离开你信任的边界"。第二，agent 场景把这个问题放大了一个数量级：agent 会把它能读到的东西全都发出去，包括它顺手 cat 到的 .env。

我的做法是三条硬规矩：凡是会流出本地边界的请求，上下文里不允许出现长期凭据；供应商选择上宁可多花一点钱走直连，也不走默认市场池；每个新接入的模型服务，先用一个便宜的 canary 探一次，看一周内有没有人回来碰它。第三件事成本不到一杯咖啡，但它给出的答案比任何 SOC 2 报告都具体。
