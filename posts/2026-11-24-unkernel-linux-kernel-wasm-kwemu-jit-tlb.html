把 Linux 内核编译成 wasm：unkernel 的架构取舍，和一张 23 行的「否决设计」表

2026-11-24
  • WebAssembly
  • Linux内核
  • 虚拟化
  • 编译器
  • 系统设计

浏览器里跑 Linux 不是新鲜事。JSLinux 在 2011 年就做到了，v86、container2wasm 一路下来，这条路已经走了十五年。所以当我看到 unkernel 的首页写着「一个真正的 Linux 内核，编译成 WebAssembly，不到一秒起 shell」时，第一反应是划过。

真正让我停下来的是它的架构图里一行字：内核是编译出来的，用户程序才是模拟的。

这句话反过来才是所有人的默认做法。JSLinux 和 v86 模拟一整台 PC，连内核一起模拟；WASI 类运行时干脆不要内核，用 JS 重新实现一遍 syscall；linux-wasm 这类项目把内核编译成 wasm 但没有 MMU，fork 退化成 vfork。unkernel 选了最别扭的第四种：内核完整编译成 wasm 以原生速度跑，用户态的 aarch64 二进制照旧模拟。这等于把整台机器的快慢开关，从「CPU 指令」挪到了「内核路径」。

这个决定对不对，得看数据。而它最值得读的地方，是作者把做错的路也标了价格。

三种主流路线，各自死在哪

README 自己列了这张对照表，我把它压缩一下：

路线 内核 用户态 MMU
整机模拟（v86、JSLinux、container2wasm、QEMU 的 wasm 版） Linux，模拟 未修改，模拟 模拟
syscall 模拟器（含各家浏览器容器方案） 无，运行时自己实现 syscall 未修改，模拟 运行时自有
wasm 上的 POSIX 运行时（WASIX、WebContainers、BrowserPod） 无 重编译为 wasm 无
无 MMU 的 Linux（linux-wasm、LKL 一类） Linux，原生 wasm 重编译为 wasm 无
unkernel Linux，原生 wasm 未修改 aarch64，模拟 真页表

前两类的问题不是性能，是语义保真度。整机模拟每个 syscall 和缺页都要穿过模拟硬件，慢；syscall 模拟器快，但它只覆盖运行时实现过的那些 Linux 部分，剩下的一律 ENOENT 或者行为不同。第三类要求原生程序重编译，fork 和任何依赖 MMU 的东西直接坏掉。

unkernel 的赌注是：程序感受得到的「慢」大部分不在 CPU 上，在内核路径里。起进程、syscall、缺页、文件与网络 I/O，这些如果以 wasm 速度跑，剩下的指令模拟慢一点也许还扛得住。反过来，如果内核路径也慢，那模拟得再准也没用。

这个赌注可以量化。而量化结果比宣传语有意思得多。

数字：什么时候真的快，什么时候是表演

作者的基准测试跑在 Node 下，单位是纳秒，四个实现对比（原生 / qemu-user / qemu-system / unkernel）：

操作 原生 qemu-user qemu-system unkernel
getppid 110 320 1662 172
从 /dev/zero 读 64 字节 161 481 2247 172
pipe 写+读 417 1032 7256 482
fork+exit+wait 73 µs 537 µs 1178 µs 57 µs

先看最后一列和第一列的比值：getppid 慢 1.56 倍，读 64 字节几乎持平（1.07 倍），pipe 往返 1.16 倍。这些数字接近原生，不是「在 wasm 里勉强能跑」。相对于整机模拟，是 10 到 15 倍的差距。

fork 那行更反直觉：57 µs 比原生的 73 µs 还快，也就是 0.78 倍。作者对这件事的解释很实在：这是 riscv64 用户态时期的测量（内核路径没变），在此测试里 fork 比原生快。我不认为这能推广成「unkernel 的 fork 比真机快」，更合理的读法是：宿主是 V8，不是内核自己的调度器，进程创建的账被记在了不同的地方。把它当成「没有明显代价」的证据是安全的，当成「优势」是过度解读。

代价在纯计算这边，而且作者没藏：

  • 解释器跑整数代码大约 250–300 M 条 guest 指令/秒。折算下来每条指令 3.6 ns 左右，对比原生差两个数量级以上。
  • JIT 打开后，ash 循环 4.0s → 2.5s（1.60 倍），seq 100000 | sort -r 7.1s → 3.1s（2.29 倍），seq 250000 | gzip | gunzip 6.5s → 3.5s（1.86 倍）。
  • 仍落后原生很多：apk search 扫主索引 0.8 秒，apk add python3 3.4 秒。

JIT 的收益区间也很清楚：2 倍上下，不是数量级。原因后面讲：JIT 只解决指令翻译，解决不了数据 TLB 查表。

启动这块倒是真的快到可以改用法：内核到 /init 约 70 ms，从 node 起到 Alpine 提示符 0.3 秒，页面下载约 10 MB，Alpine 在 48 MiB guest 内存里启动。这个量级意味着它可以是「点开就用」，而不是「等一会」。

关键在哪里：syscall 不再是一次模拟陷落

要理解为什么 syscall 能接近原生，得看它的层边界画在哪。

普通模拟器的路径是：guest 代码执行 → 模拟 CPU 发现 syscall 指令 → 触发模拟陷阱 → 切换到模拟的内核态 → 模拟操作系统处理。每一次 syscall 都要走一遍「陷阱→特权级切换→返回」的模拟硬件流程，而且内核本身也是模拟出来的指令，一行一行被翻译。

unkernel 把这条链砍成两段。用户程序跑在 kwemu 里，一个用 Zig 写的 aarch64 CPU，直接链接进内核。当程序发起 syscall，kwemu 直接返回内核，内核是编译成 wasm 的机器码，原生执行，中间没有模拟的陷阱，没有模拟的内核态。整个 syscall 处理过程是真实的 Linux 内核代码在跑，只是它跑在 wasm 上而不是 x86 上。

这就是为什么 getppid 只要 172 ns：它没有走任何模拟路径，只是进了内核、读了个字段、回来。而 qemu-system 要 1662 ns，因为它得模拟陷阱和模拟内核态。

难点在怎么让内核「返回」到用户代码。wasm 没有特权级，也没有原生的调用栈切换。unkernel 用的是 JSPI（WebAssembly.Suspending）：内核拿到真正的栈，可以挂起和恢复。这是我读下来觉得最巧的一处：它没有硬造一个调度器，而是借了宿主提供的能力来描述「内核让出 CPU」。

内存这边同样是真家伙。arch/wasm 实现了 Sv48 布局的页表，kwemu 直接走内核自己的页表。所以 fork、mmap、copy-on-write、共享内存、线程和信号都是真语义，不是「近似实现」。这个区别很大：没有 MMU 的方案里 fork 只能退化成 vfork，一堆程序直接不兼容。

src/emu/kwemu.zig 里关于 TLB 的设计也值得单独说，因为它决定了上面那张表的读法：

  • 读、写 TLB 各 1024 项，直接映射，合计 32 KiB。
  • 快速路径只有一次比较：表项存 tag = vpn 和 add = host - va，tag 跟访问的最后一个字节的 vpn 比较。所以跨页访问会自动落慢路径，不用额外判断。一次访问大约 15 条 wasm 指令。
  • 和 256 项比，apk、sort、gzip 和 ash 循环快 1.5–3%；加到 4096 项没有收益。

一次内存访问 15 条 wasm 指令，这就是纯计算慢两个数量级的真正原因。JIT 能把指令翻译的成本降下来，但每次访存扩成 15 条指令这件事，JIT 也躲不掉，它是 MMU 语义的代价。作者的「下一步」里也承认这一点：区域关闭时最大的损耗之一是「data-TLB checks 和 NZCV packing」。

JIT 为什么只值 2 倍

看 JIT 的设计，能解释上面那个「2 倍不是数量级」的结果。

编译单位不是指令，是解码后的 block。 一个 block 最多 64 条指令、必须在一页之内，条件分支是侧出口，直接分支在页内则跟进去。一个 block 编译成一个 wasm 函数，热点 block 之间还会合成一个 module（叫 region，最多 16 个成员）。生成的函数签名是这样的：

f(x, cpu, irqp, jl: i64) -> i64

x 是寄存器基址。guest 寄存器放在 wasm local 里，进入时加载，在唯一一个出口写回。返回值是一个打包的整数 (jl_left << 8) | code：0–63 表示在第 k 条 op 前交回解释器，64–127 表示本块跑完，128+k 表示在第 k 条 op 侧出口。

这个返回约定是整个设计的关键。它意味着 JIT 代码随时可以「交回」，而不是必须处理完。什么时候交回？

读写会在同一对 tlb_r/tlb_w 数组上内联 data-TLB 快速路径；miss 时在执行前把 op 交回，这样就覆盖了缺页、跨页访问和写代码页三种情况，SMC 检测逻辑完全不用改。

这句话信息量很大。JIT 并没有重新实现一遍 MMU 语义，它内联了同一条 TLB 快速路径，慢路径直接交回解释器。好处是正确性天然一致（同一段代码处理边界情况），代价就是那 15 条指令的访存税在编译代码里照旧存在。这才是 JIT 只值 2 倍的根本原因：它优化掉的只是「解码 + 分派」，而访存开销属于 MMU，编译不掉。

编译时机也很保守：一个 block 要解释执行满 2^17 条指令（131072）才进编译。按 275 MIPS 折算，大约 0.48 毫秒的解释时间。作者试过 eager 模式（首次进入就编译），短程序上从 110 MIPS 掉到 13 MIPS，为用一次的代码付编译成本是纯亏。也试过固定 2^19 的阈值：npx 能追平不开 JIT 的情况，但内存循环慢 18%、md5sum × 8 慢 60%。所以才用 2^17。

还有一处我觉得最能说明工程纪律：JIT 有 1024 个预分配 stub 函数（不扩表、不调分配器），用完了用时钟算法（second chance）淘汰一个。slot 只在 run 的入口之间释放，绝不在编译代码内部释放。这类约束看着啰嗦，但正是它们让「编译代码和解释器逐位一致」这个不变量守得住。

顺带一个数字能校准预期：区域扩张时一次完整重编译大约几百微秒，而 compiled block 之间来回跳一次的固定成本约 30 ns（A64，7-Zip 的 LZMA）。所以「块切得太碎」的代价是真实存在的，这也解释了为什么 16 个成员、按每 KiB 出口数设阈值这类参数要反复调。

那张「否决设计」表才是真正的干货

几乎所有技术博客都只讲最后的选择，不讲被砍掉的路。而 unkernel 的 .agents/kwemu.md 里有一张 23 行的表，标题叫 Rejected designs，副标题写着「Do not retry without a new reason」。

我挑几条最值钱的：

线程化分派（threaded dispatch）失败得很彻底。 直觉上每个 handler 用 continue :sw 跳自己的 br_table 应该更快，结果：run 循环大 7 倍，kwemu.o 从 363 KB 涨到 528 KB，npx --version 从 3.66 秒变成 6.14 秒（--no-jit）。慢 68%。原因不难猜：V8 的 br_table 分派前提是一个热点跳转表，拆成几十个之后每个都变冷。这条是 wasm/JIT 时代特有的反直觉：在 C 里教科书推荐的 computed goto，搬进 wasm 是负优化。

把自循环做成 region 成员，慢到荒谬：1150 vs 1880 MIPS，掉了近四成。所以自循环被单独放成一个闭合模块。文档原话是「作为一个普通 wasm loop 它比作为成员快得多」。

固定阈值扩大 region 是双输：有些循环快 30%，ash 慢 4–9%，md5sum × 8 慢 40%，因为每次扩张都要重编译整个 region。

AES 用四张 T-table 而不是一张加 i32.rotl：aes-256-cbc 慢 3.6%，省了 6 KiB 表空间。作者给自己定的门槛是 4%，没到就否。这个细节暴露了整份文档的口径：不是「大概能快一点」，是有门槛、有幅度、有被测命令的。

把编译挪到内核线程之外：即使完全免费也只值 2.4%（shell）到 4.5%（npx）。这条直接否掉了一整类优化方向。

数据 TLB 加到 4096 项：claude --help、npm、bun 的差异在噪声内，换 4 倍内存。而不砍半幸存路的 progress 会让 npm 慢 23.2%。

还有一条我特别喜欢，因为它承认了语义正确性优先于性能：SMP 下如果编译完立刻取 pending interrupt，JIT 会比解释器更早响应中断，两层的可观测行为不一致。所以 kwemu 改成在编译前查。为了「JIT 和解释器的输出必须逐位一致」，牺牲了一点延迟。

这些条目的共同点是：每一条都写清了被测的是什么命令、差多少、门槛多少。这比任何「我们的架构很先进」都有说服力。

它现在还不能做的事

作者自己列了 Known limits，我挑对使用者影响最大的：

  • 无 IPv6，无 DHCP/DNS 之外的 UDP，无入站连接。 想在 guest 里起个服务让外面访问，得走 vm.connect()、vm.fetch() 或 --forward 走 vsock，不是普通 TCP。
  • SDK 和 CLI 默认单 CPU。 页面能开多核（?cpus=），但多 CPU 的快照只能恢复到同样的核数上，别指望快照可移植。
  • 没有硬件断点/观察点。 gdb 的 watchpoint 是软件断点，靠单步实现，在大程序上会很慢。
  • 只跑几次的代码永远留在解释器上。 大程序启动（比如 npm 那类）基本吃不到 JIT 好处。浮点和 AdvSIMD 即使进了编译代码也走解释器；宿主引擎没有 wasm SIMD 时，OpenSSL 的 AES 和 SHA 路径也退回解释器。
  • 内核里一次 wasm trap 直接结束会话。 不是 panic 后还能抓现场，是整个 session 没了。

SMP 那块还有一组数字值得单独拎出来，因为它暴露了「编译」和「抢占」的冲突：编译一个 region 的几百微秒里，其他 CPU 的 IPI 得等。作者做了个 compile window 后，20 秒内 mprotect 次数从 5.53M 提到 7.07M，p99.9 延迟从 130 µs 降到 13 µs，最大延迟从 20.0 ms 降到 3.9 ms，超过 1 ms 的调用从 194 次降到 3 次。这类优化不改变架构，但决定了它能不能扛住多核工作负载。

我自己的判断

我说三点。

第一，这个项目的真实价值不是「浏览器里的 Linux」，是它给了一个可复用的层边界论证。 「内核编译、用户态模拟」这个切法可以搬到别的地方：把不常变的部分编译掉，把需要兼容的部分模拟掉，中间用宿主提供的挂起机制接缝。这是设计模式，不是玩具。

第二，它的性能画像很清楚，别用错场景。 syscall 密集、进程创建、I/O 密集的负载，它接近原生；CPU 密集、大数组遍历的负载，它落后一个数量级以上。所以「在浏览器里跑个开发环境写 Python」比「在浏览器里跑个编译器」现实得多。README 自己说的 apk add python3 3.4 秒，就是这个边界。

第三，要警惕一个传闻。 HN 上有人说「我们刚因为它是浏览器里的重内核而埋葬了 Electron」，这话是俏皮话不是分析。Electron 的问题从来不是「里面有内核」，是每个应用各自捆一个完整的 Chromium。unkernel 的方向相反：内核 10 MB，按需拉 distro 镜像，共享宿主的 V8。要判断它能不能替代容器化方案，得看 vm.connect()、--forward 和 vsock 这套能不能撑住真实的开发流程，而不是看首页的动画。

想自己验的话，最省事的两步：

npx unkernel                        # 起 Alpine，网络走宿主 socket
npx unkernel --distro debian --data my-data.img --mount .:/work

第二条会挂上当前目录到 /work、把改动写进持久 ext4 盘。

CLI 没有开/关 JIT 的开关，要对比得走 SDK 的 jit: false；页面上是 ?jit=0：

const vm = await createKernel({ distro, jit: false });   // 纯解释器

拿这两种模式跑同一个循环，能直接感受到 JIT 只值 2 倍左右。剩下那部分差距是 TLB 查表，不是编译质量。

如果要做嵌入，SDK 是零依赖 TypeScript，内核在包里，distro 镜像不在包里（Alpine 约 4 MB，Debian 约 57 MB，首次从 release 拉取并按 distros.json 校验 size 和 SHA-256，缓存到 ~/.cache/unkernel）：

import { createKernel, fetchDistro, directBackend } from "unkernel";

const vm = await createKernel({
  distro: await fetchDistro("alpine"),
  net: directBackend(),
});
vm.onOutput((bytes) => process.stdout.write(bytes));
vm.write("uname -a; poweroff\n");
const { code, kind } = await vm.exited;   // 0, "halt"

一个诚实的结尾：这项目 11 月 12 日建仓，到现在 1462 stars、72 forks，代码是 TypeScript 3.1 MB + Zig 1.06 MB + C 723 KB。作者自己在 Credits 里写明受 Kernarium、linux-wasm、iSH、v86 启发，GL 那套是 virglrenderer 用 Emscripten 编到 wasm 走 WebGL2。它不是从零发明，是把几块现成拼图按一个不常见的顺序拼了起来——而这个顺序，恰好是别人没试的那一种。
