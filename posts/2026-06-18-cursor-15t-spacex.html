Cursor 的武器库远不止 IDE：Composer 2.5、Cloud Subagent、Origin，一场开发者平台的全面战争

2026-06-18
  • AI编程
  • 开发工具
  • 架构

SpaceX 花 600 亿美金买 Cursor 的消息出来当天，市值蒸发 6000 亿。华尔街的直觉是「马斯克又冲动了」。但这个判断忽略了一件事：Cursor 在过去半年里已经从 IDE 插件悄悄长成了一个完整的开发者平台，而大多数人只注意到它「AI 改 VS Code」的那一面。

我翻了 Cursor 最近的 Changelog 和技术文档，发现他们的武器库远比想象中深。

Composer 2.5：不是换基座，是自研推理引擎

先说 Cursor 1.5T 新模型的事。外界报道的「放弃 Kimi 基座」只说对了一半。Cursor 的新模型从 Composer 2.5 开始就是自研的，不是简单地换个 API 供应商。

从 Changelog 里能看到几个关键数据。Bugbot 的底层模型已经切到 Composer 2.5，带来的性能提升很具体：平均 review 时间从 5 分钟降到 90 秒，每次 review 发现 10% 更多的 bug（0.62 个 vs 0.56 个），每次运行成本还降了 22%。这不是渐进式改进，是指标级的跳升。

更有意思的是，「Bugbot respects model block lists」这句话说明 Cursor 的模型体系已经不是单一模型了。不同任务用不同规格的模型实例：Bugbot 跑在 Composer 2.5 上，代码补全可能跑在更轻量的模型上，复杂重构任务可能路由到更大的模型。这套路由层是 Cursor 自己做的基础设施，和 Kimi 或任何第三方 API 都无关。

那么为什么之前要用 Kimi？创业公司的典型路径：先用现成 API 跑通产品、验证 PMF，用户量上来之后自研推理引擎降本增效。Cursor 在 2025 年底到 2026 年初完成了这个过渡。1.5T 参数规模的定位也合理——比开源社区的 7B-70B 大得多（能处理复杂重构），又比万亿参数模型推理成本低（能跑实时补全），是 IDE 场景的甜点区间。

真正的杀招：Cloud Subagent + Cloud Environment

很多人只把 Cursor 当本地 IDE 用，但它最值钱的东西其实是云基础设施。Cursor 现在支持：

Cloud Environment Setup：在云上自动搭建开发环境，不到 10 分钟。Agent 会在共享终端里安装依赖、配置工具链，整个环境被快照成可复用的镜像。这意味着新开发者 onboarding 从「花半天配环境」变成「点一下，等 10 分钟」。环境快照是增量式的——依赖不变的时候复用缓存，只有 lockfile 变了才重装。团队级的快照可以 commit 到仓库，新成员 clone 后直接激活，不需要本地装任何工具链。

Cloud Subagent：在本地 IDE 里启动一个运行在独立 VM 上的子 Agent。它有自己的分支、自己的环境，可以并行处理 CI 修复、代码库探索、长耗时重构，而不阻塞你的本地工作。关键特性是支持 handoff：本地和云之间的 Agent 会话可以无缝迁移。

技术上，云 Agent 的隔离用的是轻量级 microVM（类似 Firecracker），每个 agent 实例分配独立的内核和文件系统，但共享同一套构建缓存层。子 agent 之间不能直接通信，所有结果通过宿主 agent 中转，这是安全设计的底线：即使一个 agent 被恶意输入污染，也不会横向扩散到其他并行的 agent。

另一项关键基础设施是 Automations。Cursor 最近推出了事件驱动的 Agent 流水线：支持 Slack 表情回应触发、GitHub Issue/Push/PR Comment/Wiki/Workflow 完成六种触发器。效果就是：

  • 你在 Slack 里对一条消息回复 :cursor: 表情，云 Agent 自动拉起，执行预设任务
  • GitHub PR 创建后自动触发 Bugbot review，90 秒内返回 review 结果
  • CI 失败时自动启动 Agent 排查日志，修复并提 PR

这套系统和传统的 CI/CD 流水线的本质区别是：GitHub Actions 是确定性脚本，你写死的 YAML 决定每一步做什么。Automations 是目标驱动的 Agent——你说「修复这个构建失败」，Agent 自己决定怎么修。前者适合已知的重复流程，后者适合无法预定义的排查和修复场景。

这才是 SpaceX 愿意花 600 亿的核心原因。假设你是一个有 5000 名嵌入式工程师的火箭公司，你需要的不是一个写代码更快的编辑器——你需要的是能让每个工程师同时调度 3-5 个云 Agent 并行工作的基础设施。Starship 的飞控代码在 C++ 和 Rust 之间来回切，Starlink 的地面站软件跑在嵌入式 Linux 上，每次提交都需要跨仓库的集成测试。Cursor 的 Cloud Subagent 可以直接把这些集成测试并行化，10 个 Agent 各自测一个子系统，然后汇总报告。

从这个角度看，600 亿买的不是 IDE，是「AI 时代的 Jenkins + GitHub Actions + 开发环境管理」三合一套餐。

Origin：Agent 原生 Git Forge

Origin 的定位很精确——"A git forge for the agentic era"。不是替代 Git，是重新设计代码托管平台的上层交互模型。

GitHub 的 PR 流程是为人类协作设计的：你写代码，开 PR，等人 review，讨论，改，merge。整个周期短则几小时，长则几天。但 Agent 写代码的速度是人类的 10 倍以上，这个流程就成了瓶颈。

Origin 的设计假设是：代码的主要生产者和消费者都是 Agent。流程变成了：

  1. 本地 Cursor Agent 写完代码，自动推送到 Origin 的分支
  2. Origin 的 CI 自动触发（不是手动配置 YAML——Agent 自动根据项目结构推断）
  3. Bugbot（Composer 2.5）自动做代码审查，标注语义错误、安全风险、测试覆盖率缺口
  4. 如果发现的问题在阈值以下，自动 merge；以上，回传 Agent 修改
  5. 人类开发者只需要看最终汇总报告

这套流程的关键创新不在 UI 上，在「Agent 驱动的协作格式」：Origin 定义了一套 Agent-to-Agent 的代码审查协议，Bugbot 的 review 结果不是给人看的评论，而是结构化的 JSON——包含问题类型、影响范围、修复建议的 diff patch。另一个 Agent 可以直接消费这个 JSON 来自动修复。

这种 A2A（Agent-to-Agent）协作协议是 Origin 和 GitHub 最根本的分野。GitHub 的 API 是 RPC 风格的——创建 Issue、添加评论、merge PR，每一步都是离散的操作。Agent 用 GitHub API 的效率很低：它要先 poll 事件、解析人类语言评论、再决定下一步动作。Origin 的协议是事件驱动的——Agent 直接订阅代码变更流，收到的是结构化的 diff 和 review 结果，不需要解析自然语言。这听起来是个小差异，但在大规模 Agent 协作的场景下，API 调用量差异是两个数量级。

Origin 的第二个技术创新是 AI 驱动的 CI 配置推导。传统 CI（GitHub Actions、GitLab CI）需要开发者手写 YAML，定义每一步的 runner、镜像、命令。Origin 的 Agent 在创建 Cloud Environment 的时候就自动识别了项目类型（npm/pip/cargo/cmake），推断出测试命令和构建流程。不需要 YAML 文件，不需要配置 runner 矩阵——Agent 根据项目结构自动决定 CI 策略。对于有 50 个微服务的公司来说，这意味着从「维护 50 套 CI 配置」变成「零配置」。

Continue.dev 收购：模型市场的前奏

收购 Continue.dev 最被低估的价值是它的 Provider 抽象层。Continue 的架构本质上是一个模型路由网关：同样的请求可以发给 OpenAI、Anthropic、本地 Ollama、或者任何自定义 endpoint。Cursor 拿到这个之后，可以做两件事：

第一，开放模型市场。第三方模型通过 Continue 的接口接入 Cursor 生态，Cursor 抽成。比 OpenAI 的 GPT Store 更有想象力的是——开发者写代码的时候天天在用，使用频率碾压 ChatGPT。

第二，做弹性推理。Cursor 自研的 Composer 2.5 处理核心任务，复杂任务回退到 Claude/GPT，简单任务在本地小模型上跑。这套路由策略 Continue 的架构天然支持。

一次架构级的生态迁移

把上面所有组件连起来看，Cursor 在做的事情是一套从底层模型到上层协作协议的全栈闭环：

应用层：   Cursor IDE（本地） + Origin（云端）
协作层：   Automations（事件驱动） + Bugbot（自动审查） + A2A 协议
平台层：   Cloud Subagent（微VM） + Cloud Environment（快照）
推理层：   Composer 2.5（自研 1.5T） + Continue 路由网关（第三方回退）

每一层都对应一个传统开发工具栈里的替代品，但 Cursor 把它们向上集成到了一个统一层里。对比微软的开发者工具栈：

GitHub →  VS Code →  Copilot →  GitHub Actions →  CodeQL
  (托管)    (IDE)     (AI)        (CI/CD)          (扫描)

微软的问题是这四样东西是四个独立产品，各有各的产品经理、技术栈和 API。集成靠的是「微软生态」这个抽象概念，但实际用起来，Copilot 不知道你的 Actions 配置，Actions 不知道你的 CodeQL 结果。Cursor 的所有层共享同一个上下文：Agent 写完代码 → 自动提交到 Origin → Bugbot 自动审查 → Automations 在 Slack 通知你 → 你点 approve 就上线。整个流程的上下文不离开 Cursor 的边界。

这不是一个功能清单，是一套完整的基础设施。每个组件单独看都有竞品，但把它们集成到一个端到端平台里的，目前只有 Cursor。

一个开发者的视角

我用 Cursor 两年了。从它还是 VS Code fork 的时代开始，到后来出 Tab 补全、出 Agent 模式、出 Composer，一步步看着它从「更聪明的编辑器」变成「你不想换回 VS Code 的理由」。说几个个人感受：

Cloud Subagent 是体验的质变。本地 Agent 做不了的事情太多了——编译耗内存的项目会卡死编辑器，跑集成测试要等十几分钟，并行改四个仓库要来回切换窗口。把这些全扔到云端，本地 IDE 只做编辑和预览，流畅度提升很明显。但这个能力的门槛很高：不是每个 AI 编程公司都有资源自建 microVM 集群的。SpaceX 的 600 亿如果能转化成星链带宽、数据中心、GPU 集群这些基础设施，那 Cursor 的机会确实很大。

最大的风险是单点依赖。如果 Cursor 的所有能力都跑在它自己的云上，断网就等于没法写代码。本地模型的离线能力是个硬需求，特别是我这种偶尔要在没有互联网的环境下工作的场景。Cursor 说 Subagent 支持 handoff 到本地，但这套机制有多可靠还需要验证。

Origin 的冷启动问题也同样棘手。开发者社交网络的迁移成本高到离谱。Origin 在技术上可能确实比 GitHub 更先进，但你的 500 个 star、200 个 issue、PR 历史、Actions 缓存全在 GitHub 上。Origin 要说服开发者「值得重新开始」，光靠体验碾压还不够，需要给出迁移工具链。目前没有看到 Origin 提供 GitHub 导入工具。

马斯克的第一刀砍向微软 GitHub，不是因为 GitHub 不好用——而是因为微软的开发者工具栈是上个时代的架构：以人类开发者为中心，AI 只是辅助。Cursor 的架构是以 Agent 为中心，人类是监督者。两种架构对基础设施的要求完全不同。

这场仗的赌注不是 IDE 市场份额，是下一代开发者工作流的定义权。
