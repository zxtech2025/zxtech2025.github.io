284B模型塞进64GB内存：llama-modchip的1.71bpw量化与四层Cache分块内核

2026-11-09
  • LLM推理
  • 量化
  • MoE
  • AVX-512
  • llama.cpp

HN上有个项目这周被反复顶上来：llama-modchip，宣称把284B的DeepSeek-V4-Flash塞进一台64GB内存的普通桌面机，零GPU，256K上下文，还不用swap。仓库10月29号建的，11天658星，今天还在推代码。

标题听着像营销，但把README、FAQ和scripts/transcode_dsv4_shard.py读完之后，里面有几块硬东西值得拆：一个自定义的2bit量化格式、一套靠闭式解算出来的专家重要性权重、一套把DDR5带宽瓶颈往cache层级上挪的GEMM分块。另外有几个数字我自己算了一遍，和他们的宣传口径对不齐，这部分更有意思。

先说结论：这个项目确实把模型塞进去了，但"跑得动"和"跑得快"是两回事。真跑起来你才会发现，卡住速度的是每个token那2.5GB权重要从DDR5搬一遍，内存反而不是问题。

一、先算清楚账：284B × 1.71bpw 并不等于56.56GiB

README写得很整齐：284.33B总参数、13.17B激活、1.71bpw、56.56GiB。但这个1.71是平均出来的。FAQ自己承认：284B × 3.75bpw 会是133GiB，根本装不下。

我按他们的分层配方重算了一遍：

张量组 参数量 量化格式 位宽 磁盘占用
MLA + Indexer Compressor（dense） ~11.8B Fractal-64 (Q2_0) 3.75bpw ~5.2GiB
256路由专家 ffn_{gate,up,down}_exps ~265B IQ1_S / IQ1_M / IQ2_XXS 1.5625–2.0625bpw ~48.2GiB
共享专家 + embedding + norms + lm_head ~2.8B Q5_K/Q6_K/F32 ~4bpw ~1.3–2.8GiB

加起来约54.7–56.6GiB，跟56.56对得上（差异来自我按4bpw估的那2.8B），平均1.65bpw左右。所以真实结构是两套完全不同的位宽：dense张量给到3.75bpw保精度，占体积95%的路由专家压到1.5625bpw。dense层每个token都过、专家层每个token只过6/256，这个取舍是合理的，但照1.71bpw去估算自己的模型会算错。

整个模型从源头的UD-IQ1_S（76.87GiB）压到56.56GiB，砍掉20.31GiB，是原体积的73.6%。

二、SwiGLU-H2：不跑校准集，怎么定每个专家的量化权重

常规的GPTQ/AWQ量化需要跑一批校准数据，统计激活值来决定每个通道的敏感度。问题是：284B的模型跑一遍校准集，光前向就要几小时，还得先把未量化的完整模型加载起来，64GB的机器根本做不到。

llama-modchip绕开了这一步。它用的是SwiGLU结构的一个闭式性质。

SwiGLU的FFN是：

h_j = SiLU(g_j) * u_j      g = W_gate * x      u = W_up * x

在激活值近似各向同性、单位方差的假设下，第j个中间通道输出的能量期望正比于两个矩阵行范数平方之积：

E[h_j^2]  ∝  ||W_gate[j,:]||^2  *  ||W_up[j,:]||^2

这个量完全从权重本身算得出来，不需要任何数据。代码里确实是这么干的：处理ffn_down_exps.weight时，先把同层ffn_gate_exps和ffn_up_exps的指针取出来，连同目标缓冲区一起传给C扩展：

if name.endswith("ffn_down_exps.weight"):
    gt = by_name.get(f"blk.{blk_id}.ffn_gate_exps.weight")
    ut = by_name.get(f"blk.{blk_id}.ffn_up_exps.weight")
    if gt and ut:
        gate_ptr = src_base_addr + data_start + gt["orig_off"]
        up_ptr   = src_base_addr + data_start + ut["orig_off"]
lib.transcode_moe_exps(..., ncol, nrow, n_exp,
                       gate_ptr, gate_t, up_ptr, up_t)

为什么down要单独处理：down的输入维上每一行，对应gate/up输出的一个通道。

这个思路在文献里叫data-free importance，不是新东西，但落地很干净：一次性流式读三个张量、算完立刻posix_fadvise(..., POSIX_FADV_DONTNEED)把页缓存踢掉，否则在64GB机器上转码56GB模型会直接把内存打爆。

三、锚定层：哪些层不敢压

代码里有一组硬编码的层号集合，这是全篇最"工程"的部分：

GATE_UP_KEEP_IQ2 = {1, 4, 26, 28, 40}          # 这几层的 gate/up 保持 IQ2
DOWN_IQ2_LAYERS  = {0, 1, 26, 28, 41, 42}      # 这几层的 down 给 IQ2_XXS
DOWN_IQ1M_LAYERS = {2, 4, 5, 8, 27, 30, 32, 40} # 这几层给 IQ1_M
# 其余一律 IQ1_S (1.5625bpw)

为什么是这几个数？因为DeepSeek-V4-Flash的43层里，前3层（il=0..2）用的是token-ID哈希路由，不是学出来的router：

  • il = 0..2：ffn_gate_tid2eid把token ID直接映射到6个词法专家，权重接近均匀（0.22–0.30）。这几个专家是"查表"性质，砍掉任何一个等于丢了1/6的词汇查找能力。
  • il = 3..42：真正的Top-K路由器，SQRT_SOFTPLUS激活。这里专家权重呈幂律分布，top-4能覆盖约81.2%的路由权重。

所以哈希层的0/1/2和首尾边界层26/28/40/41/42被单独保护，中间的层才敢往1.5625bpw压。这套规则不通用，是拿具体模型的结构试出来的：换个MoE模型，这组层号得重新扫。

四、L2正交重标定：为什么不能用线性缩放

这是我认为全篇最有技术含量的一段。

既然专家层压到1.5625bpw必然掉精度，那就在运行时再省一点：每层只算top-4或top-5个专家，而不是全部6个。这样省下来的不只是计算，更是一次完整的权重读取。

但直接跳过第6个专家会让输出变小。朴素做法是按权重和做线性补偿：

alpha_L1 = sum(w_i, i=1..6) / sum(w_i, i=1..k)  ≈ 1.23  (k=4)

问题在这里：6个专家的输出向量在4096维空间里近似正交，它们的和的期望能量是 sum(w_i^2 * ||e_i||^2)，不是 (sum(w_i))^2。线性补偿会把路由分支相对共享专家放大约23%，而共享专家是没被剪的。两边的比例一失衡，下游RMSNorm一除，偏差就传到后面43层。

正确做法是按平方和补偿：

alpha_L2 = sqrt( sum(w_i^2, i=1..6) / sum(w_i^2, i=1..k) )
         ≈ 1.015 (k=5)   /   1.042 (k=4)

差别有多大？他们的实测：Top-4配置下，线性重标定的KL散度是0.0671 nats，换成L2重标定降到0.0281 nats，降了58%。而decode速度两者是一样的。

很多MoE剪枝实现（包括一些推理框架的--n-expert参数）就是少算几个专家、不做补偿，或者做线性补偿。省下来的是几十毫秒，赔进去的是输出质量的系统性偏移。

五、四层Cache分块：把瓶颈从DDR5挪走

prefill和decode的瓶颈完全不同。decode只算1个token，矩阵退化成矩阵-向量乘（GEMV），算术强度约1 FLOP/byte，被DDR5带宽卡死。prefill一次算512个token，是GEMM，算术强度上到160+ FLOP/byte，瓶颈变成计算和cache命中率。

标准ggml-cpu的问题是：vec_dot按1x1执行，一个token一次、一行权重一次。同一块量化权重，处理8个token就要从L2/L3里解包8遍。解包一个IQ1_S权重块的开销（移位、掩码、查表）跟做一次乘加的代价是同数量级的。

llama-modchip的做法是把权重块在寄存器里解包一次，乘以多个token列：

// 概念示意：权重块解码进 ZMM 后广播给 K 个 token 列
for k in {8, 4, 3, 2}:   // 按 M 的分解依次取
    解包 512-bit 权重块一次
    vpmaddubsw / vpmaddwd 覆盖 k 列输入

为什么是{8,4,3,2}这组魔数？因为任何≥2的整数都能表示成这四个数的非负线性组合（5=3+2，9=4+3+2，10=8+2）。MoE的MUL_MAT_ID按专家分桶，256个专家、平均每个专家6.5–12.7个token，桶大小极不均匀。用{8,4,3,2}凑，让"每个专家只要≥2个token"就永远不退化到1x1路径，省掉了为边缘情况写单独分支。

配套的还有几件事：

  • L2 tile 128行（64–276KB，远小于1MB L2），L1D 内层按token列分块，保证[ne00, 64]的切片常驻在32KB的L1D里。
  • _MM_HINT_NTA非临时访存：MoE专家权重用完就不会再用（1.8GB的总量远超64MB的L3），所以用NTA提示让它们不污染L3，把L3留给反复访问的KV cache。
  • quantize_row_q8_K的AVX-512重写：原来这函数在arch/x86/quants.c里是标量参考实现，每个token的激活量化都走它。改成16个ZMM寄存器的向量实现，位精确。

效果：prefill从24.70 tok/s到43.16–44.36 tok/s（+77%），decode从5.91到9.06 tok/s（+53%）。

六、我算了一遍，有个数字对不上

到这里我停下来自己核了一遍物理上限。

decode是带宽受限的。13.17B激活参数，混合位宽约1.56–2.0bpw，每个token要流的权重量是：

13.17e9 * 1.5625 bits / 8 = 2.57 GB / token

Zen 5移动平台双通道DDR5-5600的理论带宽是89.6 GB/s。照这个算，纯带宽上限是 89.6 / 2.572 ≈ 34.8 tok/s。而他们实测的decode是9.06 tok/s，反推有效带宽 2.572 GB × 9.06 ≈ 23.3 GB/s。

只有理论峰值的26%。

这个gap说明：现在卡住它的不是DDR5带宽，是每个token那4551个计算节点的调度开销。profiling表也印证了这点：单token 110.33ms里，MLA和共享专家的MUL_MAT占61.81ms，路由MoE的MUL_MAT_ID占22.27ms，HADAMARD/RMS_NORM/HC_PRE-POST/FLASH_ATTN这堆非矩阵算子合计占9.85ms。4551个节点、43层、每层几百次小算子调用堆出来的。

换句话说：1.71bpw量化把"装不下"变成了"装得下"，但没把"慢"解决掉。 9 tok/s大约是人的阅读速度的3倍，能跑agent，但谈不上流畅。真要提速，方向不是继续压位宽（已经到1.56bpw了，再压模型就废了），而是减少算子调用次数、把小的非矩阵算子融合掉。

七、几个使用上的坑

1. Q2_0是CPU专属格式。 Fractal-64用自定义type ID 42（GGML_TYPE_Q2_0），只有ggml-cpu实现了它的SIMD kernel，ggml-vulkan和ggml-cuda都没有。如果你用-ngl 99 --n-cpu-moe 30把这些层offload到GPU，GPU后端不认识这个类型，输出是空的或者乱码，而且不一定报错。

2. 未打补丁的llama.cpp/Ollama/LM Studio会直接拒绝。 报错是unknown tensor type 42。这不是文件坏了。

3. 64GB是硬下限，剩余空间只有3.6GiB。 峰值VmRSS 58.9GiB（256K上下文），64GB Linux可用约62.5GiB。留给页缓存和系统进程的空间非常窄，多开一个浏览器就可能触发OOM。想舒服一点应该上96GB。

4. 哈希层不能剪。 il=0..2永远是6/6专家，代码里写死了。这不是保守，是因为那三层是token-ID查表，剪掉就是直接丢词。

5. Mamba-2的投机解码不能回滚。 SSM的循环状态h_t不能像Transformer的KV cache那样把索引往回退。他们必须在投机批次前把46层状态（约18.4MB/slot）memcpy到slot.spec_ckpt，只要有一个draft token被拒（n_rollback > 0）就得整段回放。这也解释了为什么draft模型用的是192KB的Zobrist置换表（Stockfish那套国际象棋引擎的招法）而不是神经网络draft：在71.7GB/s的CPU上，流一个600MB的1B draft模型做5步要40ms，比直接跑目标模型还慢。

八、我的看法

这类项目把"MoE模型的内存账"摊开给你看，比它本身能不能跑更有价值。

MoE的参数量是个假指标。 真正决定能不能跑的是两个数：总量能否装进内存（否则要流式加载，延迟爆炸），激活量能否被带宽喂饱。只看一个必然判断错。这也是llama-modchip和Swiftlet的分界：Swiftlet把专家留在SSD上流式读，适合内存真的不够（4.3GB跑80B）；llama-modchip把整个模型压进内存，适合内存刚好够（64GB跑284B）。前者拿低内存换读盘延迟，后者拿1.56bpw的量化损失换零swap。

闭式重要性权重是被低估的方向。 行范数平方之积，本质上在说"gate和up同时很大的通道才重要"。不需要校准数据，不需要前向，成本是一次流式扫描。对于大到跑不起校准集的模型，这可能是唯一可行的路径。精度够不够得看任务——他们的100分质量门给了满分，但那个门是自己设计的，我要看到独立评测才会信。

另外提醒一句：别拿1.71bpw去套别的模型。 那套层号锚定（{0,1,26,28,41,42}保护、{2,4,5,8,27,30,32,40}给IQ1_M）是拿DeepSeek-V4-Flash的结构试出来的：3层哈希路由加40层学习路由、256专家、Top-6。换个MoE模型，层号和专家数一变，规则全部失效。想复现的话第一步应该是重扫敏感层，跑一遍perplexity找出哪几层一压就崩。

如果我要在64GB机器上跑，会先上30B那条路。Nemotron-3.5-30B-A3B只有14.35GiB，16–32GB机器上能到25–60 tok/s，是这套东西真正好用的区间：

git clone https://github.com/synchopate/llama-modchip.git
cd llama-modchip && ./modchip status   # 先确认AVX-512/大页支持，不下载模型
./modchip bench                        # 30秒两阶段测速，出可提交的scorecard

284B更像"证明可行"的工程样品：能跑，但9 tok/s的交互体验和紧到3.6GiB的内存余量，注定它是demo而不是日常工具。

以上数字除标注来源外，位宽换算、带宽上限、有效带宽反推都是我按公开参数自己算的，算法在文中给了，可以复现。
