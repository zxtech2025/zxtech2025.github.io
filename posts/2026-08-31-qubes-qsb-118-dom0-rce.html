Qubes OS QSB-118：复制到 VM 的报错通道如何变成 dom0 任意代码执行

2026-08-31
  • 虚拟化安全
  • Qubes OS
  • 信任边界
  • Linux

Qubes OS 在八月底发了 QSB-118，标题是"Dom0 在 qvm-copy-to-vm 错误上报中的任意代码执行"。这份安全公告的技术描述很短，但它是一个很干净的信任边界漏洞案例，值得逐句拆开看。

漏洞本体

公告里的 Summary 只有一句：

如果用 qvm-copy-to-vm 把一个文件从 dom0 复制到一个恶意 qube，那个 qube 可以向 dom0 注入任意命令。

qvm-copy-to-vm 是 Qubes 里从 dom0 往指定 qube 拷文件的工具。它在出错的时候会在 dom0 里显示一个图形化消息，消息内容包括错误信息和"受影响的文件名"——而这两个字段的来源是目标 qube 上报的。

这就是问题所在：目标 qube 是不受信任的，而它报告的内容会被受信任的 dom0 拿去显示。如果这条显示路径没有对内容做消毒，恶意 qube 只要把命令写进"错误信息"或者"文件名"里，就能让 dom0 执行。

公告里还提到，错误信息是按错误码字段上报的，dom0 会把这些信息拼进 GUI 消息。整个链条是：恶意 qube → 构造错误码/文件名 → dom0 收到 → dom0 把它拼进消息并显示 → 注入生效。

为什么"dom0 被拿下"是最高级别的失败

要理解这个漏洞的严重程度，得先理解 Qubes 的安全模型。

Qubes 的设计哲学是"通过隔离实现安全"：每个活动（浏览网页、处理不可信文档、管理密码）跑在独立的轻量虚拟机（qube）里，彼此之间靠 Xen 的虚拟化边界隔开。但它有一个绕不开的信任根——dom0。

dom0 是那个在架构上被完全信任的域，它负责：运行图形界面（GUI 域和它配合）、管理系统里所有的 qube（qvm-* 工具都在 dom0 里跑）、拥有对硬件和网络的后端控制权。在 Qubes 的威胁模型里，各个 qube 之间互相不信任，但所有 qube 都信任 dom0。

所以"dom0 被攻陷"不等于"一台 VM 被攻陷"，等于整个隔离体系失效。攻击者在 dom0 里能做的事包括：读其他 qube 的显示内容、伪造 UI 骗用户输入、修改或删除其他 qube、控制系统级配置。Qubes 里所有的安全承诺都建立在"dom0 是干净的"这个前提上，前提没了，上面的分层就都塌了。

漏洞的类：错误路径上的注入

从类型上看，这是一个注入漏洞 + 信任边界失守的组合。

注入的本质是"数据被当成了代码"。这里的数据是 qube 上报的错误信息和文件名，代码是 dom0 用来显示消息的那条路径——它很可能把内容拼进了 shell 命令、或者拼进了某个会被解析的标记语言（比如支持命令替换的通知/富文本），于是数据越过了边界变成可执行内容。

而它出现在错误路径上，这一点特别典型。开发者写 qvm-copy-to-vm 的时候，思路肯定是"把文件复制过去"这条正常路径，错误处理是顺手加的——收到错误码，显示个对话框告诉用户"复制失败了，文件名是 X"。这条路径通常测试覆盖少、审计关注少，但它的输入来源恰恰是不受信任的对端。

Qubes 这种高安全向的系统，理论上应该对"任何从 qube 流向 dom0 的数据"都做好消毒。这个漏洞说明：即使在按最严假设设计的系统里，"错误上报"这条看起来很无害的通道也容易漏掉。原因在于它不明显像一条数据通道——它长得像一个 UI 提示，而不是一个输入接口。

防御上能带走什么

即使你不用 Qubes，这个案例有几条通用的：

  • 把"显示消息"当成一个执行汇点。 任何把外部数据渲染成 UI 的地方（通知、对话框、日志查看器、终端标题），都是潜在的注入点，尤其是底层用到 shell、模板或者支持标记语法的时候。消毒规则应该跟"拼接字符串"一样严格。
  • 错误路径要按正常路径的标准审计。 错误信息、异常文本、错误码这些内容常常是攻击者可控的。问一句："这个字段如果完全由攻击者控制，最坏能造成什么？"
  • 信任边界要用类型/接口固化下来。 靠"开发者记得消毒"是靠不住的。更好的做法是让跨边界的返回值从一开始就带上"不可信"的标记，需要往下传时必须经过一个消毒函数，把消毒变成编译期或结构上的强制步骤。
  • 对不可信输入限制表达力。 如果 dom0 只需要展示"复制失败"，那错误信息的格式就该是一组枚举值，而不是自由文本。把攻击面从"任意字符串"收窄成"有限枚举"，注入的可能性直接归零。

我的做法

写跨信任边界代码时，我现在会坚持一条习惯：先分清哪些数据来自"我不信任的一端"，然后把它们全部当污染源处理。

  • 把跨边界的输入（错误码、文件名、状态文本）统一走一个边界层，边界层之外不允许直接使用这些值。
  • 展示层永远不从原始输入拼字符串。要用模板 + 转义，或者更进一步：只接受枚举和数字，文本由本地生成。
  • 安全公告里的错误路径值得单独看一遍。我自己的代码里，"panic/错误处理里顺手拼了个消息"的地方，就是最该复查的一类。

QSB-118 的修复很快，公告也写得很清楚。它的价值在于提醒：隔离系统的强度，取决于最小的那条跨边界通道。
