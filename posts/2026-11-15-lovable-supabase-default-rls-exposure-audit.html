15.9万个AI生成应用爬了一遍：缺省配置把数据库敞了多久

2026-11-15
  • 安全
  • AI编程
  • Postgres
  • 云服务配置
  • 数据泄露

11 月 2 日 Handelsblatt 发了一篇报道，标题问得很客气："流行的 AI 编程平台有安全问题吗"。汉堡一家做应用安全的公司 Crissy Field 配合做了调查，报告这几天才放出完整英文版。结论比标题难看得多：他们从 Common Crawl 里翻出 159,041 个用 Lovable 搭的项目，其中 24,664 个网站在页面加载时就把数据库记录吐了出来，不需要登录。

这个数字在安全圈被归到"vibe coding 又一个翻车案例"。但把报告的方法论读完，我发现真正的问题不在"AI 写的代码不安全"这种废话上。它暴露的是一整套架构选择的默认值问题：当后端即服务把数据库直接暴露给浏览器，而权限层需要用户手动打开时，一个不懂后端的用户造出来的每一个应用，都是一个待验证的洞。

一、攻击面是爬出来的，不是扫出来的

报告最有价值的部分是方法论，值得逐条看：

  • 数据源用 Common Crawl，时间窗口 2025 年 12 月到 2026 年 9 月，识别并分析了 159,041 个 Lovable 项目
  • 其中 34,545 个用了 Supabase 作为数据库
  • 24,664 个网站在首次加载时就通过 Supabase 发出了数据库记录，无需登录或任何交互
  • 对这 24,664 个站再做额外的只读请求，发现 7,403 个站（30%）的 10,560 张表里含有邮箱地址记录

注意报告自己写的三条限制，这几句话决定了这个 30% 该怎么读：

  1. 首屏返回数据本身不是漏洞，可能是设计上就要公开展示的
  2. 邮箱字段既可能是个人数据，也可能是公开联系方式或测试数据
  3. 只取了数据集的一部分而非全量下载，所以真实暴露量只会更多
  4. 反过来看，不含邮箱字段的个人记录被漏掉了

所以 30% 不是"数据泄露率"，只能算"在我们细查的这批站里，有邮箱记录且可被额外请求读到的比例"。这种在数字旁边主动标定边界的写法，比结论本身更专业。

报告没公布具体怎么构造请求，理由是"公开会让后续访问更容易"。这一点做得对，但这也意味着：方法不公开不影响复现，因为路径是平台的默认行为决定的。

二、路径为什么可复制：一个键加一条 REST 规则

要理解为什么"一个 app 的打法能套到另一个 app 上"，得看 Supabase 的请求模型。我把官方文档里两块拼起来看，链条非常清楚。

第一块是 API key 的定位。Supabase 当前有四种键，其中两种是给客户端（浏览器、移动端、CLI）用的：新的 sb_publishable_... 和旧的 anon JWT。官方对这类键的描述是"任何人都能读到，所以它只能触达 Row Level Security 允许的范围"。这句话本身就说明了一件事：这个键必然出现在打包产物里，泄漏不是事故，是设计前提。

键会映射到一个 Postgres 角色，规则写得很直白：

Publishable key + 未登录  → anon 角色
Publishable key + 已登录  → authenticated 角色
Secret key                → service_role（带 BYPASSRLS，绕过 RLS）

第二块是 PostgREST。Supabase 的 Data API 就是它，表名直接变成 REST 路径，列名直接变成查询参数：

# 官方文档示例：查 age 小于 13 的 people
curl "http://localhost:3000/people?age=lt.13"

# 多条件叠加，age>=18 且是学生
curl "http://localhost:3000/people?age=gte.18&student=is.true"

运算符一整套都支持：eq lt gt gte lte neq like ilike match imatch，加上 select=、order=、limit=、offset= 和资源嵌入。

把两块拼起来，攻击者拿到的就是一个通用模板：

GET https://<project>.supabase.co/rest/v1/<table>?select=*&limit=1000&offset=0
apikey: <从 JS bundle 里抠出来的 publishable key>

表名靠猜和字典，字段名从首屏的响应结构里就能反推出来。select=* 拿到一条完整记录后，所有列名都知道了，接下来就是翻页。这就是"跨 app 可复制"的机制：不是漏洞一样，是请求语法完全一样。

报告里列举的实际案例，量级可以感受一下：

  • 一个德语生活社区暴露了 8 万多份用户资料，含全名、邮箱、生日、性别，另有 20 多万条聊天消息可读
  • 多家活动主办方和餐厅数万条门票、餐饮销售记录，含邮箱、电话、地址、支付信息、票券码
  • 一家物业管理公司暴露了内部邮件的 AI 生成摘要，内容涉及租户和业主
  • 一家服务商暴露了 1000 多条身份证件信息，含护照号、有效期、国籍
  • 另外还有数万份合同、发票、私人相册、内部即时通讯记录
  • 一家服务商 28 万封发给客户的邮件可读

护照号那一条是典型的身份盗用素材，不需要任何"高级技巧"。

三、根因不是漏洞，是两个默认值叠加

如果只是"用户忘了开 RLS"，那就是教程没写清楚。但我把官方 RLS 文档翻到 Default privileges 一节，看到的是另一回事。

文档原文的意思是：在已有项目上，public schema 里新建的表，默认就把全部权限授予了三个角色——anon、authenticated、service_role。默认授予的权限包括 select、insert、update、delete、truncate、references、trigger，Postgres 17 上还有 maintain。

表格里"应该保留什么"那一列，anon 对应的是"只有未登录访客该读的东西"，authenticated 是"只有你的应用暴露给登录用户的操作"。也就是说，默认值与"应该"之间是错位的，需要用户自己纠正。

更关键的一句：policy 不会收回 grant。 一张表只靠 policy 保护，如果你从没 revoke 掉 grant，它依然给 anon 留了一条 insert 路径。

这就解释了大量案例的形成路径。一个不懂后端的用户做应用时，模型给的 SQL 通常长这样：

-- 模型很爱生成这种"能跑起来"的策略
create policy "公开可读" on profiles
  for select to anon, authenticated
  using (true);

using (true) 的意思是：这个角色能通过 grant 触达的每一行，全部放行。文档专门警告了这一点——"只对本来就该公开的数据使用"。但当用户的目标是"让页面能显示数据"时，true 是最省事的写法。

再加上视图这一层。文档里有一句容易漏掉的：

视图默认绕过 RLS，因为通常由 postgres 用户创建，Postgres 自动把它建成 security definer。一个建在受保护表上的视图，会把它本来该拦住的所有行全部发出去。

于是形成三个默认值的串联：新表默认全授权 → policy 不回收授权 → 视图绕过 RLS。任何一个环节用户没意识到，数据就出去了。而这三条都写在文档里，只是分散在不同页面，需要读完才知道它们会组合成一个洞。

四、我自己会怎么做这套检查

报告结尾的建议偏管理层（"上真实数据前找专家评审权限"）。对实际在写代码的人来说，缺的是能直接跑的东西。以下是我自己会用的检查顺序。

1. 从攻击者视角先验一遍

不要先看代码，先看线上。打开 DevTools，Network 面板筛 rest/v1，看首屏有没有直接打表。如果有，复制那条请求，把 select=* 加上，limit 改成 1000，翻几页。

这一步能做的原因是：请求本身就是攻击载荷。如果 1000 条能拿到，后面加 offset 就能把整表拿走。

2. 查 schema 里哪些表没开 RLS

-- 已启用 RLS 的表
select schemaname, tablename, rowsecurity
from pg_tables
where schemaname = 'public';

-- 更直接：列出所有暴露 schema 里没开 RLS 的表
select c.relname
from pg_class c
join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public'
  and c.relkind = 'r'
  and c.relrowsecurity = false;

这条查询应该是空的。不是空的就说明有人跳过了这一步。

3. 查有没有 using (true) 直接放给 anon

select schemaname, tablename, policyname, roles, cmd, qual
from pg_policies
where schemaname = 'public'
  and (qual = 'true' or qual is null)
order by tablename;

qual is null 要一起查，因为 insert 类 policy 用的是 with check，qual 为空，容易漏。再补一条看 with check：

select schemaname, tablename, policyname, roles, cmd, with_check
from pg_policies
where schemaname = 'public' and with_check = 'true';

4. 查 grant 和视图

-- anon 到底被授了哪些权
select table_name, privilege_type
from information_schema.role_table_grants
where grantee = 'anon' and table_schema = 'public'
order by table_name;

-- 有没有 security definer 的视图暴露在 public
select n.nspname, c.relname
from pg_class c join pg_namespace n on n.oid = c.relnamespace
where c.relkind = 'v' and n.nspname = 'public';

视图命中之后，判断它是不是 security definer，是的话就得单独给它加 security_invoker = true（Postgres 15+）或者干脆不暴露。

5. 把上面这些写成测试，别靠记

官方流程里有一句值得抄作业：每张表都在 supabase/tests/ 下建一个 .sql 文件，对 select、insert、update、delete 四个操作，分别断言 anon 和 authenticated 的 allow 与 deny，然后 supabase test db 跑一遍。文档的原话是"在测试套件通过之前，你不知道 policy 是不是真的按你想要的在工作"。

这一点我认同得很彻底。RLS 是一段求值在数据库里的逻辑，肉眼 review 的成功率很低，尤其是它只在你手动点过页面的那几条路径上被验证过一次，剩下 90% 的列和行根本没试过。

6. 一件事别做：把 secret key 当"保险"塞进客户端

service_role 和新的 sb_secret_... 带 BYPASSRLS。文档说得很明确：只能存在服务端、Edge Function、cron 里。有些教程为了让数据"能读出来"，会直接建议在前端用 service key——这一下把所有权限层全部作废，比 using (true) 严重一个量级。

五、这件事真正该记下的教训

我不太认同把这事说成"AI 编程不安全"。人工写的应用同样会犯这个错，过去十年 Firebase 的公开规则、S3 的公开桶都出过一模一样的量级。

真正变了的是三件事，按重要性排：

第一，产出速度和检查速度脱钩了。 过去一个人一年做三个应用，每个都可能被 review 一遍。现在一个人一周做三十个，权限层没人看过。报告里 159,041 个项目这个数字本身就是这个变化的度量。而且样本取自 Common Crawl，意味着这些是被爬到的、公开可访问的——真实总量只多不少。

第二，模式化让攻击成本趋近于零。 同一个平台、同一套默认值、同一种请求语法，攻击者写一个脚本就能横移。人工项目各有各的乱法，平台化项目是整齐地乱。

第三，不懂后端的用户无法自查。 这不是能力问题，是抽象层级的问题。当"发布"是一个按钮时，用户看到的是自己的应用能用了，看不到背后多了一个匿名可读的接口。报告里那句话说得克制："易用的开发平台不消除在应用处理机密数据前做专家评审的必要性。"

对我自己，落地的就一条：任何应用接入真实用户数据之前，先按攻击者的方式把首屏请求重放一遍。 五分钟能做完，能挡掉这次报告里 90% 的案例。剩下那 10% 需要写测试，那就写测试。
