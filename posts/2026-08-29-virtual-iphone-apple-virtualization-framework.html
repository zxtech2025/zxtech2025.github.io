用 Apple Virtualization.framework 启动一台虚拟 iPhone

2026-08-29
  • iOS
  • 虚拟化
  • Apple Silicon
  • 安全研究

Lakr233 开源了一个叫 vphone-cli 的工具，能在 Apple Silicon 的 Mac 上启动一台虚拟 iPhone。它的 README 很直白：用 Apple 的 Virtualization.framework，复用 PCC 研究虚拟机的基建。

这条值得记，因为它揭示了一个之前不那么显眼的能力：macOS 上那套给 Linux/ macOS 客户机用的虚拟化 API，其实也能承载 iOS。

它是怎么搭起来的

先看依赖清单，因为它几乎把整个流程都说清楚了：

brew install python@3.13 aria2 wget gnu-tar openssl@3 \
  ldid-procursus sshpass keystone cmake libusb ipsw zstd

几个关键的：

  • ipsw 是用来下载和解析苹果固件（IPSW 文件）的工具。要起一台 iOS 客户机，你得先把固件拉下来、解出内核和根文件系统。
  • ldid-procursus 是给 Mach-O 二进制签权限（entitlements）的工具，特点是不需要开发者证书就能签。苹果私有权限（比如下面要说的 PV=3）没法用普通证书签发，所以需要它。
  • sshpass 说明工具会通过 SSH 自动连接客户机——启动之后要非交互地执行命令。
  • keystone 是汇编框架，libusb 是 USB 相关，cmake/zstd 属于常规构建依赖。

构建只有三步：

git clone --recurse-submodules https://github.com/Lakr233/vphone-cli.git
./scripts/setup_tools.sh
./scripts/build.sh

setup_tools.sh 装依赖、构建工具链子模块、建 Python venv；build.sh 编译并签名。

硬性前提：放松 SIP 与 AMFI

README 里有一条前置条件很关键：需要放宽 SIP/AMFI，以便给未签名二进制授予私有的 PV=3 权限。

拆开看这三件事：

SIP（System Integrity Protection）是 macOS 的系统完整性保护，会阻止对系统目录和保护路径的修改。AMFI（Apple Mobile File Integrity）是负责校验代码签名的内核机制——它决定一个二进制能不能带着某组 entitlements 运行。

苹果的 Virtualization.framework 提供的公开 API，面向的是"跑 Linux/macOS 客户机"这类场景。要让它在客户机里跑 iOS，需要用到一层私有权限 PV=3。私有权限的特点是：没有官方证书链能签它，只能靠 ldid 这类工具直接写进二进制的 entitlements 段；而 AMFI 默认会拒绝这种没有合法签名的权限，所以必须把 SIP/AMFI 放松，让未签名但带私有权限的二进制能够加载。

这一步是整套方案的门票，也是它最大的代价——你要先削弱宿主 Mac 的系统保护，才能跑起这个虚拟机。对一台"只用于 iOS 安全研究的机器"可以接受，对日常主力机就不是个好主意。

为什么要复用 PCC 的基建

README 提到它"使用 PCC 研究虚拟机的基建"，这是理解可行性的关键。

PCC（Private Cloud Compute）是苹果那套跑在自研芯片上的隐私云计算节点。为了让外部研究者能审计 PCC 节点的行为，苹果提供了一个基于 Virtualization.framework 的研究虚拟机——本质上是一个"能在 Mac 上以受控方式跑苹果私有 guest 环境"的框架。

vphone-cli 的思路就是：既然苹果自己用 Virtualization.framework 做了个能跑私有 guest 的基建，那顺着这条路，把 guest 换成 iOS 也是可行的。这属于典型的"官方工具的最小意外用法"——苹果开放 PCC 研究 VM 是为了透明性，而透明性必然要求把私有 guest 的启动路径暴露出来。

安全研究上的价值

一台不用越狱、不用物理设备、可以任意重置的 iOS 虚拟机，对做 iOS 安全的人意味着什么：

  • 快照与回滚。跑一个可疑样本之前打个快照，崩了或者被污染了直接回滚，不用重刷真机。
  • 无设备依赖。CI 里跑 iOS 侧的分析不需要一堆真机排排坐。
  • 可观测性。宿主是 macOS，你可以用标准的调试和分析工具观察客户机的行为，比在真机上方便得多。
  • 可重复。客户机状态完全由固件和配置决定，实验可复现。

它的局限也明显：需要削弱宿主保护、依赖未公开的私有权限、且跟着苹果固件版本走（固件一升级，路径可能就变）。这是个研究工具，不是产品。

我的做法

这类"用官方虚拟化 API 跑非预期 guest"的项目，我会看两个信号：

  • 它依赖哪些私有权限。 公开 API 做不到的事，一定要靠私有权限补。私有权限越多，方案的寿命越短。
  • 它对宿主的保护做了什么让步。 关 SIP/AMFI 是重大让步。如果项目能在一个专用机器或独立用户空间里跑，风险可以接受；否则要掂量。

vphone-cli 把这两点都写在 README 最前面，这个做法本身值得肯定——工具敢把代价摆在明面上，用的人才知道自己在签什么。
