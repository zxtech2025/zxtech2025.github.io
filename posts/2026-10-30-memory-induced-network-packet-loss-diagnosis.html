一次内存引起的网络丢包：从现象到根因的排障路径

2026-10-30
  • 运维
  • 网络排障
  • 内存
  • 丢包
  • 性能分析

丢包是最难查的故障之一。

因为它不像宕机那样给你一个明确的错误，也不像慢查询那样有个清晰的耗时。它只是偶发地、随机地让一部分请求消失，日志里可能什么都没有。

这篇文章讨论一类具体的、容易被忽视的丢包原因：内存问题导致的网络丢包。

不聊具体的某个案例，而是把这类问题的排查路径讲清楚——因为关键不是记住某次怎么修的，而是形成一套可复用的诊断思路。

一、先确认：真的是丢包吗

这是最容易踩空的一步。很多人一看"请求超时"就断定丢包，其实可能是：

现象 真实原因 区分方法
请求超时 服务处理慢 看服务端处理耗时
请求超时 连接建立失败 看 TCP 握手状态
请求超时 真的丢包 ping / mtr / 抓包
请求失败 应用层错误 看 HTTP 状态码/错误码

分层定位

应用层报错？
  ├─ 有明确错误码 → 应用问题，不是丢包
  └─ 超时/无响应 → 往下查

传输层通不通？
  ├─ ping 丢包率高 → 网络层问题
  ├─ ping 正常但 TCP 建连失败 → 可能是 SYN 丢包/防火墙
  └─ TCP 建连正常但传输卡 → 可能是 MTU/拥塞/缓冲区

系统层有没有异常？
  └─ 内核丢包计数、内存、中断

二、内核层的丢包计数：最容易被忽略的地方

Linux 内核会把各种原因的丢包记录在统计计数器里，但很多人只看 netstat -s 的汇总，不看细分。

关键计数器

# 全局丢包统计
netstat -s | grep -iE "drop|overflow|error"

# 或更详细的
nstat -az | grep -iE "drop|overflow"

几个值得重点关注的：

计数器 含义 常见原因
TcpExtTCPBacklogDrop 全连接队列满 应用 accept 太慢
TcpExtListenOverflows listen 队列溢出 accept 跟不上
TcpExtTCPReqQFullDrop 半连接队列满 SYN flood / 建连太快
TcpExtTCPTimeouts TCP 超时重传 网络质量
TcpExtTCPAbortOnMemory 内存不足导致断开 内存压力
TcpExtPruneCalled 内存压力下裁剪发送缓冲 内存压力

最后两个是关键

如果你的丢包伴随 TCPAbortOnMemory 或 PruneCalled 增长，那问题就在内存，不在网络。

# 持续观察（每2秒一次）
nstat -n -z 2 | grep -E "AbortOnMemory|PruneCalled|BacklogDrop"

三、内存怎么导致丢包

这里要理解一个机制：内核的 socket 缓冲区是从系统内存里分配的。

传导路径

系统内存紧张
    ↓
内核启用内存回收压力
    ↓
socket 缓冲区被裁剪（prune）
    ↓
接收窗口缩小 / 发送缓冲不足
    ↓
数据发不出去 / 收到的数据被丢
    ↓
上层感知：丢包、超时

三个具体机制

机制一：tcp_mem 限制

sysctl net.ipv4.tcp_mem
# 输出：单位是"页"，不是字节
# 例：94011  125351  188022
#      ↑min   ↑pressure ↑max
  • 低于 min：无压力
  • 超过 pressure：开始裁剪 socket 缓冲
  • 超过 max：拒绝新连接

机制二：rmem/wmem 上限

sysctl net.core.rmem_max net.core.wmem_max
sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem

给得太小，高带宽长肥管道（BDP 大）场景下缓冲不够，丢包；给得太大，内存压力大。

机制三：内存回收抖动

当系统在做频繁的内存回收时，网络处理会被拖慢，间接导致丢包。

# 看回收压力
cat /proc/vmstat | grep -E "pgscan|pgsteal|pgmajfault"
# 看是否有 OOM 前的征兆
dmesg | grep -iE "oom|out of memory" | tail -20

四、完整排查路径

按这个顺序走，能大概率定位：

第 1 步：确认丢包位置

# 从本机到对端，逐跳看丢包
mtr -rwc 100 <target>

# 本机抓包看是否收到
tcpdump -i any -nn 'host <target> and tcp' -w /tmp/cap.pcap
# 然后用 wireshark 或 tcpdump 读，看重传/乱序

关键问题：丢在发出前，还是丢在到达前？

本地抓包有、对端没收到 → 网络问题 本地抓包都没有 → 系统/应用问题

第 2 步：看内核计数器

nstat -az | grep -iE "drop|overflow|prune|abort"

对比两个时间点，看哪个在增长。

第 3 步：看内存状态

free -h
cat /proc/meminfo | grep -E "MemAvailable|MemFree|Cached|Slab"
# Slab 特别值得看：内核对象占用
slabtop -o -s c | head -20

注意 MemAvailable 而不是 MemFree——MemFree 低很正常（缓存会用满），MemAvailable 才是真正可用的。

第 4 步：看 TCP 缓冲配置

sysctl net.ipv4.tcp_mem net.ipv4.tcp_rmem net.ipv4.tcp_wmem
sysctl net.core.rmem_max net.core.wmem_max net.core.netdev_max_backlog

第 5 步：看应用侧

# 每个连接的收发队列是否堆积
ss -tnmi | head -40
# Recv-Q / Send-Q 堆积说明应用读得慢

五、常见调整

警告：调参前先解释现象。 不懂原因乱调，往往是把问题藏得更深。

如果是全连接队列溢出

# 应用 accept 太慢 —— 优先优化应用，而不是调参
sysctl net.core.somaxconn          # 增大 backlog
sysctl net.ipv4.tcp_max_syn_backlog

优先看应用是不是被 CPU 或 GC 卡住了。

如果是内存压力导致裁剪

# 提高 tcp_mem 上限（单位：页，1页=4KB）
# 例：18GB 内存机器，可以给到 max = 4GB / 4KB = 1048576 页
sysctl -w net.ipv4.tcp_mem="100000 300000 1048576"

但更好的做法是找出谁在吃内存。 调高上限只是延后问题。

如果是 BDP 大导致缓冲不足

# 高带宽长延迟场景
sysctl -w net.ipv4.tcp_rmem="4096 87380 16777216"
sysctl -w net.ipv4.tcp_wmem="4096 65536 16777216"
sysctl -w net.core.rmem_max=16777216
sysctl -w net.core.wmem_max=16777216

六、这次排查的方法论

把上面的路径抽象一下，其实是三步：

1. 定位层级

网络问题有明确的层次：物理 → 链路 → 网络 → 传输 → 应用。

先确定在哪一层，再往下挖。 不要一上来就抓包，也不要一上来就调内核参数。

2. 找增量而不是绝对值

内核计数器都是累计值。看增长速率，不看总量。

# 两次取样看差值
nstat -az | grep AbortOnMemory > /tmp/a
sleep 60
nstat -az | grep AbortOnMemory > /tmp/b
diff /tmp/a /tmp/b

3. 解释现象再动手

任何调整前，先能回答："这个参数变化会怎么影响我观察到的现象？"

答不上来，就还没找到根因。

七、一点提醒

"内存引起网络丢包"这类问题，最容易在两种场景出现：

  1. 容器化环境下：容器有内存限制，但内核网络缓冲是整个宿主的，容易超限
  2. 高并发长连接场景：每个连接都占缓冲，连接数一多，内存压力就上来了

如果你在用容器，特别要查一下：

# 容器内存限制 vs 实际使用
docker stats --no-stream
# 宿主机的内核网络内存
cat /proc/net/sockstat
# 输出里的 TCP: inuse / orphan / tw / alloc / mem
# mem 那项是页数，和 tcp_mem 上限对比

/proc/net/sockstat 里的 mem 字段很多人不看，但它直接告诉你当前 socket 缓冲用了多少内存。如果它贴近 tcp_mem 的 pressure 值，问题就找到了。
