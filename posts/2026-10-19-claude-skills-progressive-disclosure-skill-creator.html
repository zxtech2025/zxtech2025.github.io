Claude Skills 源码拆解：431 字节的触发代价、被低估的执行脚本，以及那个自己跑评测的 skill-creator

2026-10-19
  • Claude Skills
  • Agent 工程
  • 上下文工程
  • MCP
  • 源码分析

前段时间 Claude Skills 在 HN 上拿下 816 分、428 条评论，评论区的第一反应几乎都是同一个问题:这不就是把 markdown 塞进上下文吗，和 MCP 有什么区别。争论了一整天之后，真正有信息量的答案不在讨论里，在 anthropics/skills 这个仓库里。

我把仓库拉下来数了一遍，几个数字比任何类比都更能说明问题:

  • 仓库 541 个文件，22 个官方 skill，18 万 star
  • pdf skill 的 SKILL.md 正文 310 行，加上 forms.md、reference.md 和 8 个 Python 脚本，实际载体接近 55KB
  • 每次会话真正常驻上下文的，只有 frontmatter 里那 437 个字符的 description

Skill 的设计不是"把文档塞给模型"，而是"设计一个索引结构，让模型自己决定什么时候去翻哪一页"。本文拆三件事:触发机制的真实成本、脚本作为确定性工具的价值，以及被大多数人忽略的 skill-creator，一个能给自己跑 A/B 评测的 skill。

一、431 字节：常驻成本的账要算清楚

pdf/SKILL.md 的 frontmatter 一共 515 字节，扣掉 name、license 这些固定字段，真正进入系统提示词的 description 是 437 个字符。它必须在一句话里同时说清两件事:这个 skill 干什么，以及什么情况下该用它。

name: pdf
description: Use this skill whenever the user wants to do anything with PDF files.
  This includes reading or extracting text/tables from PDFs, combining or merging
  multiple PDFs into one, splitting PDFs apart, rotating pages, adding watermarks,
  creating new PDFs, filling PDF forms, encrypting/decrypting PDFs, extracting
  images, and OCR on scanned PDFs to make them searchable. If the user mentions
  a .pdf file or asks to produce one, use this skill.

注意它把"读取、合并、拆分、旋转、加水印、填表单、加解密、抽图、OCR"这九个动作全部列了出来。这不是啰嗦，是在为意图匹配补充召回。MCP 工具的描述通常只写"管理 PDF 文件"，剩下靠参数 schema 表达;skill 的 description 没有 schema 可以依赖，只能把触发词直接铺在文本里。

这就是成本结构的根本差异。HN 上有人做了实测对照，几个热门 MCP 的 catalog 在没做任何事情之前就要吃掉:

MCP 工具数 常驻 token
Linear 23 ~12,935
JetBrains 20 ~12,252
Playwright 21 ~9,804

Linear 的 23 个工具、12935 个 token 是每次请求都在付的固定成本，不管这次会话要不要动 Linear。而 22 个 skill 的 description 全加起来，量级也就是一两千 token，因为每个 skill 只占 431 字节这个数量级。

三级渐进披露的代价和收益：

层级 内容 何时进上下文 pdf skill 实测
L1 name + description 每次会话常驻 431 字节
L2 SKILL.md 正文 触发时读入 7551 字节 / 310 行
L3 reference.md、forms.md、scripts/ 模型按需再读 16692 + 11854 + 23391 字节

关键在于 L3 的 8 个 Python 脚本。模型可以执行它们，但不需要把脚本读进上下文，这是它和"把代码贴进 prompt"的本质区别，也是下面第四节的重点。

二、MCP 描述的是能力，Skill 描述的是流程

评论区里最有价值的一句来自 simonw:MCP 最擅长的是"不需要完整沙箱环境也能用"，而 skill 恰恰相反，它假设模型有文件系统和命令执行能力。这条边界决定了二者根本不是替代关系。

真正的区别在描述对象上。MCP 描述的是能力边界:有哪些工具、每个工具收什么参数、返回什么结构。Skill 描述的是流程决策:先做什么、什么情况下换一条路径、哪一步容易出错。

webapp-testing/SKILL.md 是这份仓库里最像"工程经验"的一份，它直接给了一棵决策树:

User task → Is it static HTML?
    ├─ Yes → Read HTML file directly to identify selectors
    │         ├─ Success → Write Playwright script using selectors
    │         └─ Fails/Incomplete → Treat as dynamic (below)
    └─ No (dynamic webapp) → Is the server already running?
        ├─ No → Run: python scripts/with_server.py --help
        └─ Yes → Reconnaissance-then-action:
            1. Navigate and wait for networkidle
            2. Take screenshot or inspect DOM
            3. Identify selectors from rendered state
            4. Execute actions with discovered selectors

这个流程里有两条是模型自己几乎不可能"想"出来的：静态 HTML 应该直接读文件而不是起浏览器；动态页面必须先 networkidle 再截图取选择器，否则拿到的是渲染到一半的 DOM。这些是踩过坑才有的顺序知识，写成 20 个工具的参数描述根本表达不了。

同一份文件里还有一句很硬的指令:

Always run scripts with --help first... DO NOT read the source until you try running the script first. These scripts can be very large and thus pollute your context window.

这句话把"用 CLI 代替工具定义"的思路写死了。模型不知道 with_server.py 怎么实现，也不需要知道，--help 的输出就是它的接口文档。缺少参数时它自己会再问一次 --help，这个来回的成本远低于把整个脚本读进 24 万 token 的上下文。

对比之下，MCP 的形态是"把 API 表面预先翻译成 schema 塞进上下文"，skill 的形态是"把 API 表面留在磁盘上，让模型用 --help 自己去发现"。前者确定性高但固定成本大，后者固定成本极低但依赖模型会查文档。

三、技能自举：skill-creator 会给自己的 skill 跑 A/B 评测

22 个 skill 里最有意思的是 skill-creator。它不处理 PDF 也不画图，它负责造别的 skill，并且带一整套评测基础设施。

先看它的目录结构，这已经不像一个"提示词文件"了:

skill-creator/
├── SKILL.md                      33,168 字节
├── agents/grader.md              9,049
├── agents/comparator.md          7,287
├── agents/analyzer.md           10,376
├── scripts/improve_description.py 11,116
├── scripts/aggregate_benchmark.py 14,386
├── scripts/run_eval.py           11,464
├── references/schemas.md         12,061
└── eval-viewer/generate_review.py 16,365

它的工作流是标准的实验设计，只是执行者是子代理:

  1. 根据意图写出 skill 草稿和 2-3 条真实用户会说的话作为 test prompt
  2. 对每条 prompt 同时起两个子代理，一个带 skill 一个不带，一起跑完
  3. 跑的过程中并行起草可程序化校验的 assertion
  4. 每个子代理结束时从通知里抓 total_tokens 和 duration_ms，立刻写进 timing.json
  5. grader 子代理逐条判定 assertion，aggregate_benchmark.py 输出 mean ± stddev 与 pass_rate delta
  6. 起一个本地 viewer，让用户逐条看输出、填反馈，feedback 存成 JSON 喂下一轮

它把"这条 skill 到底有没有用"变成了一个可以重复测量的数。HN 上有人质疑 Anthropic 的发布博客里没有任何评测数据，skill-creator 就是对这个问题的方法论回答，代价是这件事得你自己跑。

其中 improve_description.py 解决的是一个很实际的失效模式:skill 不被触发。HN 用户 rane 的实测是典型的:

我写了一个描述极其明确的 skill：Use when creating or editing bash scripts，但让 Claude 写 bash 脚本时它根本不触发。我又改成 description: CRITICAL: Use when writing bash scripts，仍然没有任何效果。

这不是描述写得不够醒目，而是"该不该触发"这件事本身没有 ground truth。improve_description.py 的做法是把它变成一个分类任务:构造 should_trigger / shouldn't_trigger 两组查询，每条跑多次统计触发率，把 false positive 和 false negative 分别列给模型，要求它泛化到意图类别而不是堆关键词，每轮的 description 和训练结果记进 history，显式要求"不要重复之前的尝试，换个句子结构"。最后取分数最高的那一版。

description 超过 1024 字符会被截断，所以脚本里还有一道兜底:生成结果若超限，会再发一次单轮请求，把超长版本塞回去要求压缩。

这套东西的定位很清楚:它衡量的是触发准确率，不是回答质量。真正衡量后者的是 grader + benchmark 那条链，需要人工写 assertion、人工看 viewer 里的输出。

四、执行脚本：把确定性外包给代码

slack-gif-creator 只有 4 个核心文件，但把"什么时候该写代码、什么时候该交给模型自由发挥"分得很清楚。

core/validators.py 里有 validate_gif()，返回 (passes, results)，results 里带 size_kb、frame_count、duration_seconds、fps，并且分别校验 emoji（要求 128x128，64 到 128 之间算 acceptable）和 message GIF（宽高比不超过 2.0，短边 320 到 640）。

core/gif_builder.py 的 save() 才是真正解决问题的地方:

if optimize_for_emoji:
    if self.width > 128 or self.height > 128:
        self.width = self.height = 128
        self.frames = [np.array(Image.fromarray(f).resize((128, 128), Image.Resampling.LANCZOS))
                       for f in self.frames]
    num_colors = min(num_colors, 48)      # emoji 更强的调色板限制
    if len(self.frames) > 12:             # 帧数压到 12 附近
        keep_every = max(1, len(self.frames) // 12)
        self.frames = self.frames[::keep_every]

再加 deduplicate_frames(threshold=0.9995):用逐像素平均差算相似度，把几乎一样的连续帧删掉，阈值刻意定在 0.9995 而不是 0.98，注释写得很直白，保留细微动画。

同一份 pdf skill 里还有一段更典型的硬约束，正文用了全大写的 IMPORTANT:

Never use Unicode subscript/superscript characters (₀₁₂₃₄₅₆₇₈₉, ⁰¹²³⁴⁵⁶⁷⁸⁹) in ReportLab PDFs. The built-in fonts do not include these glyphs, causing them to render as solid black boxes.

这种句子通常是踩了坑才写下来的，所以我在本机用 reportlab 5.0.1 + pypdf 6.21.1 复现了一遍，两种写法各生成一份 PDF:

# A：直接写 Unicode 下标
c = canvas.Canvas("/tmp/a.pdf", pagesize=letter)
c.setFont("Helvetica", 20)
c.drawString(72, 700, "H\u2082O  CO\u2082")
c.save()

# B：用 ReportLab 的 <sub> 标签
doc.build([Paragraph("H<sub>2</sub>O  CO<sub>2</sub>", styles["Normal"])])

A 抽出来的文本是 H■O CO■，字体资源里除了 /Helvetica 还多出一个 /ZapfDingbats:找不到字形时 reportlab 退到 Dingbats 里碰运气，屏幕上就是两个黑块。B 抽出来是 H2O CO2，2 是被真正排版成下标的独立文本对象，字体资源只有 /Helvetica 一个，渲染出来是缩小下沉的数字。

这个例子能解释 skill 里为什么值得放脚本和硬约束:模型的默认写法是 H₂O，这个写法在 HTML 里完全正确，在 ReportLab 里就错。一句 Never 加一段对照代码，比让模型自己在几百页 ReportLab 文档里翻字体覆盖表便宜太多。

为什么这些必须写成代码而不是写在 SKILL.md 里让模型自己做？三个原因:

  • GIF 的大小不是"感觉一下"能判断的。少 10 个颜色、多减 3 帧，文件从 2.1MB 掉到 1.8MB，这种反馈必须可测量
  • 调色板要全局共享。optimize_colors(use_global_palette=True) 会先均匀采样 5 帧拼成一张图做量化，得到单一调色板再套用到所有帧;逐帧各自量化会让颜色在帧间抖动，文件也更大
  • 确定性的步骤不该花 token。用 token 生成的方式"排序一个列表"极其昂贵，同理，用模型去估算 GIF 尺寸既慢又不准

这也是 skill 与"塞一段长 prompt"最实际的差别:prompt 能描述步骤，不能提供可执行的校验器。有 validator 之后，模型的失败模式从"交出一个超限的 GIF 然后说完成了"变成"看到 passes=False 再调一次参数"。

五、两个真实的设计约束

拆完源码，有两件事值得写下来。

先说第一件，触发是靠文本匹配，不是靠语义理解。429 条评论里对这一点最集中的抱怨是"我说的明明就是这件事，它没用"。description 的字面覆盖度基本决定了召回率，所以官方 skill-creator 里明确建议把 description 写得"pushy"一点，把用户可能说的各种同义表达铺进去。这也解释了为什么 pdf 的 description 要穷举九个动作。反过来说，skill 数量一多，description 之间会开始竞争，improve_description.py 里"要 distinctive"那一条就是为这个准备的。

第二件事，skill 会拿到代码执行权限。Anthropic 自己的工程博客在这一段没有绕弯:

malicious skills may introduce vulnerabilities in the environment where they're used or direct Claude to exfiltrate data and take unintended actions. We recommend installing skills only from trusted sources.

这条风险在 2026 年上半年已经有过实例:某 skill 市场被注入上千个恶意 skill，套路是安装成功后弹一个伪造的"诊断命令"，实际是 base64 载荷，解码后下载窃密程序。skill 的形态决定了它的分发成本极低:一个 markdown 加几个脚本就能装，而安装动作本身就等于把命令执行权交出去。

我的做法

如果要在自己的仓库里用 skill，我目前只做三件事:

一是把流程写在 skill 里，把校验写成脚本。 凡是"怎么判断做对了"能用代码表达的，就不写进 markdown。validate_gif() 那种返回 (bool, dict) 的函数，比十句"请注意文件大小不要超过限制"有用得多。

二是 description 当接口来写，并且测触发率。 写了 skill 但很少被触发，通常是 description 的问题而不是模型的问题。构造十几条"该触发"和"不该触发"的查询，跑三遍看触发率，比反复调措辞靠谱。

三是第三方 skill 先读脚本再装。 这条没有捷径，SKILL.md 可以写得很无害，真正干活的在 scripts/ 里。

Skill 这个概念本身很朴素，SKILL.md 就是一个带 YAML 头的 markdown。真正让它成立的是配套的那套东西:一个足够的索引层、一组可执行的确定性脚本、一个能自己跑评测的循环。缺了后两样，它就只是一段比较长的提示词。
