MikroTrick：MikroTik RouterOS SSH 认证绕过攻击链全拆解（CVE-2026-67276/86060/67277）

2026-09-11
  • 安全
  • 漏洞分析
  • 网络设备
  • RouterOS

9 月 5 日，CERT Polska 发了一份措辞少见的预警：他们发现并协调披露了 MikroTik RouterOS 里的 6 个漏洞，其中两条组合成一条被命名为「MikroTrick」的攻击链，能让攻击者在零认证的前提下，通过 SSH 完全控制一台暴露在公网的设备。更罕见的是，MikroTik 在修复版本里第一次向装了官方 App 的用户推送了通知，这是它历史上头一回。

这不是一份普通的 CVE 公告，而是一条「认证绕过 + 提权」的完整在野利用链，而且它的发现方式本身也值得单独写一段。

CVE-2026-67276：RSA 公钥只比对了模数（CVSS 9.2）

SSH 公钥认证的整套安全假设，建立在一条规则上：服务器把客户端出示的公钥，和自己授权列表里的公钥做逐字节比对，确认「这把就是那把」，然后才让客户端证明自己持有对应私钥。

把这一步放回协议里看更清楚。SSH 公钥认证（RFC 4252）的握手大致是：客户端发 SSH_MSG_USERAUTH_REQUEST，method 填 publickey，附带公钥 blob；服务器拿这个 blob 去授权列表里查，查到才回 SSH_MSG_USERAUTH_PK_OK，并给客户端一个带会话随机数的签名挑战；客户端用自己的私钥签名；服务器用列表里那把公钥验签。

漏洞就出在第二步的「查」。RSA 公钥是一个 (n, e) 二元组，私钥是 (n, d)，正确实现必须连 n 带 e 一起比对。RouterOS 只比对了模数 n，没覆盖完整的 key blob。模数 n 只是公钥的一半，只比 n、不看 e，等于把「这把钥匙是不是授权的那把」降级成「钥匙柄像不像」。于是「授权列表里那把钥匙」和「签名验证用的那把钥匙」之间的绑定被切断了，这是典型的 key confusion。攻击者只要知道目标用户名，以及该用户公钥的模数 n，就能构造一把模数相同、其余部分不同的钥匙，通过 SSH 登录，全程不需要受害者的私钥。

「知道模数」听起来苛刻，其实不然：公钥本来就是公开信息，而下面要讲的 CVE-2026-67277 能直接从内核缓冲区读出未初始化数据，两条漏洞之间形成了天然的配合。这是认证绕过里最危险的一类，它不猜密码、不爆破，直接瓦解了认证协议本身的前提。

CVE-2026-86060：一个非法开头的用户名，换来管理员权限（CVSS 9.2）

第二条更隐蔽。RouterOS 的 SSH 登录机制，对「以不允许字符开头的用户名」处理不当。攻击者用一个精心构造的用户名登录，就能把会话权限抬升到完整管理员级别。

这类缺陷的本质是解析差异（parser differential）：某个字符在 RouterOS 内部有特殊含义，比如标记特权账户的前缀，当它出现在用户名开头时，登录路径里的权限校验就被跳过或绕过了。用户名在这里不是一个普通字符串，而是一个注入点。跟 SQL 注入、路径穿越是同一个家族：把「数据」混进了「控制」的语义里。

CVE-2026-67277：带宽测试服务的状态机越界（CVSS 8.8）

带宽测试（bandwidth-test）服务允许未认证连接进入一个「本该登录后才能到达」的状态。再叠加两个独立缺陷：数据包缓冲区的未初始化数据泄露，以及大小校验里的整数下溢，就能实现内核内存泄露，或远程 DoS 导致设备重启。

整数下溢是这里最经典的一环。服务端对攻击者可控的长度字段做校验，但校验发生在错误的类型宽度上，或者用了有符号比较，攻击者传入一个能绕回负数的值，于是分配了一个很小的缓冲区，拷贝却按一个巨大的长度进行，读越界，把内核里没初始化过的内存字节原样回传给攻击者。泄露出来的字节里，就可能有别处的密钥材料、指针，甚至前面说的公钥模数。

这里的关键词是「状态机」。一个协议实现里，客户端和服务端各自维护状态机，攻击者跳过了某个本应强制完成的阶段（认证），直接进入了后续状态。这正是后面要讲的发现方法论的核心。

MikroTrick：两条漏洞怎么串成一条链

MikroTrick 的杀伤力来自组合。67276 解决「能不能进门」，86060 解决「进门之后是什么权限」。单独看，67276 拿到的是目标账户的权限，可能只是普通用户；叠加 86060 的用户名提权，就变成完整管理员。于是「零认证 → 完全控制」这条链闭合了。官方公告里这 6 个漏洞还波及 SSH 服务器和客户端、X.509 证书处理、以及 WebFig 接口。修复版本是 7.25beta3、7.24.2、7.23.4、6.49.21。

在野利用：ops 用户和两个 IP

CERT Polska 确认攻击已经发生。被攻陷设备的日志里会留下这些痕迹：

login failure for user - 2 from <ip> via ssh
user <name> added by ssh: - 2 @<ip>

额外的一个 IOC 是：出现一个高权限用户，名字就叫「ops」。攻击至少从 9 月 2 日开始，源头是 82.192.72.4，另有 103.102.31.18 参与过尝试。出现任何一个痕迹，都要立刻排查。

「Flagged」机制：厂商的亡羊补牢

修复版本引入了一个「Flagged」机制：RouterOS 启动时扫描配置，寻找已知的未授权修改痕迹，禁用可疑配置项，写入 critical 日志，并打上标记。但 CERT 明确警告：这个标记只检测「选定的」痕迹，没有标记不等于设备安全。它应该被当作「可能已被攻陷」的提示，而不是「没被攻陷」的证明。

最值得写的一段：漏洞是 LLM 帮着挖出来的

这 6 个漏洞由 CERT Polska 的 Sławomir Rozbicki 发现，工具是 GPT-5.5-cyber 和 GPT-5.6-sol 模型，来自团队通过 OpenAI GTAC 计划获得的访问权限。模型跑在一个 agent 化的研究环境里：隔离实验室、自动化创建与恢复设备、下载并比对版本、分析 RFC 和二进制、生成验证 PoC 的脚本。

最有价值的方法论，一句话就能概括：把协议建模成状态机，然后检查「跳过某个阶段、重复某个阶段、打乱顺序执行」会发生什么。这套方法被证明特别有效，而 CVE-2026-67277 恰好就是「跳过认证阶段进入后续状态」的 bug，方法论和结果形成了闭环。

具体怎么做：先用 LLM 把 RFC 或反汇编结果整理成一张状态机图，标注每个状态和每条迁移的触发条件；然后系统性地试探三类非法迁移——跳过（skip，直接跳进后续状态）、重复（repeat，把同一个请求发两次）、乱序（reorder，调换两个阶段的先后）；每次试探都在干净状态的设备上做，看是否进入了本不该到达的状态。这套流程几乎可以直接照搬。

CERT 特别强调这不是一句 prompt 的事。每一个假设都要在真实 RouterOS 上确认、做阴性对照测试、在干净状态的机器上重复、再评估真实影响。模型大幅加速了分析和假设探索，但没有替代这些环节。这句话对任何想用 LLM 做安全研究的人都值得抄下来。

我的做法：先查这三样，再谈修复

别急着只点升级。按顺序来：

  1. 升级到 7.25beta3 / 7.24.2 / 7.23.4 / 6.49.21 之一。
  2. 查 Flagged 标记：
/system/device-mode/print
  1. 查未知用户、脚本、定时任务、代理和隧道：
/user print
/system script print
/system scheduler print
  1. 如果日志里出现「ops」用户，或上面那两条日志特征，按「已被攻陷」处理：隔离设备，先保全日志和配置，再恢复出厂，重新基于可信配置部署，更换所有口令和密钥。不要盲目恢复一份来自可能被攻陷设备的完整配置备份。

一句话收尾：路由器这种常年开着、很少登录的设备，最适合藏一个高权限后门。有空就上去看一眼 /user print，比任何应急响应都便宜。
