一个广告拦截器里的通用 XSS：uBlock Origin 元素拾取器被网页反向控制

2026-11-16
  • 浏览器安全
  • uBlock Origin
  • XSS
  • 扩展安全
  • 攻击链分析

浏览器扩展是唯一一类同时拥有你的登录态和任意站点权限的本地代码。它的攻击面一旦被翻过来，攻击者拿到的不是某个站的 XSS，而是所有站的 XSS。11 月初 uBlock Origin 修掉的那个漏洞就是这条逻辑的教科书样本：受害者只需要在恶意页面上点一下，攻击者就能给任意域名植入一条受信任的注入规则，然后在这个域名下执行任意 JS。

漏洞在 11 月 1 日通过邮件报告给作者 Raymond Hill，11 月 15 日 GitHub Security Advisory GHSA-cmqw-9r2w-6wv2 公开，评级 high，没有分配 CVE 编号。修复跨越 1.75.2、1.75.4、1.76.0、1.76.4 四个版本，前后四次提交。四次提交说明一件事：这不是一个补丁能关掉的问题，而是一串被拆开的信任假设；每关掉一处，攻击者就换一个入口进来。

攻击链：四步把"用户点一下"变成"任意站点执行 JS"

漏洞的原始报告写得很干净，攻击链只有四步。

第一步，拿到扩展的内部 URL。Firefox 上 moz-extension:// 后面的 UUID 每次安装随机生成，本来属于不好猜的东西。但 uBO 的默认规则集里有一条 uAssets 规则：

lootdest.*##+js(no-fetch-if, adsbygoogle, war:googlesyndication_adsbygoogle.js)

这条规则的意图是：当页面 fetch 广告脚本 adsbygoogle.js 时，不发真实请求，改为从扩展的 web_accessible_resources 目录里取一份不做事的替身脚本，保证页面的 API 形状不变但不真加载广告。问题在于它内部是用 XHR 去读那个 moz-extension:// 地址的。而页面自己可以钩住 XMLHttpRequest.prototype.open：

const origOpen = XMLHttpRequest.prototype.open;
XMLHttpRequest.prototype.open = function(m, url, ...a) {
    const e = /^moz-extension:\/\/[^/]+/.exec(url);
    if (e) {
        // e[0] 就是 moz-extension://<UUID>
    }
    return origOpen.call(this, m, url, ...a);
};

然后页面执行 fetch('/adsbygoogle.js') 触发这条规则，钩子随即拿到 UUID。防御边界是"UUID 不可预测"，但扩展自己把 UUID 当参数传给了页面可观察的 API，可预测性就消失了。

第二步，iframe 拾取器。拿到 UUID 后，页面直接建一个 <iframe>，src 指向 moz-extension://<UUID>/web_accessible_resources/epicker-ui.html。这是在 web_accessible_resources 里声明的资源，任何网页本来就有权内嵌。至此页面里跑着一个扩展源的文档，而且这个文档带着扩展的全部特权。

顺带说清楚为什么这一步能成：web_accessible_resources 的设计意图是"允许页面引用扩展的静态资源"，比如图标、样式、用来做替换的 shim 脚本。但 uBO 把整套元素拾取器 UI 也放进了这个目录，而拾取器不只是一个界面，它是能向后台发 createUserFilter 消息的控制端。资源可见性和控制能力被绑在了同一个 URL 上。

第三步，跟它说话。拾取器 UI 在一个 MessageChannel 上等 epickerStart 消息，页面直接发：

iframe.contentWindow.postMessage({ what: 'epickerStart' }, '*', [ch.port2]);

拾取器回一句 start，页面发 showDialog 带上要"展示"的过滤规则，再回 resultsetDetails 把"创建"按钮点亮。整段对话里双方都没有验证过对方的身份：postMessage 的 '*' 目标源，加上监听器里没有任何 origin 判断，等于页面对拾取器说"我是你的内容脚本"，拾取器就信了。

这里还有一个更细的问题值得记下来。拾取器的消息监听是这样注册的：

globalThis.addEventListener('message', ev => { ... }, { once: true });

once: true 的效果是第一条 epickerStart 决定一切。真实的用户操作要经过右键菜单、内容脚本启动、iframe 加载，中间有几十到几百毫秒；而恶意页面在 iframe 一加载就往里发消息。谁先到，谁就锁定了这个 MessagePort。这是典型的竞态型授权缺陷，不是"忘了校验"那么简单。

第四步，投毒。这里是最漂亮的细节。resultsetDetails 里有个 opt 字段，本意是"这条规则匹配哪类网络请求"（image、script 之类），会被拼到规则末尾变成 $image。页面控制的字符串直接带换行：

const opt = 'image\n' + String.raw`google.com##+js(trusted-rpnt, script, /^[\s\S]*$/, alert('injected on '+document.domain))`;

换行把单条规则劈成了两条。第一条 ||example.com^$image 是给用户看的，第二条是一份完整的、针对 google.com 的脚本注入规则，用的是 uBO 的 trusted- 前缀脚本片段。因为元素拾取器创建的过滤器默认就被标记为可信（trusted），这条注入规则不需要用户信任模式即可生效。页面再把这个 iframe 的 opacity 设成 0 盖到任意位置，用户随手一点"创建"，规则就写进了"My filters"。

之后攻击者打开 google.com，alert 里的内容在 google.com 的源里执行。换掉 alert 就是完整的信息窃取。

修复：四次提交，四个假设

把四次提交按时间排开，能清楚看到作者是怎么把这条链一段段掐断的，也能看到每一段背后的设计假设错在哪。

1.75.2（11 月 2 日，bf69cf7）：别再调用页面能改的方法。 这条提交只有 4 行新增、2 行删除，改的是 src/js/resources/safe-self.js 和 src/js/resources/utils.js。思路是把 XHR 的 open/send 从原型上"摘"下来，在 safeSelf() 里存一份干净引用：

'XMLHttpRequest': self.XMLHttpRequest,
'XMLHttpRequest_open': Function.prototype.call.bind(self.XMLHttpRequest.prototype.open),
'XMLHttpRequest_send': Function.prototype.call.bind(self.XMLHttpRequest.prototype.send),

然后 war: 分支里的 warXHR.open(...) / warXHR.send() 改成 safe.XMLHttpRequest_open(warXHR, ...)。这是在扩展自己的 safeSelf 抽象里加两个白名单条目。uBO 早就有一套"页面可能污染过的 API"清单，只是 XHR 的方法漏了。

补丁当天就被绕了。报告者在同一天回信：

Object.defineProperty(
   XMLHttpRequest.prototype, 'responseText', {
     get() {
       mount(/^moz-extension:\/\/[^/]+/.exec(this.responseURL)[0]);
     }});

open 和 send 收回来了，responseText 的 getter 还在原型上，而 getter 能读到 this.responseURL，里面就是 moz-extension://<UUID>。只要扩展还在用页面的 XHR 对象去碰自己的 URL，UUID 就守不住。 这个认识直接决定了第四次提交。

1.75.4（11 月 3 日，9859477）：加一道口令。 这次是结构性修复，19 行新增。后台脚本（src/js/messaging.js）在启动时生成一个随机口令：

const epickerPassword = self.crypto.randomUUID();

内容脚本（src/js/scriptlets/epicker.js）通过 vAPI.messaging.send 把它取回来，塞进启动消息：

iframe.contentWindow.postMessage(
    { what: 'epickerStart', password: pickerPassword },
    url.href,
    [ channel.port2 ]
);

拾取器 UI 侧（src/js/epicker-ui.js）改成异步函数，消息进来先比对：

async function bootPicker(ev) {
    const msg = ev.data || {};
    if ( msg.what !== 'epickerStart' ) { return; }
    const epickerPassword = await vAPI.messaging.send('elementPicker', {
        what: 'elementPickerPassword'
    });
    if ( msg.password !== epickerPassword ) { return; }
    ...
}

口令存在 vAPI.messaging 的 background 侧，页面拿不到。因为它没有 runtime.sendMessage 权限，web_accessible_resources 里的文档不继承扩展的 API。攻击面从"任何人都能对话"缩小到"知道口令的对话方"。

1.76.0（11 月 8 日，b1f7d27 与 150df12）：校验内容、停掉通道。

b1f7d27 加了 24 行、删了 17 行，只动一个文件，把过滤器校验抽成 parseRawFilter 并在两处补上。这是关键，因为原来的校验只在"从文本框读到规则"时做，不在"把候选规则拼成最终规则"时做：

function parseRawFilter(raw) {
    const parser = staticFilteringParser;
    parser.parse(raw);
    if ( parser.isFilter() === false ) { return; }
    if ( parser.hasError() ) { return; }
    if ( parser.isExtendedFilter() ) {
        if ( parser.isCosmeticFilter() === false ) { return; }
    } else if ( parser.isNetworkFilter() === false ) { return; }
    return raw;
}

userFilterFromCandidate 里在拼完 $opts 之后补了一次：

if ( parseRawFilter(filter) === undefined ) { return; }

换行偷渡的第二条规则这时候过不了 parser.hasError()。同一版本里的 150df12 更狠，直接把 war: 整个分支砍掉：

if ( directive.startsWith('war:') ) {
    // TODO: resources should be fetched by messaging ISOLATED world
    return '';
}

war: 是"从扩展包里取一份替身资源"的机制（WAR = web accessible resource），本身就有问题，它要求内容脚本去读扩展的 WAR 目录。作者的 TODO 注释说明了正确的方向：这类取资源的事应该回到隔离世界，通过 messaging 走，而不是让注入到页面的脚本去发请求。

这个机制的设计意图不难理解。广告脚本被替换成空壳，能同时满足两个目标：页面不报错（adsbygoogle 这个全局对象还在、方法签名还在），广告又没真的加载。实现在 generateContentFn 里，页面侧的 shim 需要拿到那份空壳脚本的内容，于是它从扩展目录里 XHR 一份出来。便利性和隔离性在这里是直接冲突的：页面侧的代码要读到扩展目录的内容，就必须有一次跨边界的读取，而这次读取一旦发生，路径就暴露了。

作者的最终选择是"砍掉便利性"：return ''，等以后用 messaging 从隔离世界重新实现。这条提交删了 19 行、加了 4 行，是整个修复里唯一一处功能回退。删代码比加校验更诚实，它承认了这个抽象的边界画错了。

1.76.4（11 月 15 日，5466554）：关掉剩下的口子。 这条提交的说明只有一行 "Address remaining reported security issues"，实际改了三处，其中两处值得单独说。

一是清掉 war: 留下的 warOrigin/warSecret（73ef1b23 先删注入点，5466554 收尾）。scriptletGlobals 会以 JSON.stringify 形式塞进注入到页面的代码，也就是说扩展的内部 URL 和 WAR 密钥曾经直接写在页面可见的 JS 里。这解释了为什么单纯收回 XHR 方法没用：只要这些值还在注入代码里，页面读一遍就拿到了。

这一条比表面看起来严重。这说明 1.75.2 那个补丁在逻辑上不完整：你把 open 和 send 的引用藏进 safeSelf，可同时序列化输出到页面的 scriptletGlobals 里就躺着 WAR 密钥。攻击者不需要钩任何东西，打开 DevTools 看一眼内联脚本就行。这里暴露的是个常见设计误区：把"给注入代码用的上下文变量"和"给扩展自己用的密钥"混在同一个结构里。 前者注定要跨边界，后者永远不该跨。

二是顺手修了资源更新器（src/js/diff-updater.js）的去重键和校验逻辑：

function getCanonicalPatchURL(assetDetails) {
    const { patchPath, cdnURLs, patchURLs } = assetDetails;
    if ( Array.isArray(cdnURLs) === false ) { return; }
    if ( cdnURLs.length === 0 ) { return; }
    const canonicalPatchURL = resolveURL(patchPath, patchURLs?.[0] || cdnURLs[0]);
    if ( Boolean(canonicalPatchURL) === false ) { return; }
    return canonicalPatchURL.href.replace(/#.*$/, '');
}

以及加了 checksum 长度下限：

if ( typeof checksum !== 'string' || checksum.length < 10 ) {
    assetDetails.error = 'badchecksum';
    return false;
}

原来的去重键是 URL 的 basename，不同 CDN 上的同名文件会互相覆盖缓存（736ef4d10 修的就是这个）；checksum 不校验长度，空串或极短值都能通过。这两条不是 XSS 主线，但同一个提交里一起关掉了。

MV3 侧：同样的缺陷，不同的补丁

uBO Lite（MV3 版本）也受影响，只是严重程度不同，MV3 没有 MV2 那样宽的自定义过滤能力，trusted- 脚本片段的可达面更小。它的修复是独立的一条（ead588aa5c，11 月 3 日），落在 platform/mv3/extension/js/：

后台侧加了一个 getToolOverlaySecret 消息，首次调用时惰性生成 crypto.randomUUID()；tool-overlay.js 里 install() 改成先 await 拿口令，再把 secret 塞进 startOverlay 消息，且 postMessage 的目标源从 '*' 换成了 realURL.origin（由 @@extension_id 拼出来）。注意这里把 new Promise(resolve => ...) 改成了 Promise.withResolvers()——一个次要但影响可读性的重构。

两边对照着看，作者的修复模式是统一的：凡是"页面能构造出扩展内部文档的引用"的地方，都要加一道页面拿不到的随机口令；凡是 postMessage，目标源不能是 '*'。 这不是 uBO 独有的问题，是所有需要往页面注入 UI 的扩展共同的毛病。1Password、Postman、各种密码管理器的自动填充浮层，用的都是同一套 iframe + MessageChannel 套路。

从防御侧看：四个可以立刻自查的点

第一，检查你所有带 web_accessible_resources 的扩展。 这个清单里每一项都是页面可以直接内嵌的入口。Chromium 现在支持 matches 字段限缩来源，别用 "<all_urls>"。如果一个 UI 文档被列进 WAR 只是为了让内容脚本能 iframe 它，那它就不该在 WAR 里——内容脚本有 vAPI.getURL()，不需要 WAR 权限。

第二，所有 postMessage 的目标源和 message 事件的来源都要显式判断。 本文这条链的每一个环节都违反了这条：'*' 做目标源、监听器里没有 ev.origin 检查、MessagePort 建好就信。改造模板：

// 发送侧
iframe.contentWindow.postMessage(payload, expectedOrigin, [port2]);

// 接收侧
self.addEventListener('message', ev => {
    if ( ev.origin !== expectedOrigin ) { return; }
    if ( ev.source !== expectedWindow ) { return; }
    if ( ev.data?.password !== secret ) { return; }
    // ...
});

三道判断成本为零，但能挡掉整类"页面冒充内容脚本"的攻击。

第三，别在注入到页面的代码里放任何内部标识。 scriptletGlobals 那个坑最值得记住：扩展把 warOrigin、warSecret 序列化进注入脚本，等于把钥匙贴在门上。内容是给自己人看的，但执行环境是攻击者的页面。真要传值，走 runtime.sendMessage 的单向通道，别塞进字符串。

第四，版本判断。 MV2 Firefox 版本 1.76.4 才集齐全部修复，Chromium 侧 uBO Lite 需要 2026.1110.1816 或更新。1.76.0 之前的版本能挡掉 iframe 劫持，但 1.75.4 又被 responseText 绕过，中间的窗口期是真实可用的。翻一下你浏览器里的版本号，低于 1.76.4 就直接更新。

被利用过的话，痕迹会落在"My filters"里。打开 uBO 的仪表盘 → 我的过滤器，找这几类异常：

  • 你没有印象创建过的规则，尤其是带 trusted- 前缀的。trusted- 脚本片段只有元素拾取器和手动输入能写，正常使用中极少出现。
  • 一个域名下的规则指向另一个完全不相关的域名（比如一条 example.com 相关的规则里出现了 google.com##+js(...)）。
  • 带换行残片的规则，或者以 $image、$script 结尾后面还跟着内容的畸形条目。uBO 正常写入时会格式化，不会留下这种结构。
  • 规则里出现 war: 字样的（1.76.0 后这种过滤器已被禁用，但它作为历史残留值得看一眼）。

自动化一点，直接读 uBO 的存储。Firefox 的扩展数据在 profile 目录下，规则本体在 IndexedDB 里，用 sqlite3 或浏览器控制台 vAPI.storage 都能取。想省事就在 uBO 仪表盘导出备份，JSON 里 userFilters 字段是明文的：

# 从导出的备份里筛可疑规则
python3 - <<'EOF'
import json
d = json.load(open('ublock-backup.json'))
for f in d.get('userFilters', []).split('\n'):
    if 'trusted-' in f or 'war:' in f:
        print(f)
EOF

命中就删掉，然后重新编译过滤器（改动后 uBO 会自动重建，可信标记也会一起清掉）。

一个开发者的视角

这个漏洞让我重新审了一遍自己对扩展的安全直觉。我一直把"扩展是可信的、页面是不可信的"当成默认前提，但这条链说明前提本身不成立：页面可以构造出一个扩展源的执行上下文，然后在里面操作扩展的特权。所谓信任边界，不是靠"文档从哪来"划的，是靠"消息是谁发的、带了什么凭证"划的。

作者的处理方式也值得学。他没有憋一个大的"安全重构"，而是四天四版、每次 20 行上下，每一版都对应一个被证伪的假设。更重要的是他把整段邮件往来原样放进了 advisory，包括那个绕过的 responseText getter 和报告者自己说"我不太能稳定复现，但可能存在"的 iframe 竞态。这种披露的质量，比一份只说"已修复，请升级"的公告有用得多。

顺带说一句：报告者在博客里写清楚了，漏洞是 GPT-5.6 Sol 找到的。他给了个方向假设（过滤规则注入应该有 UXSS），模型把具体路径翻了出来，他验证，Claude 写了 PoC 大部分代码。这件事本身没什么可惊奇的，值得注意的只是它和这个漏洞的性质很搭：都是"看起来没有桥的地方，其实有一座桥"。
