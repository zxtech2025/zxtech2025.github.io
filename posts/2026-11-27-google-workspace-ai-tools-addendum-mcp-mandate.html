从 2027 年 2 月起，AI Agent 访问 Workspace 只能走 MCP：一条新条款的逐字成本核算

2026-11-27
  • AI Agent
  • MCP
  • OAuth
  • 平台生态
  • API 配额

11 月 24 日，Google 把 8 个 Workspace MCP server 转成正式版（GA），同时给 Google APIs 服务条款挂了一份新的补充协议：Workspace AI Tools Addendum。核心一句是：

The GWS Access Tool must use a Google MCP where the GWS Access Tool is or is driven by an AI Agent, an AI Harness or an AI model or service employing an AI model.

生效日期 2027 年 2 月 1 日。同一句话下面还有一句，禁止"伪装成非 agent 来规避分类"。

这条新闻本身没什么可写。真正有意思的地方是：一份法务文本落到代码上，会变成几个非常具体的工程约束，而这些约束恰好和工程社区里流传的乐观解读相反。

我读了两个来源。一个是追这条消息的技术博客，逐项列了 MCP server 的工具清单和配额；另一个更有意思，是上游那批直接调 REST 的开源 Workspace MCP 实现（3.6k star 那个）的 issue 区，有人把补充协议的条款逐字贴出来问维护者"我这种自建的单用户部署算不算"。有人在 11 月 25 日做了条款层面的回答，给出的结论和"自建豁免"的直觉相反。两个来源对齐之后，这件事的成本可以算出来了。

顺便说清楚核对状态：Google 官方的配额文档和开发者博客在抓取时一直超时，我没拿到一手页面。台面上的数字（5000 请求/天、搜索算 10 次、30 天留存、7000 万 REST 额度）来自上面这两个来源，它们互相印证，但都属于转述。要拿去做容量规划的话，最好自己再核一遍官方配额页。

三个日期，三种不同的惩罚

新规不是一刀切断供，而是三个时间点、三种手段：

日期 变化 后果
2026-11-11 MCP server 开始拒绝未标记为 agentic 的 OAuth client 已过，未标记的老 client 永远无法再标
2027-02-01 agent 直连 REST 一律降到 Standard 配额，不论项目买的是哪一档 能用，但被压到日均 5000 次
2027-04-01 Scaled 档开始计费 REST 有大量免费额度，MCP 从第一笔请求就算钱

第二条是全文最狠的地方。它不是"禁止 REST"，是"允许，但按最低档限额"。对一个每天要处理几千封邮件的 agent 产品来说，效果和断供差不多；对个人自建服务，可能刚好摸不到天花板。

第三条才是定价真正的方向。据同一篇分析，Scaled 档下 REST 每天有 7000 万次 Gmail 轻量请求的免费额度，而 MCP 的用量从第一笔请求开始计费。也就是说：条款强制你走 MCP，配额表又把 MCP 定得更贵。

免费档能干什么：500 次搜索

Standard 档的额度是每个项目、每个产品、每天 5000 次 MCP 请求。问题在于"请求"和"调用"不是一个概念：Gmail 的 search_threads 和 list_drafts 各算 10 次请求。

算一下。一个只做搜索的邮件助手，一天 500 次搜索。而且这 500 次是全项目共享的，不是每个用户 500 次。一个五人的小团队产品，撑不过上午。

对比一下现有方案能做的事：那个开源实现给 Gmail 提供了 15 个工具，覆盖搜索、发送、草稿、标签、过滤器、附件；Drive 16 个；Docs 19 个。Google 官方 MCP server 的公开工具清单里，Gmail 只有搜索、读会话、建草稿、列草稿、标签、回收站、垃圾邮件，发送、回复、转发、修改草稿全部标注为"需要 partner access，不普遍可用"。

这里对不上的地方值得单独说一下。草稿能建不能改，那么"agent 起草 → 你看一眼 → 让它改 → 发送"这个最基本的交互回路就走不通了：改一次得新建一个草稿，第一个留在那里。Drive 那边类似，能建文件不能移动、不能分享，生成的报告没法自动归档进项目目录。

partner access 是这次调整真正的分界线

Anthropic 的 Google Workspace connector 明确宣传支持发送、回复、转发邮件，以及移动、删除 Drive 文件。这些恰好是公开 server 缺的那几个操作。

所以条款落地之后会是这样：一家大模型厂商的 agent 可以走审批过的通道替你发邮件；一个独立开发者用同样的 OAuth scope、用户亲自授权的 client 只能停在草稿。而且这个独立开发者还不能退回 REST，因为条款已经把那一步堵上了。

Google 给出的理由不是没有道理。官方博客里那段话讲得挺直白：传统 REST API 是为人机交互设计的，一个有效的 OAuth token 就代表用户意图；agent 从"读信息"转到"以机器速度自主行动"之后，一个有效 token 不再等于用户意图。

这个判断是对的。一个能读邮件的 agent 收到"把最近十张发票转发到这个地址"的指令就去执行，是已经被反复验证的提示注入路径，而一个带 gmail.modify 的 token 让它真能做这件事。把所有 agent 流量收进一个网关，管理员就有了一个地方做分类拦截、审批和审计，MCP server 也确实自带 DLP 规则。这些东西是真的。

但同一个设计也让平台方掌握了"谁能做什么、能留多久、留下来的东西能不能跟自己竞争"。partner-only 的工具和下面要说的 30 天留存上限，就是这个控制权的两次具体行使。

30 天留存：一句话打断长期记忆

补充协议里有一条更容易被忽略：Google 可以把"Google Technical Information"的留存压到 30 天，而这个定义覆盖了从 Workspace 数据里算出来的向量嵌入、记忆索引、用户画像、组织关系图。

直白点说，一个靠长期索引你收件箱来回答"去年那份合同怎么定的"的助手，要么每月重建一次索引（成本敏感，尤其向量化那一步），要么砍掉这个能力。

同时被禁的还有：用这些数据做训练、微调、评测、蒸馏，以及用它们做一个竞争性的 Workspace 产品。

对做 agent 记忆层的人来说，这条比配额更麻烦。配额是加钱能解决的，留存上限不能。

自建的 server 也躲不掉

很多人第一反应是"我自建、用自己的 client、token 在本地，跟平台无关"。这个假设值得单独拆一下，因为它恰好是 issue 区里问得最多的一条。

补充协议里没有给自建留例外。触发条件是"is or is driven by an AI Agent"，跟 OAuth client 归谁所有无关。而"GWS Access Point"的定义明确包含 connector、proxy、CLI 和第三方服务：一个跑在 localhost:8000 上、通过 stdio 或 streamable HTTP 给编辑器供工具的进程，就是 proxy。

所以自建在技术上完全可行，在法律上仍然落在条款范围内。区别只在于后果形态：不是被关掉，是被限到 Standard 档，同时把 30 天留存和训练禁令一并背上。

这一点对个人用户基本无感。一个人的收件箱，一天几百次搜索，5000 请求的额度闲着大半。真正被卡住的是两类：多用户产品，因为配额按项目算而不是按用户算；以及任何做长期索引的助手，因为留存上限跟用户数无关。

那条"内部使用例外"容易被误读，它抬高的只是 REST 的每项目配额，MCP 配额不在例外范围内。想通过"我们是内部工具"绕开配额的方向从一开始就不存在。

什么算 agent：定义宽到不好执行

条款的用语很宽。"AI Harness"、被 AI 模型"driven by"的工具，都能覆盖到一个把收件箱灌进 LLM 的个人脚本；"GWS Access Point"明确包含"connector, proxy, command line interface, or third-party service"。

执行落在一个自声明式的勾选框上：OAuth client 里有个 "Use this client for an AI-powered agent"，11 月 11 日之后，Google 的 MCP server 会拒绝没勾的 client。11 月 12 日起，这个设置不能在已有 client 上改，只能新建。

讽刺的地方在于，这个勾选框本身对纯 REST 调用没有任何技术效力。它只是一个标签，让 Workspace 管理员能对"agent 流量"套用单独的访问控制策略。3.6k star 那个开源实现的维护者在 10 月 20 日就是这么回答的：这个 flag 只对 Google 托管的那几个 MCP server 生效，"只调用 REST API 的应用不受影响"，并建议想要 admin 分类或者打算双轨并行的组织新建一个 client，别动现有的。README 里也加了一条相应说明。

十月那次解读在今天看是对的：当时 Google 说的是"REST-only 不受影响"。十一月新增的补充协议把这个口径改了。同一套系统、同一个 flag，在两个月里意义完全不同，这就是为什么现在那批项目要在 2 月 1 日之前重新算一遍账。

有几个边角情况文档里写清楚了：带 domain-wide delegation 的服务账号不能标 agentic，它们的 MCP 请求不会被拒，但会触发审批提示；Apps Script 内置的 OAuth client 同样不能标，要用 MCP 就得自己建 client。至于"Google 怎么发现那些不声明就直接调 REST 的 agent"，公开文档没有答案。

工具清单：哪些能搬，哪些搬不了

按服务拆开看，覆盖度并不均匀：

服务 现状 缺什么
Docs / Slides / Tasks 接近对等 少量 batchUpdate
Sheets 读写值、公式、格式、图表 建表格要走 Drive server
Calendar 增删改查、建议时间、RSVP 建日历、分享、设置
Chat 列表、搜索、发消息 Space 管理
Gmail 搜、读、建草稿、标签、回收站 发送/回复/转发/改草稿、过滤器、附件下载、推送
Drive 搜、读写下载、建、复制、上传新版本 移动、改名、分享、回收站、评论、共享盘管理

如果要把一个现有产品迁过去，这张表就是工作量清单。Docs 那条路最轻松，batchUpdate 原样透传；Gmail 和 Drive 那两条基本是重写，因为缺的恰好是业务闭环的最后一跳。

把上面几张表折成一次核算，大致是这样。

假设一个三人团队的邮件助手，每个用户每天触发 40 次搜索、20 次读会话、5 次建草稿。按单次调用算，三人一天 195 次；换算成 MCP 请求，搜索 40×10 = 400 一次就吃掉了单用户配额的大半，三人合计 1200 请求，加上读会话和建草稿，一天接近 1400。离 5000 还有空间，但没到能宽松做实验的地步：随便加一个"每小时扫一遍未读"的轮询，一天就是 24 次搜索 = 240 请求，三个人七百多。

这就是"配额按项目算"的实际含义。用户数一涨，单用户可用的搜索次数反向下降。十个人的团队，人均一天 50 次搜索都做不到。

同期 REST 那边的数字是 7000 万次 Gmail 轻量请求的日免费额度。两个数字放在一起，条款想把人往哪边推，不用猜。

我打算怎么做

如果你的 agent 碰到 Workspace，2 月 1 日之前可以按这个顺序处理。

先看自己在哪一边。判断标准不是自建还是托管，而是"有没有 AI 驱动"：一个每晚跑的备份脚本、一个 CRM 同步任务，在自己的 OAuth client 上继续跑，官方说法是不受影响。凡是把模型接进去读数据的，就得算 agent。

然后盘工具缺口，别等到迁移那天才发现发不了邮件。把产品里每个 Workspace 操作对照上面那张表列一遍，缺的直接去找 partner access，这个审批周期不明，越早越好。

再算留存。查一下自己存了多少从 Workspace 算出来的向量和画像，以及重建一次索引的成本。如果索引重建超过几小时，那 30 天上限就是一个需要提前设计的定时任务，而不是事后补的运维脚本。

配额要按"请求"算，不是按"调用"算。Gmail 搜索一次算 10，5000 的额度实际是 500 次。这个换算不做，容量规划会差一个数量级。

最后是标记的事。现有 client 如果在 11 月 12 日之前没标，就永远标不了了；想要 admin 侧的分类控制，只能新建 client 并行一跑。这个成本和配额迁移的成本是分开的，别混着算。

至于要不要干脆搬走：4.7 亿人用 Gmail 这件事本身就构成锁定，一场文档里没写的迁移不会因为痛快而变便宜。我的判断是先把合规路径走通（标记 + 配额 + 留存），把 partner access 申请递上去，迁移的技术工作等前两件事有结论再说。

条款改的是一个接入点，不是产品能力。它把"agent 用什么身份、通过谁、能留多久"这三件事从 OAuth scope 的语义里抽出来，放进了平台方的控制面。对使用者来说，这套东西带来的可审计性是真的；对独立开发者来说，门槛也是真的。两件事同时成立，不用非得挑一个。
