当 AI 改写了开源信任模型：Ladybird 关闭公开 PR，Anthropic 开源漏洞挖掘框架

2026-06-05
  • 开源
  • AI
  • 安全
  • Claude

今天 HN 上有两条新闻放一起看很有意思。Ladybird 浏览器宣布不再接受公开 Pull Request。同一天，Anthropic 开源了一个叫 DCRH 的自主漏洞挖掘框架。一个在关门，一个在开门。背后是同一件事：AI 正在瓦解我们对"代码贡献"这件事的默认假设。

Ladybird 关上了门

Ladybird 是一个从零开始写的开源浏览器，目标是做一个全新的、不带任何历史包袱的现代浏览器。听起来好像不可能，但他们已经快出 alpha 版了。

6月5日，项目创始人 Andreas Kling 发了一篇博文，宣布 Ladybird 不再接受公开 PR。以后的代码变更只由项目维护者引入，所有目前打开的公开 PR 全部关闭。

理由说得非常直接：

几十年来，代码贡献一直是开源项目识别信任的方式。人们提交补丁、做工作、对修改负责，然后留下来。信任是从工作本身生长出来的。

AI 工具迅速改变了这件事的经济学。一个实质性补丁曾经意味着实质性投入，而这种投入是善意的合理代理。这个假设不再成立。

翻译一下：以前一个人提交一个包含几千行代码的 PR，大概率这个人认真读了代码、理解了架构、花了真实时间在上面。现在用 Claude 或 ChatGPT 十分钟就能生成一个看起来很像样的 PR，但提交者自己可能并不理解代码在干什么。

对于一个浏览器来说，这件事尤其致命。浏览器接收来自整个互联网的不可信输入，一个精心伪装的漏洞就够了。而 AI 让"看起来像是认真的贡献"这件事的成本降到了几乎为零。

Kling 没有说他们发现了恶意 AI 生成的 PR，但他明确提到了开源社区里已经出现过"耐心、资源充足的渗透行动"——攻击者通过长期参与、积累信任，然后在合适的时机植入后门。AI 让这个过程的成本大幅降低。

Ladybird 的选择是用非常传统的方式回应一个新问题：缩小信任边界。只有少数人有权提交代码，代码审查的门槛提高。外部贡献者仍然可以通过 Bug Report、测试、安全报告、技术讨论参与项目，只是不能再直接提交代码。

Anthropic 的答案：让 AI 挖漏洞

如果 Ladybird 的回应是"防御性收缩"，那 Anthropic 的 DCRH（Defending Code Reference Harness）就是从另一个方向解题。

DCRH 是一个开源参考实现，用 Claude 做自主漏洞发现和修复。它不是产品，是一个可以定制的框架。典型的工作流：

recon → find → verify → dedupe → report → patch

具体来说：

Recon：一个轻量级 Agent 读源码，分析出"哪些输入解析子系统值得独立攻击"，做分区。后续的 Find Agent 被分派到不同区域，避免所有人撞到同一个 bug 上浪费时间。

Find：N 个并行 Agent，每个跑在独立的 gVisor 沙箱里。Agent 读源码，构造畸形输入，跑目标二进制（带 ASAN），直到某个输入在 3 次尝试中 3 次触发 crash。

Verify：一个独立的裁判 Agent 在全新的沙箱里复现 crash。Find Agent 只传给它 PoC 输入，别的什么都不共享。

Dedupe：法官 Agent 对比 crash 签名，判断是新 bug、已有 bug 的更好复现方式、还是应该跳过的重复项。

Report：生成结构化的可利用性分析：原语类型、可达性、升级路径、严重程度。

Patch：写修复，然后校验 Agent 确认修复后的代码能编译、测试套件通过、原来的 PoC 不再 crash、新 Find Agent 找不出绕过方式。

这套流程跑在 gVisor 容器里，每个 Agent 的出站流量白名单限制在 Claude API。Find Agent 是最危险的——它要执行未信任输入——所以隔离级别最高。

Anthropic 的文档里有一段挺有意思的话：

自主分诊和修补仍然是开放问题，这个参考框架没有完全解决它们。修复验证策略提高了标准，但严重度和优先级最终取决于你的环境判断，验证过的补丁也不总是能上游合并。很多合作方反馈说这些步骤是他们目前的瓶颈，你得为它们留出真实的工程时间。

他们很诚实——这不是银弹，只是一个起点。

两条路，同一个信号

Ladybird 和 Anthropic DCRH 看起来方向相反：一个在关贡献通道，一个在开漏洞挖掘通道。但背后是同一个问题：AI 让代码的量变不再传递信任信号。

以前我们默认：一个人写了代码 = 这个人理解这段代码。现在这个等式不成立了。

Ladybird 的选择是收紧"谁能写"。Anthropic 的选择是让 AI 去验证"代码里有什么"。本质上都是对信任模型的重新校准。

不只是浏览器开发者和安全工程师会碰到这个问题。维护任何稍微有点规模的开源项目，迟早要面对。公司内部在推 AI 辅助编程的，审计流程也必须跟着变。

我自己的看法是，Ladybird 这种完全关门的做法短期有效，长期不可持续。真正的趋势应该是 Anthropic 的方向——用 AI 对抗 AI 引入的问题。让 AI 帮你审查 AI 写的代码，让 AI 帮你发现 AI 可能植入的漏洞。

开源社区正在重新校准信任模型——从"谁写的代码"转向"代码里有什么"。这件事没有回头路，AI 制造了这个问题，但它也是目前最靠谱的应对工具。
