当 Claude 身价超越 ChatGPT：AI 编程的下半场，写代码的人去哪了？

2026-05-29
  • AI编程
  • Claude
  • Agent
  • Anthropic
  • 开发者工具

5 月 29 日，一条消息在开发者圈子里炸了：Anthropic 估值达到 9650 亿美元，首次超过 OpenAI。 同一天，Claude Opus 4.8 被开发者社区疯狂实测，最重要的一个评价是——"AI 终于学会承认自己不知道了"。

这两件事放在一起看，有一个信号越来越清晰：AI 编程的牌桌，正在重新洗牌。

Anthropic 凭什么超车？

9650 亿美元，18 倍 PS（市销率），这个数字放在两年前会被当成笑话。但现在，Anthropic 的营收已经反超 OpenAI 至少 35%，而且差距还在拉大。

原因不复杂。OpenAI 卖的是"通用智能"，Anthropic 卖的是"可信智能"。

对开发者来说，选哪个模型的决策已经从"谁回答得更聪明"变成了"谁的 API 更稳定、更安全、更适合企业级场景"。Claude Code 的爆发式增长验证了这一点——按 Claude Code 负责人的原话，他们已经看到"80 倍的需求增长"，而且不是来自个人开发者，是企业团队。

团队要的不是一个能和你聊天的 AI，是一个能在 CI/CD 流水线里运行、不出安全审计事故、有清晰问责链的 AI 程序员。Anthropic 恰好在这块吃到了最大的饼。

Opus 4.8：承认"不知道"才是真正的智能

有人实测 Opus 4.8 后说了一句让我印象深刻的话："它不再强行编答案了。"

几乎所有大模型都有一个通病——当被问到它不知道的东西时，会编造出听起来很合理的谎言。Opus 4.8 在这个问题上有了质的改变。它会在不确定的时候明确说"我不确定"或"这个问题超出我的知识范围"，而不是硬着头皮瞎编。

听起来是个小改进，但对 AI 编程来说，这是致命的代差。

一个会在代码库里瞎编 API 接口的 AI 助手，你每用一次都要 Review 一遍。一个会在不确定时主动告知的 AI 助手，Review 的工作量降了一个数量级。这就是为什么 Claude Code 的企业采用率在爆发——省的不是写代码的时间，是 Review 代码的时间。

但"省时间"真的省了吗？

V2EX 上有个热帖标题特别扎心："推行 AI 写代码一年后，Code Review 变成了新的加班理由。"

这句话揭示了 AI 编程的一个悖论：

  1. AI 写代码确实快——原来 2 小时的功能，现在 15 分钟生成
  2. 但 Review AI 生成的代码也需要时间——而且因为 AI 写得太快，提交量翻了几倍
  3. 结果：Review 环节被撑爆了，PM 觉得产能提高了于是加需求，于是开发更忙了

这跟自动化工厂的逻辑一模一样。机器人让产线更快了，但质检员没变多——反而因为产出暴增，质检变成了瓶颈。

AI 缩短了"写"的时间，却没有缩短"确认"的时间。 直到 Opus 4.8 这种"会承认自己不知道"的模型出现，Review 成本才开始真正下降——因为你不用每一行代码都怀疑它是不是在编了。

Token 预算失控：你花钱的速度比写代码的速度快

另一个被反复讨论的话题：Token 预算失控。

Agent 编程模式下，一次任务可以吃掉几百万 token。Claude Code 跑一个"重构这个模块"的任务，轻松烧掉 $5-10。如果你把 Agent 放到 CI 流水线里——每个 PR 跑一遍——一个月下来账单能顶一个初级工程师的工资。

这催生了一个新话题："服务即软件"（Service-as-Software）和 Token 经济。

以前卖软件是一锤子买卖（买断）或者订阅（SaaS）。现在有了 Agent，变成了每次运行都计费。写一个"自动 Code Review Bot"，部署成本是零，但每次运行的推理成本是实打实的。

有人算过一笔账：让 Claude Code Review 一个 500 行改动 PR 的成本是 $2-5。让人类工程师 Review 同样的 PR，按时薪折算下来大概 $20-30。AI 确实更便宜，但如果 PM 觉得"反正便宜"就开始什么 PR 都丢给 AI Review，总成本就上去了。

Token 预算控制正在变成开发者需要掌握的核心技能——prompt 怎么写能让 AI 一次做对、少跑几轮，这个能力直接影响团队预算。

AI Skill 生态的散落与整合

还有一个有趣的现象：AI Skills 系统的碎片化。

目前有 Claude Code 的 skills、Cursor 的 rules、GitHub Copilot 的 instructions、OpenCode 的 custom commands——每个工具都有自己的"给 AI 写提示词"的格式。有开发者在 V2EX 上发帖说"做了个 skillx，想解决 AI skills 到处散落、更新靠手拷的问题"。

这不只是个痛苦——这是个机会信号。意味着一个跨平台的 Skill 标准正在酝酿。类似 Docker 统一了"这个环境能跑"的问题，下一个要统一的问题是"这个 AI 在这个项目里应该怎么干活"。

一个写代码的人的看法

上面这些放在一起，我自己有几点判断：

1. 选模型 = 选 Review 策略。 Opus 4.8 的"不瞎编"比多拿几个 benchmark 第一重要得多。选模型的时候，别只看 SWE-bench 分数，去实测一下它会不会在不确定时承认——这直接决定你每天要多花多少时间 Review。

2. Token 计数是新的内存管理。 十年前写 C 要关心 malloc/free，现在写 AI 应用要关心 prompt 里塞了多少 token、每次 Agent 循环花了多少钱。这不是抠门，是工程能力。

3. 你的价值不在"写代码"本身了。 AI 写代码越来越快、越来越准，但判断什么该写、什么不该写、写出来对不对——这三个问题没有一个 AI 能替你回答。开发者从"打字员"变成"审核员"的趋势不可逆，越早接受，越早有优势。

4. Skills 标准化会来，别急着 All-in 某一个。 现在就把你的项目规范写在 .claude/skills/ 或 .cursor/rules/ 里没问题，但保持这些文件的结构化（别写散文，写声明式指令），将来迁移到统一标准会轻松很多。

Claude Opus 4.8 让 AI 学会说"我不知道"——而写代码的我们，可能需要学会说"我知道你不一定知道"了。
