一个校验和偏移，掀翻整台宿主机：PwnEscape 从 virtio 元数据到 KVM 逃逸

2026-11-07
  • Linux内核
  • 虚拟化安全
  • KVM
  • 漏洞分析
  • 网络协议栈

一个 32 字节的宿主内存泄露，最后变成 root 代码执行。整条链的起点不在 KVM 里，在 net/ipv4/ip_output.c 的几行代码。

pwn.ai 团队（Paulos Yibelo）在 Vercel 百万美元 Sandbox 挑战赛里做出来的东西，CVE-2026-99999，CVSS 9.3。三天找到原语，从提交上游到合入不到一个月。

值得写的不是"又一个逃逸"，而是它暴露的结构性缺陷：同一份数据包，在内核不同阶段被赋予不同可信度，中间有一个延迟写入可以改掉已经被信任的那部分。

一、CHECKSUM_PARTIAL 是一张"稍后付款"的欠条

Linux 不总是立刻算传输层校验和。它先让包处于"待完成"状态，再由网卡或软件辅助函数 skb_checksum_help() 补齐：

skb->ip_summed    = CHECKSUM_PARTIAL   // 校验和还没算
skb->csum_start   = <偏移>              // 从哪儿开始累加
skb->csum_offset  = <偏移>              // 从起点再偏移多少写结果

写入位置 = csum_start + csum_offset

这三个值不是描述性元数据，而是一次写操作的授权。谁能影响它们，谁就间接决定了将来往内存哪个地址写两个字节。正常路径下这个地址落在 TCP/UDP 头的校验和字段，而 virtio 的 __virtio_net_hdr_to_skb() 从 guest 侧读这些值——guest 可以直接影响它们。

历史代码在入口用 skb_transport_offset(skb) 做最小头部检查。这个偏移相对当前 skb->data 算，能挡住"起点明显太靠前"，但回答不了：包里带额外链路层头时，起点距离网络头有多远？

两个不等式看着像一回事，其实不是：

transport_offset                    >= minimum_network_header_length
transport_offset - network_offset   >= minimum_network_header_length

前者是帧内相对坐标，后者是网络头相对坐标。二层头一剥离，两套坐标系就对不上。

二、真正的杀手是执行顺序

问题不在某个检查写错了，而在于检查和使用之间隔了一次可以改数据的写入。修复前 ip_do_fragment() 的次序：

if (skb->ip_summed == CHECKSUM_PARTIAL)
        skb_checksum_help(skb);   /* 延迟写入发生在这里 */

iph = ip_hdr(skb);
/* 后面从 iph->ihl 推出头部长度 */

skb_checksum_help() 本身没问题。它变危险，是因为畸形元数据让它的写入落在已经被解析、已经被信任的 IPv4 头里面。

被改的字段是 ihl，4 个 bit，单位 32 位字。受控几何里首字节从 0x45（IPv4，5 字 = 20 字节）变成 0x4f（IPv4，15 字 = 60 字节），版本位 4 没动，只有长度解释从 20 变成 60。

不可信输入                      宿主网络栈
──────────                      ──────────────────────────
包 + 部分校验和元数据 ───────►  元数据装入 skb → L3 归一化
                                → IPv4 解析、重组、路由
                                  头部按 IHL=5（20 字节）被信任
                                → 出口分片 → skb_checksum_help()
                                  延迟写入改掉已解析的头部
                                → ip_do_fragment() 读到 IHL=15
                                  头部声称 60 字节，拷贝超出线性数据
                                → 发出的 IP options 里混进宿主字节

全过程确定性，不是线程竞态。隔开"检查"和"使用"的"时间"，是若干合法网络步骤，中间夹一次受攻击者影响的延迟写入。

32 字节是怎么来的

Linux 包缓冲不要求连续，sk_buff 有线性 head 还可能有非线性 frag。该案例重组后逻辑线性长度只有：

20 字节  原始 IPv4 头
 8 字节  第一个分片里的有效载荷
────────
28 字节  skb 逻辑线性长度

延迟的校验和操作让分片器以为 IP 头有 60 字节，于是把 20 字节头之后的 40 字节全当 IPv4 options：8 字节确实在线性 head 里（本是载荷），剩下 32 字节根本不属于这个包的逻辑线性数据。skb_headlen(skb) = 28，后续拷贝长度 60，差正好 32。

必须说清："越界"指越出 sk_buff 的有效逻辑包数据，不必然越出整个分配器对象。 宿主可能已物理映射了 tailroom，读那些字节不会崩，但它们属于宿主内存。塞进要发出去的 IP 头就跨了机密性边界，而且可外部观测——旁边抓包就能看到这些字节冒充 IP options。

实验设计上他们设了身份组（头长度不变，证明基线）和活跃组对照，除了抓包还有一路应用层收据独立验证。活跃案例每次稳定泄露 32 字节，并在自有的 Linux 6.12 / 7.x 机器上确认了宿主侧可用性故障。

三、从读原语到写原语

可重复、攻击者可控的宿主内存读取，在多租户环境里已经很严重。但更有意思的是它对漏洞研究本身的作用：有了读原语，宿主内存状态的不确定性大幅下降，下一批内存操纵假设变得可测试。在自有 KVM 环境里，研究推进到了选择性 64 字节宿主内核写，并在受限实验室链条里跑起宿主 root 辅助程序，把宿主产生的标记回传给 guest。四次真正的冷启动都复现了。

原文措辞很克制，值得照着写：

我们说"guest 到宿主逃逸"，指的是在隔离的自有验证环境里的证明。它不是从一次越界读推断出来的结论，也不是对任何厂商生产环境 root 命令执行的宣称。

证据阶梯是：源码假设、受控变异、宿主内存泄露、选择性内核写、自有机器上的受限执行，每级是不同强度的主张。多数人写到第三级就直接喊 RCE 了。

四、Part 2：接管 Firecracker 的 vCPU 线程

Firecracker 是每个 microVM 在宿主上的一个进程，每个虚拟 CPU 对应进程里一个线程。线程进入 KVM 跑 guest，遇到需在用户态处理的事件时返回：

ioctl(vcpu_fd, KVM_RUN, 0);

线程停留在该系统调用里时，宿主内核把它的用户态寄存器保存在 pt_regs 里。这些寄存器描述 Firecracker 线程：指令指针说该回到哪儿继续，栈指针说该用哪个用户态栈。 所以从 KVM_RUN 返回的那一刻是极好的攻击点——能改这个保存的寄存器帧，就能决定 Firecracker 回到用户态后执行什么。触发也简单：让 vCPU 返回一次。

定位链条四步

第一步，找自己那个 guest 页在宿主的哪。 guest 物理地址（GPA）和宿主物理地址（HPA）是两个空间，靠 EPT 翻译。他们往 guest 页放一个 nonce，搜宿主物理范围里的候选 EPT 根，按 guest 地址走表，走到物理页比 nonce：

for root in candidate_ept_roots:
    page_hpa = walk_ept(root, guest_gpa)
    if page_hpa is invalid: continue
    if read_host(page_hpa, length(nonce)) == nonce:
        candidates.append((root, page_hpa))

两个候选，用嵌套页表验证收敛到一个，得到 guest_page_hpa。

第二步，反查是哪台进程映射了它。 正常页表遍历是从虚拟地址求物理地址，这里反过来：已知物理页，求虚拟地址和页表根（PGD）。遍历宿主页表找 guest_page_hpa 的映射，拿到候选的 pgd 和虚拟地址，再用 walk_host_page_tables(pgd, va) 正向走一遍确认能回到同一物理页、且内容仍是那个 nonce，双向校验通过才算数。留住 host_pgd。

第三步，找到 Firecracker 本体，绕过 ASLR。 找 ELF 镜像，校验 Firecracker write(2) 包装里一段已知字节序列。镜像内地址和运行时地址的差就是 load bias：

runtime_code_address = load_bias + code_address_in_elf

第四步，锁定当前 vCPU 的寄存器帧。 线索是返回地址——在 KVM_RUN 里的线程，保存的指令指针应指向 ioctl 调用点之后，这个地址能从验证过的二进制加 load bias 算出。但单纯地址匹配会碰到栈上陈旧内容，所以候选还要同时满足栈检查（绑回从 guest 页恢复的地址空间）、指令和调用者地址（绑回 Firecracker 镜像）、系统调用字段（绑回正在跑 vCPU 的操作）。最后只剩一个。

五、劫持返回，然后恢复现场

payload 很朴素：让 Firecracker 往自己的 stderr 写一个可识别字符串。字符串 N8V23M2\n，七个字符加换行，正好一个栈字：

write(2, "N8V23M2\n", 8);

改之前先保存三个栈字（一个放字符串，两个放临时调用序列的返回地址），然后把保存的寄存器帧改成：

RIP = Firecracker write 包装的地址
RDI = 2
RSI = Firecracker 栈上标记字符串的虚拟地址
RDX = 8
RSP = 临时返回序列的虚拟地址

返回路径有个细节：write 成功返回 8，KVM_RUN 成功返回 0。所以返回序列第一个地址放 xor eax,eax; ret 清零，第二个地址跳回原本的 ioctl 继续点。触发方式是 guest 往自己串口写一个字节，这让 vCPU 线程从 KVM_RUN 返回，内核恢复被改过的寄存器，Firecracker 进入 write 包装。宿主侧单独捕获 stderr，完整输出八个字节：

N8V23M2

同时 Firecracker 还在跑，guest SSH 还能连，三个临时栈字已恢复。随后又跑一次不做内存修改的校验，重复寄存器、代码、栈三组检查，通过且无残留标记。

环境：Firecracker v1.16.1 / x86-64，宿主内核 7.0.0-1011-aws，guest 内核 6.18.44+，Firecracker 由 systemd-run 直接以 root 启动并 taskset 绑核，所以那个受控调用以宿主 root 身份执行。

边界必须点明：这个配置没开 jailer。生产环境的 Firecracker 会降权限、用 namespace 和 seccomp 限制进程。用了那些管控的部署，打穿 VMM 之后还能拿多少权限，需要单独评估。

六、防御方该改什么

最终合入的是 Michael S. Tsirkin（Red Hat）的版本，commit 6785011f8b16，10 月 8 日进 net.git，10 月 14 日进主线。思路是在每个消费点前加一道 IPv4 专用检查，而不是重做 virtio 校验和 API。共享辅助函数放在 include/net/ip.h：

static inline int ip_check_csum_start(const struct sk_buff *skb)
{
        if (unlikely(skb->csum_start <
                     skb->network_header + ip_hdrlen(skb)))
                return -EINVAL;
        return 0;
}

不变量一句话：校验和起点必须不早于「IPv4 网络头起点 + 已解析的 IPv4 头长度」。 对非负 csum_offset，这保证最终写入位置不会落进 IPv4 头。它不去认证目标是否合法 TCP/UDP 校验和字段，只做保护已信任 IPv4 头所必需的窄承诺。

改动范围：6 个文件，44 行新增、12 行删除——include/net/ip.h 新增辅助函数，其余五处是消费点：ip_output.c 的 ip_do_fragment()、网桥的 nf_conntrack_bridge.c、XFRM 的 xfrm_output.c、nfnetlink_queue.c 的 nf_queue_checksum_help()、xt_CHECKSUM.c 的 checksum_tg()（IPv4 检查失败直接 NF_DROP）。

ip_do_fragment() 修复后：

if (skb->ip_summed == CHECKSUM_PARTIAL) {
        err = ip_check_csum_start(skb);
        if (!err)
                err = skb_checksum_help(skb);
        if (err)
                goto fail;
}

先验起点，再补校验和。 就这一个顺序调换。补丁说明写得很明确，这是 defence in depth，完整入口校验还需要更多工作——别把"已修复"理解成"这个攻击面关了"。

自查

# 1. 内核版本，对照 distro stable 分支是否已含 6785011f8b16
uname -r

# 2. 是否开了 jailer
ps -o pid,args -C firecracker | grep -c jailer

# 3. seccomp / 权限是否真的收住了
grep -E "Seccomp|CapEff" /proc/<firecracker_pid>/status

第三条尤其重要。PwnEscape 的杀伤力很大程度来自"VMM 进程权限过高"这个前提。降权到非 root、开 jailer、限制 seccomp，即使 VMM 被打穿，拿到的也只是受限进程。

七、这个模式有个名字：deferred-metadata trust inversion

原文给这类缺陷起了名，是最有复用价值的部分。三种信任转移叠加：

  • 来源信任：较低信任的 guest 或进程，描述了宿主将来要执行的操作
  • 解释信任：包在链路层处理中改变了表示，内核按某布局解析字段
  • 时间信任：延迟操作在被解析状态被下一个消费者使用前把它改掉
不可信元数据进入 → 按早期表示校验 → 包被归一化/解析/授权
  → 元数据驱动的操作稍后运行 → 安全相关字节变化
  → 后来的消费者信任了被改过的解释 → 内存安全或策略边界失效

对应的审计问题不是"校验和偏移校验了吗"，而是：每一次变换之后，延迟写入还能不能指向那些语义已经被信任了的字节？ 这个问题可以拿去问零拷贝路径、GSO/GRO 聚合、BPF 的 skb 改写、io_uring 提交队列。凡是"先检查后执行、中间还允许改数据"的地方都值得过一遍。

八、我的看法

虚拟化边界的信任模型该重画了。 大家习惯认为 VM 隔离住在 hypervisor 里，攻击面就是 arch/x86/kvm/。实际 guest 面对的是整个宿主操作系统。PwnEscape 的漏洞不在 hypervisor，在 net/ipv4/ip_output.c。

性能契约是天然攻击面。 CHECKSUM_PARTIAL 存在的唯一理由是性能。为了跑得快把工作推迟，天生拉长了不变量暴露窗口：你接受延迟，就等于接受"这段时间里数据不能变"这个额外约束，而这类约束最容易被漏掉。

研究方法的可复制性比漏洞本身值钱。 三天找到原语，靠的是把攻击面画成"哪里不可信状态被提升为可信状态"的地图，再逐个挑战后续消费者，而不是死磕初始解析器。证据分层那套比任何一份 hex dump 都更该抄进自己的报告模板。

AI 辅助漏洞研究已经不是新闻稿里的东西。 这次用 Omega-Pwn 加 GPT-5.6 Sol 做源码级分析，人类定范围和判定什么算证据，整轮 API 成本不到 700 美元。价值不在"AI 找到了漏洞"，而在那个循环：提出不变量违背 → 建受限测试 → 检查对照和否证案例 → 保留证据 → 与专家迭代 → 请独立 reviewer 攻击结论。

一点保留：所有结论都基于自有的、无 jailer 的 Firecracker 环境。看这类研究容易直接跳到"KVM 不安全"，但 Firecracker 的安全模型本来就是假设 VMM 会被打穿，用 jailer 兜底。如果你在跑 Firecracker 又没开 jailer，那才是今天该去改配置的事。
