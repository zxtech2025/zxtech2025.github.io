杀毒软件成了投递管道：cPGuard 更新通道被投毒，以及"可信更新"这个概念还剩多少

2026-11-13
  • 供应链攻击
  • 安全
  • Linux
  • 凭证泄露
  • 更新签名

11 月 2 日凌晨 2 点 06 分，有人登录了 OPSSHIELD 的更新分发网络。用的是一组能用的账号密码。不是零日，不是越权，没有一行漏洞利用代码。

从那一刻起，cPGuard 的更新通道变成了投递管道。cPGuard 是装在 Linux 宿主机上的防火墙加恶意软件扫描器，虚拟主机商、IDC、小型云厂商用得很多。也就是说，被投毒的更新包，落在了管理员最信任的那批机器上，那些"已经有安全软件保护"的机器。

厂商 12 小时内切断投递，估计攻击者取走了 32 个文件，每个文件对应一台客户服务器。32 台听起来不多，但每一台都是虚拟主机商的核心节点，一台上面可能跑着几百个客户站点。

我读完时间线和脚本行为之后，最想拆的不是"供应链攻击又来了"，而是一个更尴尬的问题：为什么投毒一个杀毒软件的更新通道，成本比发一封钓鱼邮件还低。

一、脚本干了什么：全部指向 root 手里那点东西

恶意脚本的目标非常收敛，全部指向 Linux 服务器上权限最高的那部分资产：

  • /etc/shadow 和 /etc/passwd，本地账号与密码哈希
  • root 的 my.cnf，里面有数据库的 root 口令
  • root 的 shell 历史，这是最容易被低估的一项：很多运维顺手把云厂商 token、S3 密钥直接敲在命令行里
  • root 的 SSH 授权文件（authorized_keys）和 known_hosts

暂存方式很朴素：在 /var/tmp 下建一个隐藏目录，收集完再上传。上传目标是 OPSSHIELD 自己的授权服务器，用一个已攻陷的账号。

这一手值得单独说。用受害者的基础设施存受害者的数据，两个好处：流量看起来就是一次正常的授权校验，混在正常心跳里不显眼；而且从检测的角度，你很难对自己产品的授权域名做阻断策略。后门 shell 落在 /var/tmp/.cpg91511_sh。

受影响版本是 5.88.12 到 5.88.19。修复版本 5.88.25 会清理后门脚本和暂存文件。

二、为什么这次比普通供应链攻击更难受

供应链攻击这几年不缺案例：SolarWinds 攻破 Orion 的构建流程，3CX 投毒桌面客户端，xz 在 liblzma 里埋后门。套路都是攻破上游、借信任往下推。

cPGuard 这次的不同在于被投毒的是一个安全软件本身。这带来两个连锁后果。

第一，它绕过了所有人对"更新"这个动作的心理防线。运维看见"cPGuard 更新到 5.88.15"，第一反应是"安全补丁，赶紧装"。没有人会去审计一个杀毒软件的更新包，就像没有人会每天检查门锁有没有被人换掉。

第二，它站的位置太好了。cPGuard 跑在宿主机上，通常有 root 权限，能读所有文件，能改防火墙规则。攻击者不需要提权，不需要横向移动，一步到位就是最高权限。你平时用来"提升安全性"的那个组件，本身就持有你最敏感的数据的读取权。

厂商的原话是"使用了被泄露的凭证获取未授权访问"。这是 2026 年最需要反复讲的一句话：防线崩塌的地方，绝大多数时候不是代码，是账号。

三、自查：版本、日志、后门文件

先看版本，5.88.12 到 5.88.19 之间全部视为受影响。

# 当前版本
cpgcli --version

# 更新日志：只要出现过受影响版本号，就按已失陷处理
grep "Successfully updated" /opt/cpguard/logs/install_log

厂商的建议很硬：日志里出现过受影响版本，即使现在已经升到修复版，也要按已被入侵处理。升级只清理后门文件，不改变"凭证已经泄露"这个事实。

反过来，日志不存在不代表安全。日志可能被清过，也可能根本没记全。

# 已知后门路径
ls -la /var/tmp/.cpg91511_sh

# 更值得查的：/var/tmp 下最近新建的隐藏目录（暂存用）
find /var/tmp -maxdepth 1 -name ".*" -newermt "-7 days" -ls

只查已知路径是不够的。脚本在 /var/tmp 下建过隐藏目录做暂存，这些目录名看起来像随机串，得靠创建时间和权限特征去翻。

四、清理顺序：先升级是错的

很多人的第一反应是"先升级"。升级必须做，但不能只做，而且顺序错了会把简单问题做成复杂问题。

第一步，升到 5.88.25 或以上。新版会删掉后门脚本和暂存文件。

cpgcli update --start
cpgcli --version

第二步，从可信环境重置 root 和所有本地账号的密码。注意是"可信环境"：如果这台机器本身可能被动过，用它自己的 passwd 去改密码毫无意义，攻击者留下的后门会照抄新密码。

第三步，轮换所有可能在 shell 历史里出现过的凭证。数据库口令、对象存储的 Access Key、云厂商 API token、各种 secret。凡 root 敲过的，一律作废重发。这一条工作量最大，也最容易被跳过。

第四步，替换 /root/.ssh 下的密钥对，并且去所有信任这把公钥的地方把旧的删掉。这一步经常漏，因为大家只管本机，不管对端。authorized_keys 被拿走了，攻击者可以随时回来。

第五步，翻 /root/.bash_history 找异常命令和登录记录。如果里面有攻击者执行的痕迹，这台机器要按失陷主机处理，不是按"打补丁"处理。

厂商目前的说法是不建议整体重装，理由也成立：托管几百个站点的机器重装成本太高。但它同时说了调查还在进行中，"目前没有发现其他恶意活动"是初步结论。如果这台机器上跑着客户的支付数据或身份信息，要不要重装，这个决定不该由厂商替你做。

五、真正的问题：更新这个动作缺一层验证

xz 事件之后，开源社区讨论过一轮"我们该信任谁"。cPGuard 把问题往前推了一步：连商业安全厂商的分发通道都能被一组泄露的凭证打开，那"可信更新"这个概念还剩多少含金量？

答案不是"不要更新"，那是自杀。答案是把验证加进去。几个已经在做、也该普及的做法：

更新包要签名，客户端要验签，而且验签的根不能和分发通道在同一个权限域里。这次攻击者进的是 CDN。如果签名私钥不在 CDN 上，投毒的包根本过不了校验。工程上这意味着签名服务要和分发网络彻底分权：不同账号体系、不同网络位置、最好不同云。

分发账号必须和设备侧解耦。一组静态密码不应该成为整条链的单点。硬件密钥或者短时令牌，成本很低。

客户端要有行为白名单。一个杀毒软件的更新逻辑应该是确定的、可预期的。一旦更新后出现新行为，比如突然去读 /etc/shadow，本地就该拦。听着讽刺，但杀毒软件本身没有读取 shadow 文件的业务需求，这类访问完全可以默认拒绝。这是 eBPF 或 LSM 最实际的用武之地，比拿来做"零信任"演示有价值得多。

最后一条是组织层面的：给安全产品本身做资产分级。它比业务系统更该被重点保护，因为它站在更高的权限位置上。很多公司的 CMDB 里，cPGuard 这种 agent 就是一串 IP，没有责任人，没有变更记录。出事的时候没人说得清哪台装过、什么时候更新的、谁批的。

六、我的做法

我自己的机器上也装了类似的东西，看完这件事改了几处：

# 1. 更新日志单独留档，不跟厂商日志轮转一起删
grep "Successfully updated" /opt/*/logs/install_log >> /var/log/agent-updates.log

# 2. 敏感文件访问兜底：任何 agent 进程读这几条就告警
auditctl -w /etc/shadow -p r -k agent_shadow_read
auditctl -w /root/.bash_history -p r -k agent_hist_read

# 3. 更新包落地后、执行前，校验签名并留 hash
sha256sum /var/cache/agent/*.pkg >> /var/log/agent-pkg-hash.log

三条都不复杂，核心思路是一致的：别把"它是安全软件"当成它可以高权限无审计的理由。恰恰相反，权限越高的组件，越需要独立的可观测性，因为它出事的时候没有第二道防线。

32 台服务器，12 小时窗口，一组被偷的密码。攻击者付出的成本可能还不如准备一次钓鱼邮件来得多。而防守方要付的，是全部凭证的轮换、客户的解释，以及一个很难回答的问题：

我们凭什么相信下一个更新包是干净的。
