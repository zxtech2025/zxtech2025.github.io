Google 把 Gemini 和搜索向所有开发者开放：这是 agentic web 的 SEO 时刻

2026-10-28
  • AI
  • Google
  • AI Agent
  • MCP
  • 平台生态

10 月 28 日，Google 做了一件在 AI 平台竞争里挺关键的事：把 Gemini 和 Google 搜索的"连接应用"能力，向所有企业开发者开放。

以前只有少数合作方能接入，现在任何商家或开发者都可以提交自己的应用，让用户在 Search 或 Gemini 里直接调用。

TechCrunch 的 Sarah Perez 给了个很准的类比：这相当于 agentic web 的 SEO 时刻。

一、机制：通过 MCP 接入

技术路径很清晰：

开发者集成 cloud-hosted MCP server
        ↓（或 Android MCP + AppFunctions API）
    Google Connected Console
        ↓（注册 / 测试 / 提交）
        应用上线
        ↓
用户在 Search / Gemini 里直接调用

MCP（Model Context Protocol） 是关键。这个协议原本是 Anthropic 提出的，现在被 Google 用在自家平台上——某种程度上说明 MCP 正在成为 Agent 调用外部工具的事实标准。

开发者能获得什么

能力 说明
流量 用户在 Search/Gemini 里直接触达你的服务
监控 流量、延迟、错误率
品牌控制 已验证的 logo、认证账号
可选范围 自己决定在 Search 还是 Gemini 上架

当前状态

  • Beta 阶段
  • 仅限美国开发者
  • 通过 AppFunctions API 集成

二、为什么叫"agentic web 的 SEO 时刻"

这个类比值得展开。

SEO 时代发生了什么

搜索引擎出现之前，网站要靠用户记住域名。搜索普及后，能不能被搜到决定了流量归属。

于是诞生了一整个行业：关键词优化、结构化数据、外链建设……核心就一件事——让你的内容被机器理解并优先展示。

Agentic web 时代在发生什么

现在用户在 AI 里提问："帮我订下周三去杭州的高铁，靠窗，下午的。"

以前用户要： 1. 打开 12306 或携程 2. 搜索、筛选、比较 3. 下单

现在希望 AI 直接做完。

但 AI 怎么知道该调用谁的服务？ 这就回到了"被机器理解并优先展示"——只是这次不是给搜索爬虫看，是给 Agent 看。

差别在哪

SEO Agentic SEO
优化对象 搜索爬虫 AI Agent
交付形式 网页（用户自己看） 结构化能力（Agent 调用）
关键指标 排名、点击率 被调用的准确率、成功率
技术门槛 HTML、结构化数据 MCP server、API 设计

技术门槛明显更高了。 不是写几段 meta 标签的事，你得真的提供一个机器可调用的接口。

三、这件事的真实含义

1. Google 在防守，也在进攻

TechCrunch 点出了背景：

ChatGPT 和 Meta 的 Muse 都在做类似的连接应用。前提是这些集成最终会把消费者行为从"打开单个应用"转向"在 AI 里完成任务"。

如果用户不再打开 App，而是让 AI 代劳，那么"被 AI 选中"就取代"被用户打开"成为流量入口。

Google 的优势是它同时握着搜索和Gemini两个入口。开放接入，是把生态锁在自己的入口上——你不接 Google，用户就可能被接了的竞对抢走。

2. MCP 正在成为标准

值得单独说一句：Google 选择用 MCP 而不是自研协议。

这个信号很强。原本 MCP 是 Anthropic 提出的开源协议，现在 OpenAI、Google 都在用或兼容。协议层的统一，对开发者是好事——写一次接入，能覆盖多家平台。

3. 但不是所有开发者都能用上

注意两个限制：Beta、仅美国。

这意味着短期内，这个红利主要给美国本土服务商。对其他地区的开发者，现在最实际的动作是把自己的 API 设计成"Agent 友好"的形态，等平台开放时能快速接入。

四、如果你要做"Agent 友好"的接口

几条实操建议，跟具体平台无关：

1. 能力要原子化

别做一个"下单"大接口，拆成： - 查询商品/库存 - 查询价格 - 创建订单 - 查询订单状态

Agent 需要的是可组合的小步骤，因为用户的需求往往是模糊的，Agent 得自己拼路径。

2. 返回结构要稳定可解析

{
  "status": "ok",
  "data": {
    "items": [
      {"id": "xxx", "name": "yyy", "price": 123.00, "available": true}
    ]
  },
  "meta": {"total": 1, "page": 1}
}

不要返回自然语言描述让 Agent 自己解析——那是给 LLM 增加出错概率。

3. 错误信息要能指导下一步

{
  "status": "error",
  "code": "OUT_OF_STOCK",
  "message": "该商品无库存",
  "suggestion": "可查询替代商品 /alternatives?id=xxx"
}

Agent 看到 suggestion 就知道该怎么转向，不用瞎猜。

4. 提供置信度和不确定性

如果某个结果不确定（比如"大概有货"），明确标出来。Agent 需要这个信号决定要不要询问用户。

5. 幂等很重要

Agent 可能重试。相同的请求应该返回相同结果，不要重复下单。

五、一点判断

这个开放的短期影响不会很大——Beta、仅美国、生态还在建设。

但方向很清楚：未来流量的分配权，掌握在"入口"手里，而入口正在从 App 变成 AI。

对开发者的启示是："能不能被 Agent 调用"会像当年"能不能被搜到"一样，成为基础能力要求。

现在开始把接口往"Agent 友好"方向改，比等平台开放了再改要划算得多——接口设计这种东西，改起来成本很高。
