4bpp 图像解码只用 7 条指令：nibnib 用"差分调色板"把 RP2350 的显存难题绕过去了

2026-11-02
  • 图像压缩
  • 嵌入式
  • RP2350
  • 汇编
  • 编解码器

Raph Levien 上周放出了一个叫 nibnib 的图像格式，一句话概括：4bpp，解码一条扫描线只用 7 条 ARM 指令，目标是把 640×480 的画面直接从 flash 里喂给 DVI 输出。

这个东西本身不大，README 六千多字，decode.rs 77 行。但它解决的是一个很具体的问题，而且解法在 40 年前就有人用过，只是被重新发明了一次。我把编码器、解码器都用 Python 复刻了一遍跑出数据，再对着 vic-2350（配套的 RP2350 复古电脑项目）的汇编看了一遍，下面是我觉得值得记下来的部分。

问题：没有显存，也没有时间

RP2350 是树莓派的双核 Cortex-M33 单片机，520KB SRAM。它有个 HSTX 外设，能以 TMDS 方式直接输出 DVI：你给它一串 RGB565 字，它就按像素时钟往外扫。

640×480 的 RGB565 一帧是 614400 字节，远超它全部的 SRAM。所以 framebuffer 这条路直接断了。

剩下的选择只有"边算边送"：DMA 按扫描线从某个缓冲区取像素，CPU 必须在这一行的 31.7 微秒内把下一行的像素算好。按 144MHz 主频算，一行只有大约 4570 个周期，摊到 640 个像素上是每像素 7 个周期左右。这就是 README 里"每像素约 6 个周期预算"的由来，它不是性能目标，是硬件给的硬上限。

vic-2350 的做法是抢跑（beam racing）：HSTX 扫第 y 行时，渲染中断在算第 y+3 行，中间靠四个行缓冲垫着。源码 main.sy 里写得很清楚：

const LINE_WORDS = 1 + H_ACTIVE / 2   // 1 个 HSTX 命令字 + 640 个 RGB565 像素
const N_LINES = 4
static mut video_lines: [[u32; LINE_WORDS]; N_LINES]

四个缓冲 = 120KB，占掉接近四分之一的 SRAM。渲染方最多领先三行，能吸收一次约 95 微秒的卡顿；再晚，那一行就吐一条全红的 err_line（ERR_PIXELS = 0xf800f800，两个 0xF800 拼成一个字）。

所以真正要解决的约束有两条，都很硬：数据得压到 flash/SD 读得动的程度，解码得在 7 个周期内完成一个像素。

解码：两像素一组，加一个查表

nibnib 的解码循环就这几行，从 decode.rs 抄的：

let mut pix = read_u32(&src[i..]);      // 行首的像素对原样存
two_565_pixels(&mut result, pix);
i += 4;
for _x in 1..(width / 2) {
    let inp = src[i];
    i += 1;
    pix = ((pix >> 16) * 0x10001).wrapping_add(pal[inp as usize]);
    two_565_pixels(&mut result, pix);
}

拆开看，一个字节输入对应两个输出像素：

  1. 取上一个像素对的右像素，乘 0x10001。这一步是"复制到两半"——p * 0x10001 等于把低 16 位和高 16 位都填成 p。实测 0x1234 * 0x10001 = 0x12341234，0xffff 得到 0xffffffff。
  2. 加上调色板第 inp 项。调色板存的是差值，一个 32 位字同时装了两个 16 位增量：低 16 位给左像素，高 16 位给右像素。
  3. 低 16 位就是左像素，高 16 位是右像素，各取出来转 RGB888。

这就是全部。没有熵解码，没有霍夫曼表，没有比特流对齐。一个输入字节索引 256 项调色板，一次 32 位加法的结果直接就是两个像素。

对应的 RP2350 汇编在 vic-2350/image.sy，写在 symbolasm 里，主循环是这样的：

loop {
    ix @r5 = *src8++
    *pixels++ = pair
    delta @r5 = *(pal + ix * 4)
    pair = pkhtb(pair, pair >> 16)     # 把右半复制到左半
    #(count -= 1)
    pair += delta
    if #ne goto loop
}

7 条指令一组，出两个像素，也就是每像素 3.5 条。加上取指和分支的实际开销，正好落在 6 周期预算里。pkhtb 是 Thumb-2 的半字搬运指令，在这里干的是"复制右像素到左半"的活，一条指令替代了移位加或运算两条。

编码：慢五个数量级，但只在打包时慢一次

解码这么简单，代价全压到编码端。README 自己说了："搜索空间很不对称，当前编码器比解码器慢几个数量级。"

我把它 port 成 Python 跑了一下，在 160×120 的合成图上编码 6.7 秒、解码 0.01 秒，比值 500 倍左右。纯 Python 的数字不能当性能基准，但比值数量级是可信的——因为算法结构决定的：每个像素对，编码器要对 256 项调色板穷举一遍。

encode.rs 里的搜索循环：

for code in 0..256 {
    let pixpair = base.wrapping_add(pal[code]);
    let cand0 = Pix::from_565(pixpair as u16);
    let cand1 = Pix::from_565((pixpair >> 16) as u16);
    let delta0 = pix0_w_err - cand0;
    let delta1 = pix1_w_err - cand1;
    let errp = (delta0 + delta1).hypot2();          // 和，低空间频率权重
    let err_base = (7. / 16.) * delta0.hypot2() + delta1.hypot2();
    let total_err = errp + 0.5 * err_base;
    if total_err < best_err { best_code = code; best_err = total_err; }
}

两个细节值得看。

base 用的是 p as u32 * 0x10001，而 p 是上一个像素对的右像素。 我一开始以为这是巧合，验证了一下不是：编码器用来评估"这颗码字会解成什么样"的起点，和解码器实际用的起点，是同一个算术表达式。这意味着编码器的搜索空间精确等于解码器的可达集合，不存在"编得出来但解不出来"的码字。差分编码最容易翻车的地方是误差累积导致解码漂移，而这里因为编码器是逐像素模拟解码过程再选码，压根不会积累到"解错"。我写了个小脚本对着几个边界值（0x0000、0xffff、0x07e0、0xf800）双向验算过，浮点侧和整数侧对得上。

误差度量的 hypot2 是加权平方和：0.3r² + 0.7g² + 0.1b²。人眼对绿通道最敏感、蓝通道最不敏感，这个权重是标准做法。而 errp 用的是 (delta0 + delta1)——两个像素误差之和，不是各自误差之和。README 的解释是模拟人眼对低空间频率更敏感：一对像素如果同向偏了 3 个色阶，比一个偏 6、一个不偏要更显眼。这个"先加再算范数"的设计是全篇唯一非标准的地方，也是它能达到 4bpp 还不太难看的原因。

32 位加法里的进位：一个真问题，但它无害

RGB565 的两个像素打成 32 位一个字，低 16 位加高 16 位一次加完。这里有个显而易见的隐患：低半字溢出的进位会串到高半字。

我实测了一下，随机取起始像素和调色板项，50.0% 的情况下低半字的进位确实改变了高半字（200000 次采样命中 99966 次）。所以这不是理论风险，是每次加法都有一半概率发生的事。

但它不构成 bug，理由是：编码器在搜索时就调用了同一份 base.wrapping_add(pal[code]) 和 Pix::from_565(pixpair >> 16)，它评估的候选值就是带进位串扰的那个值。解码器侧一样。两边用的同一个函数，串扰就成了编码的一部分，只是往右像素里掺了一点左像素的信息。只要编解码两侧的算术完全一致，"多余"的运算反而是免费的保真度。

这个思路比"避免进位"更省事：真去屏蔽进位，每个像素得多两条指令，7 条预算立刻爆掉。

调色板：45 项结构化网格 + 211 项随机

README 里提到"没有 cube 项就会有坏 artefact"。encode.rs 的 gaussian_pal() 揭示了 cube 的构造：

for step in 0..=2 {
    let delta = (2.0f32).powi(step);      // 1, 2, 4
    for geom in 0..45 {
        if geom == 22 && step > 0 { continue; }
        let dx = (geom % 3 - 1) as f32;   // -1, 0, 1
        let dy = ((geom / 3) % 5 - 2) as f32;  // -2..2
        let dz = (geom / 15 - 1) as f32;  // -1, 0, 1
        let r0 = 0.5 * delta * dx;
        ...
    }
}

geom 从 0 数到 44，拆成 3×5×3 的三维索引，落在 ±1/±2 的格子上，再乘 1、2、4 三档幅度。这就是"小差值立方体"。geom == 22 是原点（0,0,0），除了 step 0 之外都跳过，避免重复零项。

为什么要这个立方体，README 讲得比我清楚：只在接近 0 和满幅的地方需要精确的差值，防止溢出。 差分编码在极值附近最脆弱——上一个像素是 0xFF，再加一个正增量就绕到黑；上一个像素是 0x00，减一点就饱和。结构化的小步长项能保证这两处有可用的码字，不至于被迫用大幅跳变。

剩下 211 项走加权高斯，scale = exp(-2.0 * rand()) 让大部分项很小、少数项很大，配合高斯采样生成相邻像素的斜率。这套参数是作者调出来的，源码里 // Tune error balance、// Semi-structured palette 这些 commit 记录了过程。

我实测的数

我把 encode.rs、decode.rs 翻成 Python，用真实的照片（flowers7.png，1000×750 裁一块降到 120×90）和几种合成图各跑一遍，调色板按上面的规则重建：

内容 分辨率 bpp PSNR
真实照片（裁切缩放） 120×90 4.27 26.1 dB
双向渐变 + 硬边面板 160×120 4.20 37.6 dB
双轴渐变 + 锯齿对角 160×120 4.20 30.3 dB
纯合成平滑图 160×120 4.20 38.2 dB

表里"bpp"只算像素数据，不含 1028 字节的文件头（4 字节尺寸 + 1024 字节调色板）。小图上这个头会稀释掉整张图的压缩率：120×90 的图，屏体 16200 字节，头部占 6%，整文件算下来是 5.4bpp。

4.20 而不是 4.00 的原因在行末：line_stride(160) 返回 84，实际载荷是 160/2 + 2 = 82 字节，剩 2 字节填充。宽 640 时是 324 对 322，填充占比降到 0.6%，所以 640×480 实测 4.05bpp。

同一套编码器、只把调色板换成"45 项 cube、不加随机项"，照片的 PSNR 从 26.1 掉到 23.9。README 说 cube 是防溢出的必需品，从数据看它同时也贡献了相当一部分画质。

顺手做了个对照：经典 4bpp 调色板图（128 色均匀网格 + Floyd-Steinberg），在同样的渐变图上只有 18.0 dB，而 nibnib 的差分方案在 37.6 dB。差距不是调色板大小造成的，是差分把"绝对颜色"变成了"局部斜率"——渐变内容在斜率域里几乎是常数，一个码字能覆盖一大片区域。代价是硬边缘：锯齿对角线那张，nibnib 掉到 30 dB，而 128 色绝对调色板反而有 18.5 dB 的稳定表现（它不会因斜率失配而炸开）。这也是 README 承认的"锐边右侧拖尾"。

码字分布也印证了这一点。渐变图上 160×120 只用到 89 个不同码字，前 8 个占 40.5% 的像素；而锯齿图用到 166 个。也就是说实际内容对调色板的 256 项只消费了一小部分，这也是作者在"未来改进"里把"自适应调色板"列为第一条的原因——按图生成调色板，理论上能把这 4bpp 的信息密度再抬高不少。

视频：把 SD 卡的带宽卡进 7ms

vic-2350 的 sd_video.sy 把 nibnib 用于 60fps 视频播放，这才是真正吃紧的地方。

一帧 152.9KB，补到 306 个 512 字节块（156672 字节），3600 帧正好 60 秒，release 里那个 564MB 的 VIDEO.NIB 就是这么来的。按 60fps 算需要 9.4MB/s 的持续读速，这对 SPI 模式的 SD 卡不算高，但问题在于你不能卡在正在画的那一行上。

源码的处理：双帧槽，两个 DMA 通道（2 和 3）交替写入，每条连续簇跑一次 CMD18。流控手段很粗暴也很有效——直接停 SPI 主机状态机 SM0，CLK 一停卡就等着。允许流跑到正在显示的那一帧上去，但只到 MARGIN_BLOCKS = 80 块（40KB）的余量，留 RESUME_BLOCKS = 16 恢复。

注释里说每行轮询一次，约 32 微秒，正好一个块；垂直消隐那 1.4ms 不轮询，等于 48 个块的空窗。一次簇结束重新发 CMD12 + CMD18 花掉四分之一毫秒，60 秒里 3600 帧，每帧 7ms 余量够用。

我按源码里的时序参数算了一遍 640×480@60 的预算：

  • H_TOTAL = 640 + 16 + 96 + 48 = 800，像素时钟 25.2MHz → 行周期 31.75 微秒
  • V_TOTAL = 10 + 2 + 33 + 480 = 525 → 帧周期 16.67 毫秒，正好 60Hz
  • 有效行时间 15.24 毫秒，消隐 1.43 毫秒
  • 每帧要读 156672 字节 → 消隐期间以外必须跑满 10.3MB/s
  • CPU 侧：640×480×6 周期 = 184 万周期，144MHz 下 12.8 毫秒，占帧时间的 76.8%

两个 76%~84% 叠在一起。 每行 31.75 微秒里，解码要吃掉 26.7 微秒（84%），剩下 5 微秒留给 DMA 中断重装通道和 SD 流控。这不是"优化一下更好"，是刚好卡着不留余地，任何一次中断延迟过长都表现为一条红线或者一帧重复。

为什么这个设计现在还有意义

HN 上有两条批评说得对：这不算压缩，就是差分加调色板；也没有和 JPEG 的对比数据。后者完全成立，README 只给了周期预算，没给质量-码率曲线。我上面那张表补了一小块，但那是我的合成图和 Python 模型，不是作者实现。

另有两条说偏了，都在拿现代硬件标准评价。有人提 BCx 格式能调色板插值，那是给桌面 GPU 纹理压缩用的，假设你有几百 GB/s 带宽和专用解码单元，RP2350 上两样都没有。还有人提 Amiga HAM，这个倒是真像：HAM 的 6 位输入输出 12 位颜色，机制就是"每像素选一个通道做微调"。区别是 HAM 的调整线性（每次 1/16 量程），nibnib 的调整是 256 项查找表，而且一次管两个像素。这是把 HAM 的思路从 1985 年的位平面硬件搬到 32 位加法和查表上。

一个开发者的视角

这个东西对我的启发不在图像格式本身，在非对称编解码这个思路的适用范围。编码器比解码器慢 500 倍，而这个比值不花钱，因为编码在开发机上跑一次，解码在设备上跑每帧 60 次。只要你的数据是"写一次、读千万次"，就有一个可以无限加深的编码端。字体子集化、预计算路由表、烘焙光照贴图、序列化时排好序的索引，都是把搜索代价从运行时推到构建时。

想自己动手的话，我建议按这个顺序：

先测解码预算，再选格式。 别先看压缩率。RP2350 的 6 周期是 HSTX 和 DVI 时序逼出来的，换个 MCU 这个数就完全不同。main.sy 里那些 H_FRONT_PORCH = 16、H_SYNC_WIDTH = 96 是 DVI 标准的 640×480@60 时序。

先写解码器，再写编码器。 nibnib 的复杂度全在编码端搜索，格式是由解码器定义的。我复刻时先照 decode.rs 写出能解的版本，喂随机字节流看它吐什么，然后才动手写编码器。这个顺序能保证你不会写出"编得来解不出来"的码字。

验证边界值。 差分编码出问题永远在两端。我跑的那组 0x0000、0xffff、0x07e0、0xf800 是 RGB565 的黑、白、纯绿、纯红，四个角过一遍，省得后期对着满屏偏色找 bug。

能 32 位打包的话，算算进位要不要屏蔽。 nibnib 每次加法有一半概率出现半字间进位串扰，它选择不修，因为编码器复用了同一份算术。这省下的两条指令在 7 条预算里是 30%。前提是编解码两侧的取整、溢出、字节序逐位一致，前提不成立时这招就是毒药。

顺带说一句，作者在 HN 上被问"这些代码是不是 vibe-coded"，回答得挺坦白：两个项目都是手写起步，后来用 Claude 往前推，但他坚持自己写 prose。他不认为用 LLM 会让结果变差，只承认会让人怀疑，然后选择把这件事写清楚。

仓库在 github.com/raphlinus/nibnib。配套的 vic-2350 更有意思，那个"80 年代平行宇宙家用电脑"整个跑在 RP2350 上，视频输出、SD 卡、USB 主机、字体渲染全是手写汇编。如果你对 beam racing 这个消失了的技术方向好奇，main.sy 那 759 行比任何文章都讲得清楚。
