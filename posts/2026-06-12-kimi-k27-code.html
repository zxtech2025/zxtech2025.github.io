Kimi K2.7-Code：开源编程模型悄悄逼近了，token效率才是真正的杀手锏

2026-06-12
  • AI编程
  • 开源模型
  • LLM
  • 编程助手
  • MoE

今天 Moonshot 发布了 Kimi K2.7-Code，HN 上一小时就上了首页（102 points，41 comments）。看起来只是个常规的模型迭代——K2.6 → K2.7，作为开发者能有什么惊喜？但我读完模型卡之后发现，这次更新有一个被标题严重低估的点：token 效率。

K2.7-Code 相比 K2.6，thinking token 减少了约 30%。这个数字比任何 benchmark 分数都重要。为什么？因为在实际使用中，thinking token 就是钱，是延迟，是 agent 在循环里打转的时间。

架构没变，但训练方向变了

先过一遍基础参数。K2.7-Code 跟 K2.6 同架构：

  • MoE，总参数 1T，激活参数 32B，384 个专家每次选 8 个
  • 61 层（含 1 个 dense 层），MLA 注意力，SwiGLU 激活
  • 256K 上下文，MoonViT 视觉编码器（400M 参数）
  • 原生 INT4 量化

说白了，K2.7-Code 不是新架构，而是在 K2.6 基础上做了一轮 coding-agent 专项训练。重点是让模型在长周期编程任务中少绕弯路——这就是那 30% thinking token 缩减的来源。

Moonshot 管这叫 "token efficiency"，翻译成人话就是：以前 K2.6 在写代码前要自言自语半天，现在 K2.7 能更快地进入"写"的阶段。在 agent 场景里，这意味着更少的 API 调用次数、更低的费用、更短的等待时间。

Benchmark 深度解读：数字背后藏着什么

官方给出了三组对比数据：K2.6 → K2.7-Code → GPT-5.5 → Claude Opus 4.8。我不打算列全部（你去 HF 看完整表格），只挑最有信息量的几个：

Kimi Code Bench v2（自研基准）

模型 分数
Kimi K2.6 50.9
Kimi K2.7-Code 62.0
GPT-5.5 69.0
Claude Opus 4.8 67.4

K2.6 → K2.7 跳了 11.1 分，这是自研基准，有优化 bias 的可能。但即使打折扣，这个提升幅度说明专项训练确实有效。注意它跟 Opus 4.8（67.4）的差距已经缩小到 5.4 分——开源模型正在逼近顶级闭源模型。

Program Bench（客观第三方基准）

这个基准很有意思：给 agent 一个编译好的二进制和文档，不给源码、不能联网、不能用反编译器，让它从零实现一个行为完全一致的程序。200 个任务，从小 CLI 工具到 FFmpeg、SQLite 级别。评测用 24.8 万个 fuzz 生成的测试用例。

模型 分数
Kimi K2.6 48.3
Kimi K2.7-Code 53.6
GPT-5.5 69.1
Claude Opus 4.8 63.8

这里 GPT-5.5 优势明显（69.1），K2.7 跟 Opus 4.8 差了 10.2 分。这说明在极端困难任务上（从零重建一个程序的行为），顶级闭源模型仍有明显优势。但 K2.6 → K2.7 的 5.3 分提升是实打实的。

MCP Mark Verified（工具调用基准）

这是对真实 MCP 服务器环境的评测——Notion、GitHub、Filesystem、Postgres、Playwright——每个任务经过人工验证。

模型 分数
Kimi K2.6 72.8
Kimi K2.7-Code 81.1
GPT-5.5 92.9
Claude Opus 4.8 76.4

这个结果有点反直觉：K2.7-Code 在 MCP 工具调用上反超了 Opus 4.8（81.1 vs 76.4）。GPT-5.5 仍然大幅领先（92.9），但 K2.7 证明了一件事：开源模型在工具调用这个具体方向上，已经可以跟 Anthropic 掰手腕了。

30% token 缩减，到底省了什么

这是 K2.7-Code 最被低估的特性。我来算一笔账：

K2.6 的价格是 $0.7/$3.4 每百万 token（输入/输出）。假设一个典型的 coding agent 任务消费 20K thinking token + 10K 输出 token + 5K 输入 token，总费用大约： - K2.6：(5K × $0.7 + 30K × $3.4) / 1M ≈ $0.10 - K2.7（thinking 减少 30%）：（5K × $0.7 + 24K × $3.4）/ 1M ≈ $0.08

单次差 2 美分看起来不多。但 agent 场景下，一个稍微复杂的 PR 可能涉及 30-50 次工具调用，每个调用都是一轮完整的 LLM 交互。乘以 50，差 $1——一天下来，你的 API 账单能差出好几杯咖啡。

更关键的是延迟。thinking token 是串行生成的，减 30% 意味着你等模型"思考"的时间少了 30%。在交互式 coding 场景（Kimi Code CLI、OpenCode），这个感知差异非常明显。

再来看看跟 Anthropic 的价格对比。Opus 4.8 的 API 定价是 $5/$25 每百万 token，K2.6 是 $0.7/$3.4——输入便宜 7 倍，输出便宜 7 倍。这意味着同样的 coding agent 预算，Kimi 能跑的 token 量是 Opus 的 7 倍。如果你用 OpenCode 搭配 Kimi 跑一个完整的功能开发（假设消费 500K token），费用大约 $1-2；同样的任务用 Claude Code + Opus，直奔 $10-15。差距不是理论上的，是每月账单上的。

HN 社区怎么看

这次 HN 讨论的质量不低，摘几个有意思的观点：

一个用户提到他尝试从 Anthropic 迁移到开源模型的经历："我不断尝试切换到开源模型，但总是回到 Claude 去修它们的输出。功能和风格都不太行。我也试 GPT，它很快，调试很强，但代码有时过于聪明，看得脑仁疼。"

另一位用 GLM 5.1 的用户分享了在 Claude Code vs OpenCode 上的体验差异："GLM 5.1 在 Claude Code 里一直卡住，但在 OpenCode 里比 Sonnet 4.6 还强。我不太理解为什么——可能跟 oh-my-openagent 的规划系统有关。"

关于 Kimi 本身的槽点，有两条很精准："Kimi 的问题是不跟指令走，经常跑偏。修不该修的东西，因为它卡在了一个问题上就开始重构别的。"另一个用户接话："这听起来像是从 Claude 蒸馏来的副作用。我不理解一个不听话的 agent 有什么吸引力。"

但也有正面评价："我用 Claude 上班，Kimi 做 side project。我其实更喜欢 Kimi——看它推理的过程很像面试中白板讲解的感觉，它说 'wait' 的次数特别多，很搞笑。Claude 更像一个已经知道自己是正式员工的团队。"

preserve_thinking：一个被强制开启的特性

K2.7-Code 强制开启了 preserve_thinking 模式，且不能关闭。这个设计选择值得说两句。

什么是 preserve_thinking？正常 thinking 模型在多轮对话中，每一轮都重新生成 reasoning content，不会"记住"上一轮想了什么。preserve_thinking 会在 assistant message 里附加 reasoning_content 字段，下一轮 API 调用时模型能读取之前的推理链。

为什么强制？因为 coding agent 的多步任务天然需要这个。你用 Kimi Code CLI 改一个 bug，第一步定位问题、第二步写修复、第三步补测试——每一步的推理都建立在上一步的基础上。如果每次都要重新推理，token 节省那 30% 也不够挥霍的。

实际使用时，调用方需要在每次 assistant message 中把 reasoning_content 传回去。vLLM 部署的话注意，有些版本用 reasoning 而不是 reasoning_content，要看文档。

开源编程模型的竞争格局

把 K2.7-Code 放回当前的开源编程模型版图里看，格局大致是这样：

DeepSeek V4 Pro：性价比之王。HN 上有用户算了 OpenRouter 上的价格——DeepSeek 自己的 API 输入 $0.05/M、输出 $0.87/M，第三方托管输入 $0.33/M、输出 $1.52/M。虽然 coding 能力不如 K2.7，但便宜到离谱，适合大吞吐量的批量任务。

Qwen 3.6 / 3.7-Max：本地部署友好，RTX 5090 或 32GB+ 的 Mac 就能跑。有用户用 Qwen-3.7-Max 做设计和架构类任务，说"感觉最接近 Opus 3.6/3.7"。

GLM 5.1：在 Claude Code 里表现一般，但在 OpenCode 里明显更好——这是 agent 框架适配差异的典型案例。一个用户总结得很精辟："Claude Code 里它一直卡住，OpenCode 里居然比 Sonnet 4.6 还强一点。"

Kimi K2.7-Code 的定位：开源模型里 coding 能力最强的那一档，价格合理，原生 agent 优化好。短板是有用户反映"不跟指令走，经常偏题，修不该修的东西"——这可能是从 Claude 蒸馏带来的基因缺陷。

实际使用建议

如果你在考虑从 Anthropic 迁移到开源模型，这里是我基于 HN 讨论和自身体验整理的建议：

不要一刀切切换。区分任务类型：写样板代码、CRUD、格式化重构——用 Kimi/DeepSeek 完全够用；复杂调试、跨文件重构、架构设计——Claude/GPT 还是更可靠。一个 HN 用户说得很直白："Kimi coding 完了，Claude 还得修一遍。"

Agent 框架选择很重要。同一个模型在不同 agent 框架里表现差异巨大。K2.7 官方推荐 Kimi Code CLI，但 OpenCode、oh-my-openagent 等也有不错的适配。建议先用小任务在不同框架里测试，找到最适合你工作流的组合。

本地部署的门槛。K2.7-Code 的 1T 总参数看起来吓人，但激活参数只有 32B，加上原生 INT4 量化，在消费级硬件上并非不可能。不过实际部署建议走 vLLM 或 SGLang，transformers >= 4.57.1。KTransformers 也是一个选择，尤其在 CPU 推理场景。

API 接入。Moonshot 提供 OpenAI/Anthropic 兼容 API，platform.moonshot.ai。温度推荐 1.0，top_p 0.95，thinking 模式强制开启。

一个开发者的视角

K2.7-Code 让我最感兴趣的不是 benchmark 分数（说实话，自研基准看看就好），而是 30% token 效率提升这件事本身。

这说明 Moonshot 的训练团队在思考一个实际问题：不是"怎么让模型在理想条件下拿到更高的分数"，而是"怎么让模型在真实 coding agent 工作流中少浪费时间和钱"。这个优化方向是对的——现在 coding agent 最大的痛点是费用和延迟，而不是"模型不够聪明"。

回顾从 K2.5 到 K2.6 再到 K2.7 的演进，能看到一条清晰的路线：先做参数规模（K2.5），再做通用能力（K2.6），现在专项优化 coding agent（K2.7）。如果这个路线继续走下去，K2.8 可能会在更多 vertical 场景（安全审计？DevOps？数据处理？）上做专项优化。

对开发者来说，这意味着一个越来越现实的选项：用开源模型做主力 coding，只在关键节点调用闭源模型兜底。K2.7-Code 让这个选项离"够用"又近了一步。

不过也得承认一个现实：开源模型跟闭源顶级模型之间，确实还有一道"理解你意图"的鸿沟。一个 HN 用户说得好："Claude 更懂我想要什么，Kimi 更懂怎么写出能跑的代码。"这两个能力在 coding agent 场景里都很重要，但目前看来，前者比后者更难复现。token 效率提升解决的是成本问题，但"理解力"的问题可能得等下一轮训练范式的突破了。
