你点的那下"不再询问"，把生产库密码写进了仓库：Claude Code 权限规则泄密链拆解

2026-11-08
  • 安全
  • AI Agent
  • 开发工具
  • 密钥治理

npm run test 要点确认，psql 要点确认，curl 要点确认。一天两百下之后，手指比大脑快。

Claude Code 给的解法很贴心：Yes, and don't ask again。点一次，这个命令以后就不再问了。它把这条批准写进 .claude/settings.local.json，一条 allow 规则，永久生效。

问题在于，文件夹里存的不是"允许跑 npm test"这种抽象描述，而是你当时敲的那条完整命令行，包括里面的密码。

Apiiro 的研究团队扫了一遍 GitHub：1,122 个公开仓库里的 Claude Code 权限文件，藏着能直接用的凭证。1,105 个仓库有真密钥，其中 539 个的提交里有一个 Claude 联合署名的 commit。这篇文章把这套机制拆开，然后说清楚怎么查自己有没有中招。

规则文件里到底存了什么

先把机制讲准，因为网上很多讨论把它说偏了。

Claude Code 把批准写进 .claude/settings.local.json，官方文档在 Settings 页面写得很明确：当你对一个 Bash 命令选择"Yes, and don't ask again"时，这条批准会作为 allow 规则存进这个文件。

规则长这样：

{
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run test *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}

注意 Bash() 括号里是什么：是命令全文。文档说得很直白，Bash 规则匹配整个命令文本，* 代表任意文本。没有 * 的规则匹配一条完全相同的命令。

所以当你批准这条：

mysql -h db.internal -u root -pSuperSecret123 myapp < dump.sql

落盘的就是：

"Bash(mysql -h db.internal -u root -pSuperSecret123 myapp < dump.sql)"

密码现在是一个字符串字面量，躺在一个 JSON 文件里。这个文件叫 settings，不叫 credentials，git 不认为它敏感，secret scanner 的默认规则也未必覆盖它。

复合命令会拆开存

这里有个细节让泄漏面更大。文档说 Claude Code 识别 shell 操作符，&&、||、;、|、|&、& 和换行都算分隔符。你批准一个复合命令时，它给每个需要批准的子命令单独存一条规则，而不是存整条复合字符串。

文档举的例子是：批准 git status && npm test 会存一条 npm test 的规则，以后不管前面跟着什么，npm test 都认。

这意味着一次批准可能吐出多条规则。我按这个逻辑拆了一遍：

cd ./infra && aws s3 sync . s3://bucket --profile prod

拆成 Bash(cd ./infra) 和 Bash(aws s3 sync . s3://bucket --profile prod)。第二条把 profile 名留下了。如果那条命令是 --profile 之外还塞了 --access-key，那么 key 也在里面。

两个"看起来安全其实等于全开"的规则

真正让这个事故从"偶发失误"升级成"系统性风险"的，是 Bash(python:*) 这类解释器级规则。

我按文档描述的语义写了个匹配器验证了一遍，10 条用例全部和文档一致：

规则 命令 匹配 说明
Bash(ls *) ls -la ✅ 空格是规则的一部分
Bash(ls *) lsof -i ❌ 因为 ls 后面必须有空格，lsof 不算
Bash(ls*) lsof -i ✅ 没空格，lsof 也匹配
Bash(npm run test *) npm run test --watch ✅
Bash(npm run test *) npm publish --registry evil ❌ 前缀锁住了子命令
Bash(python:*) python any_script.py ✅

最后一行是坑。Bash(python:*) 等价于 Bash(python *)，意思是任意参数的 python 调用都放行。配上 Write(a.py)（写文件本来就在工作目录内默认允许），就等于可以执行任意代码。文档自己在警告里说得很清楚：Bash(python:*) 和 Bash(node:*) 这类解释器规则"在实践中与全放开基本等价"。

HN 上有人指出，那篇研究里 5% 的规则直接允许任意 shell 命令，另有 43% 是 Bash(python:*)、Bash(node:*) 这类解释器规则。也就是接近一半的规则文件，实际上没有起任何限制作用。

谁把它提交上去的

这是最有意思的部分，也是讨论里吵得最凶的。

Claude Code 团队的 Boris 在 HN 上亲自回复了，讲了三点：

  1. .claude/settings.local.json 本来就不该进版本控制。Claude 自己创建这个文件时会自动 gitignore，所以这次事件里那些文件是手工创建然后被提交的。
  2. 权限规则这套做法已经过时了，应该用 auto mode。
  3. 他们在研究加基础密钥扫描。

第 1 点是真的，文档也印证了：文件第一次被 Claude 写入时，它会把 **/.claude/settings.local.json 加到你的全局 git excludes。如果文件是你自己手写的，就得自己加 .gitignore。

但 Apiiro 的数据给了另一面：1,105 个有真密钥的仓库里，539 个的提交中包含 Claude 联合署名的 commit。也就是说，至少一半的泄漏不是"人手动提交"这么简单，Claude 参与了提交动作。

两件事都要成立。手写文件不加 ignore 是第一层失误；Claude 在后续会话里把工作目录的文件一起提交，是第二层。第二层尤其阴：你自己没提交，但 agent 帮你"顺手整理"时提交了。

还有第三层：私有仓库变公开。文档说这个文件的规则"在文件未被追踪时不等待 trust 检查"就生效。一旦它被追踪，就要走 workspace trust。这个设计与泄漏无关，但它解释了为什么这类文件在仓库里存在了很久也没人注意。

HN 上有个评论说得很准：文件在仓库里，不等于它现在公开。但一旦仓库转公开、或者 fork 出去、或者被 CI 拉进别的构建，它就公开了。而且即使是私有仓库，"公司里每个开发者都能拿到生产库密码"也不是你想要的状态。

自查：三条命令

别等出事再查。以下几件事现在就能做。

先找文件。find 会列出本机所有项目里的这个文件，git ls-files 只列被追踪的。后者才是关键：本地有没关系，只要没被追踪就不泄漏。

find . -path '*/.claude/settings.local.json' -not -path '*/node_modules/*' 2>/dev/null

# 只找被 git 追踪的（真正会进仓库的）
git ls-files | grep -E '\.claude/settings\.local\.json$'

接下来扫规则里的凭证形态。这个 grep 直接盯 allow 数组里的命令行：

grep -nE '"Bash\([^)]*(-p[^ )]+|--password[= ][^ )]+|Bearer [^ )]+|://[^/ :]+:[^@ )]+@)' \
  .claude/settings.local.json .claude/settings.json 2>/dev/null

命中的形态包括 -p密码、--password=xxx、Authorization: Bearer 后面跟令牌，以及 URL 里内嵌的 user:pass@host。

再揪出等于全开的规则：

grep -nE '"Bash\((python|node|bash|sh|zsh|perl|ruby):?\*?"' .claude/settings.local.json

这些规则本身不含密钥，但它们是放大器：一条泄漏的写文件权限加上一条 Bash(python:*)，攻击者就能在你的开发机上跑任意代码。

已经推到远端的怎么办？删文件不够。git rm 之后历史里还在，得用 git filter-repo 或 BFG 重写。而且先把密钥轮换掉：1,122 个文件挂在 GitHub 上，扫描机器人抓取速度是分钟级，重写历史追不回来。

我的处理方式

我自己是这么用的，三条：

权限文件不进项目目录。我把项目级的 .claude/settings.local.json 一律加到全局 excludes，靠 ~/.config/git/ignore 而不是逐个仓库 .gitignore，因为逐个加总会漏。Claude 自己创建时也会加，但手写的需要我自己管。

涉及凭证的命令永远不批准"不再询问"。一个经验法则：命令行里出现 -p、token、Bearer、://user:pass@ 这四种形态中的任何一种，只点"Yes"（单次），绝不点"don't ask again"。这个判断不需要想，看到就单次。

Bash(python:*)、Bash(node:*) 这类规则我全删了。它们给的安全感是假的，实际权限比看起来大得多。要跑脚本就批准具体那个脚本：Bash(python scripts/build.py)，而不是整个解释器。

还有一件事值得做：把上面那三条 grep 写进 CI。pre-commit hook 跑一遍，命中就拦。密钥泄漏这件事，人靠不住。一天两百次确认之后，手指比脑子快，这是生理问题不是纪律问题。
