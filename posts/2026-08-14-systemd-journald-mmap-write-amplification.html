一行日志写掉 110KB：systemd-journald 的 mmap 写放大解剖

2026-08-14
  • Linux
  • systemd
  • 文件系统
  • 性能分析

八月十四号 Hacker News 上有个帖子很扎眼：《Single log line is 49KB+ (ext4) / 110KB+ (btrfs) of systemd-journald disk writes》。来源是 systemd 仓库的 issue #40262，标题更朴素——"Excessive IO caused by systemd-journald"，2026 年 1 月 3 日开的，到现在 24 条评论还没关。

问题本身不新鲜。报 issue 的人在一台 VM 上每秒写两行日志，磁盘看到大约 50 IOPS。系统是 Debian 13、systemd 257.9、内核 6.12.57、XFS。他在 issue 里把同样的抱怨指向了 2020 年就被关掉的 #15292，那次维护者的结论是"iotop 不准，是内核把 IO 放大了"。这次他把内核这一层也测了，结论反过来了：不是量测工具的问题，是慢。

先复现，再谈责任

这种"到底谁在写盘"的争议，靠感觉吵架没有意义。评论里 ValdikSS 给了一套可复现的方法，值得抄下来：

  • 在 tmpfs 上建一个 ext4 loop 设备，专门挂到 /var/log/journal
  • 同时采集 /sys/block/loop0/stat 的第 7 个字段（写扇区数）和 journald cgroup 的 io.stat
  • journald 侧配 Compress=no、SyncIntervalSec=10s，systemd 侧开 DefaultIOAccounting=yes
  • 挑一台"绝对安静"的机器，保证除了测试注入的那条日志没有别的来源

然后注入一条 logger -p info test，观察增量。他贴出来的原始数据是这样：

21:40:42: Started with 8482816 bytes loop0, 442368 bytes journald cgroup
21:41:38: loop0: 8556544 bytes (+73728) | cgroup: 479232 bytes (+36864)
21:41:48: loop0: 8765440 bytes (+208896) | cgroup: 552960 bytes (+73728)
21:42:09: loop0: 8904704 bytes (+139264) | cgroup: 552960 bytes (+0)

一条几十字节的日志，块设备层面先 +72KB，后续周期又追加了两百多 KB。这不是计量误差，/sys/block/*/stat 是块层统计，任何用户态工具都改不了它。

顺带排除了一个常见误解：SyncIntervalSec 并不控制数据落盘的时间，它只控制 fdatasync/fsync 叫用的时机。journald 收到日志就立刻往持久文件里写，只是把 fsync 推迟了。想靠调大它来省 IO 的人可以放弃了。

根因一：mmap 写入撞上 large folio

journald 追加 .journal 文件用的是 mmap，不是 pwrite。这个选择在 2011 年可能是为了省一次拷贝，现在的代价是：mmap 的写缺页（write fault）会把整页标记为 dirty，而内核启用 large folio 之后，folio 可能是 16KB、64KB 甚至更大。一条 100 字节的日志把整个 folio 弄脏，写回时整块落到盘上。

这个放大倍数能解释为什么不同文件系统差这么多：ext4 上的观测是 49KB+，btrfs 上 110KB+，CoW 文件系统还要额外承担写时复制的代价。有人贴了 bcachefs 作者在 Reddit 上的说法，大意是"large folio 落地之后每个文件系统都被 mmap 写坑了"，并建议在这些场景下关掉 folio。

有意思的是两个方向完全不同的修复意见同时出现在这个 issue 里：

  • 内核侧。willy613 提交了一个 iomap 补丁，做的是"只弄脏具体那一页，而不是整个 folio"，覆盖 xfs、exfat、ntfs、zonefs。他自述能开机，但还没跑完 fstests；amluto 建议试试直接用硬件 dirty bit 优化。这个补丁到八月底还没进 mainline。
  • 应用侧。amluto 讲了他自己的经历：很多年前他做过一个用 mmap 追加写的数据库，踩了一堆坑，为此跑 LSF/MM 跟人对线，最后还写了补丁让 mmap 写别那么难受（至今没被合）。他的结论很硬——设计本身错了，应该用 pwrite。他还指出 Linux 上 MAP_SHARED 和普通 IO 是缓存一致的，journald 完全可以保留 mmap 映射、只把写改成 pwrite，改动不会很大。

根因二：磁盘格式自己就很浪费

就算 mmap 那边修好了，格式的问题还在，而且先被用户看见。issue 里有个人用 iotop -a 的累计模式量了一下，15 分钟 journald 写了将近 7GB，22 分钟接近 11GB，机器在那段时间里 IO 顶满、明显卡顿。一条日志的净荷是几十字节，剩下的全是元数据。

打开 journalctl -o verbose 看一眼就知道钱花在哪了。你注入的那一行字，journald 会附上一整套隐式字段：_BOOT_ID、_MACHINE_ID、_HOSTNAME、_PID、_COMM、_EXE、_CMDLINE、_SYSTEMD_CGROUP、_SYSTEMD_UNIT、_TRANSPORT、_SOURCE_REALTIME_TIMESTAMP，随手就是十来个。每个 entry 对象带 64 字节头部，后面紧跟一串指向字段数据对象的偏移，字段值本身在同一文件里做过去重（同样的 _BOOT_ID 只存一份），但每条 entry 都要把这十几个引用重写一遍，加上时间戳序列和 xor 校验。短日志行的净荷占比因此低得可怜。

这也解释了为什么格式换成 SQLite 或按列去重的日志存储会被反复提议：现在这个布局，写入贵、读取也贵——查找也没有为最常见的"按服务和时间段翻日志"做合理索引。issue 里维护者 XANi 的总结很直白：格式为了多数用户根本不在乎的目标膨胀，反而没命中用户真正在意的两点，快速查找和可接受的写性能。

代价是抗损坏性和密封性下降，权衡是真实的，但"现在的格式浪费"基本是共识。

Compress=no 这个测试配置也暴露了一个细节：短日志行根本触发不了压缩，所以关不关压缩在短行场景下没差别。

能立刻做的事情

我不会等内核补丁。手上有几台跑 journald 的机器，按代价从低到高做了这几件事。

第一，不需要重启后保留日志的机器直接 Storage=volatile。日志进 /run，走 tmpfs，零持久写。这一条几乎解决了所有日常开发机的写放大。

第二，设上限，别让日志无边界膨胀：

# /etc/systemd/journald.conf
[Journal]
Storage=persistent
SystemMaxUse=512M
SystemMaxFileSize=64M
RuntimeMaxUse=128M
RateLimitIntervalSec=30s
RateLimitBurst=1000

第三，观测手段要对。iotop -a 用累计模式看，别用瞬时值；要看块设备真实写入就差分 /sys/block/<dev>/stat 第 7 字段；journalctl --disk-usage 看总量；systemd-cgtop 看是哪个单元在贡献。

第四，如果 /var/log/journal 在 btrfs 上且不需要 CoW，chattr +C 能省掉一层复制。ext4 上 lazytime 有意义，但 atime 本身不是这个 bug 的主因——大多数日志文件都是最近访问过的，relatime 已经处理了。

最后一点经验：SSD 寿命被日志写没这件事，在这个 issue 里被好几个人当成段子讲，但它不全是段子。一台每秒两条日志的机器，按 100KB 的放大系数算，一天就是十几 GB 的写入量，对消费级 SSD 的 TBW 是实打实的消耗。如果你看到 SSD 的 Wear Leveling 计数掉得比预期快，先确认一下 journald 是不是元凶，方法就是上面那个 loop 设备差分。

一行日志要写 110KB 才能落盘，这个数字本身已经足够说明问题：该由格式和写入路径负责的事，不该让文件系统和闪存来扛。
