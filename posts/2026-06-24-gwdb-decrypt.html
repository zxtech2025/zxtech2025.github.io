GWDB 加密数据库逆向分析实战：从二进制到数据恢复

本文记录了一次完整的加密数据库逆向分析过程，从二进制文件分析到算法识别、密钥提取，最终实现数据全量恢复。内容仅供安全技术研究学习，请勿用于非法用途。

一、背景

最近在研究一款办公辅助软件的数据库格式时，遇到一个 .gwdb 后缀的文件，约 68MB。标准工具完全无法读取——file 命令只返回 data，hexdump 看到的是彻底的"乱码"：

$ file target.gwdb
target.gwdb: data

$ hexdump -C target.gwdb | head -6

字节分布均匀，没有可识别的 ASCII 字符串，没有 Magic Number——这是经过加密的典型特征。

二、文件级侦察：寻找结构性线索

虽然数据是乱码，但文件本身的结构信息不可伪造。我们先做几个基础测量。

2.1 文件大小分析

$ stat target.gwdb
  大小：68231168
$ python3 -c "print(68231168 % 4096, 68231168 / 4096)"
0 16658.0

68,231,168 ÷ 4,096 = 16,658，余数为 0。

4096 是 SQLite 默认页面大小。文件恰好对齐到页面大小的整数倍，强烈暗示这是逐页加密（page-by-page encryption） 模式。如果是整体加密（如 OpenSSL 对整个文件做一次 AES），文件大小不会恰好是页面大小的整数倍。只有加密引擎逐页处理时，才会输出对齐的数据。

2.2 字节分布检验

$ python3 -c "

# 按 4096 块计算字节分布

    page = data[page_num*4096:(page_num+1)*4096]

每个页面中字节值分布均匀，最高频字节出现仅 20~25 次（4096 字节中），接近随机分布。这说明：

  1. 确实是加密数据——明文 SQLite 页面中有大量 0x00 填充字节，分布会极度偏斜
  2. 流密码的可能性大于块密码——块密码（AES-CBC 等）输出的字节分布通常更均匀，但流密码 XOR 后的统计特征与此吻合

2.3 跨页相关性检测

$ python3 -c "
data = open('target.gwdb','rb').read()
page0 = data[0:4096]
page1 = data[4096:8192]
# XOR 两页，看是否有模式
xor_result = bytes(a ^ b for a, b in zip(page0, page1))
# 统计 XOR 结果的分布
c = Counter(xor_result)
print('XOR 后分布:', c.most_common(5))
# 如果两页用相同密钥流加密，XOR 后会抵消密钥，露出明文差异
"
XOR 后分布: [(137, 24), (242, 22), (55, 21), (198, 21), (13, 20)]

XOR 后仍是均匀分布——每页使用了不同的密钥流。这排除了所有页面共享同一 RC4 密钥流（即整体加密）的可能性。初步判断：每页独立加密，密钥来自同一密码派生，但 RC4 状态每页重置。

三、程序逆向：锁定加密方案

文件本身的信息就到这了，下一步只能分析程序本身。

3.1 .NET 程序集分析

程序主文件是 .NET Framework 编译的可执行文件。.NET 的反编译门槛极低——ILSpy、dnSpy、dotPeek 等工具都能直接还原出接近源码的 C# 代码。

GongWenManager.exe

├── GongWenManager.Core.dll     # 业务逻辑
├── System.Data.SQLite.dll      # 数据库接口 (大小异常！)

关键线索在 System.Data.SQLite.dll——这个文件比 NuGet 上标准版的 System.Data.SQLite.dll 大很多。标准版约 900KB，而这个版本接近 2.3MB。这是因为集成了 SEE (SQLite Encryption Extension) 组件。SEE 是 SQLite 官方提供的商业加密扩展，以静态链接方式嵌入到 System.Data.SQLite 中。

3.3 静态分析确认调用关系

通过 ILSpy 反编译 GongWenManager.Core.dll，追踪数据库连接代码：

// 反编译结果 (伪代码)
internal class DatabaseManager
{
    private static string password = "[REDACTED_PASSWORD]";

    public static SQLiteConnection OpenDatabase(string dbPath)
    {
        var conn = new SQLiteConnection($"Data Source={dbPath};UTF8Encoding=True;");
        conn.SetPassword(password);  // 关键调用！
        conn.Open();
        return conn;
    }
}

SetPassword 是 System.Data.SQLite 中激活 SEE 加密的入口点。它会使用密码对数据库进行 SEE 加密。调用 SetPassword 后打开的数据库连接，后续的所有读写操作都会自动加解密。

重要发现：密码是硬编码在代码中的，且对所有用户、所有数据库文件统一。这意味着只要拿到这个密码，任何 .gwdb 文件都能解密。

3.4 加密方案最终确认

综合文件分析和程序逆向，可以锁定：

加密方案: SEE (SQLite Encryption Extension)
算法:     RC4 流密码
密钥派生: SHA1(password) → 取前 16 字节
页面大小: 4096 字节
加密模式: 逐页独立加密 (每页新建 RC4 cipher)

为什么确定是 RC4 而非 AES？因为 SEE 虽然同时支持 RC4 和 AES，但 System.Data.SQLite 内置的 SEE 版本默认使用 RC4（因其无需额外的 AES 指令集支持，兼容性更好）。AES 变体需要有单独的 SEE 许可证编译，而我们从 DLL 的特征确认这是 RC4 变体。

四、解密实现：从理论到代码

4.1 RC4 算法回顾

RC4 是 Ron Rivest 在 1987 年设计的流密码，核心由两部分组成：

KSA (Key Scheduling Algorithm)：用密钥初始化 S-box

S[0..255] = [0, 1, ..., 255]
j = 0
for i in 0..255:
    j = (j + S[i] + K[i mod keylen]) mod 256
    swap(S[i], S[j])

PRGA (Pseudo-Random Generation Algorithm)：生成密钥流

i = j = 0
loop:
    i = (i + 1) mod 256
    j = (j + S[i]) mod 256
    swap(S[i], S[j])
    K = S[(S[i] + S[j]) mod 256]  ← 输出密钥字节

加密时，明文与密钥流 XOR：Ciphertext = Plaintext XOR Keystream

关键特性：RC4 是对称流密码，加解密使用同一操作。最重要的是，每次新建 RC4 实例都会从 KSA 重新开始，产生相同的密钥流。

4.2 密钥派生

SEE 的密钥派生过程非常简单：

import hashlib

password = "[REDACTED_PASSWORD]"

# Step 1: SHA1 哈希，输出 20 字节
sha1_digest = hashlib.sha1(password.encode('utf-8')).digest()
print(sha1_digest.hex())
# → [SHA1_DIGEST_REDACTED]

# Step 2: 取前 16 字节作为 RC4 密钥
rc4_key = sha1_digest[:16]
print(rc4_key.hex())
# → [RC4_KEY_HEX_REDACTED]
print(len(rc4_key))  # → 16

# 就这么简单。没有盐值，没有迭代拉伸，没有 HMAC。

安全分析：这种密钥派生方式有严重缺陷：

  1. 无盐值（No Salt）：相同密码永远产生相同密钥，彩虹表可以直接命中
  2. 单轮 SHA1：没有使用 PBKDF2/bcrypt/scrypt 等拉伸算法，暴力破解速度可达每秒数亿次
  3. 16 字节密钥：128 位密钥空间在现代 GPU 面前并不安全

4.3 逐页解密——最容易踩的坑

SEE 的页面加密模式是这样的：

Page 0:  E0 = RC4(key, P0)     ← 新建 RC4，生成密钥流 0
Page 1:  E1 = RC4(key, P1)     ← 新建 RC4，生成密钥流 1（和 0 相同！）
Page 2:  E2 = RC4(key, P2)     ← 新建 RC4，生成密钥流 2（和 0 相同！）
...

等等——每页独立 RC4 意味着每页的密钥流完全相同！这看起来是安全缺陷，但考虑到：

  • SQLite 页面头中有随机性（如行数据分布不同）
  • 攻击者不知道具体的明文内容
  • 同密钥流加密不同数据，理论上可以 XOR 两页密文消除密钥：C1 XOR C2 = P1 XOR P2，但这需要攻击者已知 P1 或 P2 中的至少一个

SEE 的设计者显然认为这足够了（虽然密码学上并不理想）。

解密时最关键的一点：每页必须新建 RC4 实例。错误示范：

# ❌ 错误：跨页复用 RC4 实例
cipher = ARC4.new(key)
for i in range(num_pages):
    page = data[i * 4096:(i + 1) * 4096]
    decrypted.extend(cipher.decrypt(page))  # 状态持续累积！

# 结果：第一页正确（因为起始状态相同），从第二页开始全部错误

因为 RC4 是状态维护的流密码——PRGA 的 i、j 指针会随着输出而移动。如果跨页复用，第一页输出后 i/j 已改变，第二页的密钥流与加密时的密钥流对不上，解密全部错位。

正确做法：

# ✅ 正确：每页新建 RC4
for i in range(num_pages):
    page = data[i * 4096:(i + 1) * 4096]
    cipher = ARC4.new(key)  # 每页重新初始化！
    decrypted.extend(cipher.decrypt(page))

这个细节排查了很久——第一页正确让人误以为整个方案正确，结果后面的数据全是乱码，一度怀疑密钥错了。

4.4 完整解密代码

#!/usr/bin/env python3
"""
GWDB 数据库解密工具
加密方式: SEE (SQLite Encryption Extension)
算法: RC4, 密钥 = SHA1(password)[:16], 页大小 4096
用法: python3 decrypt_gwdb.py <加密文件.gwdb> [输出.db] [密码]
"""
import hashlib, sys
from Crypto.Cipher import ARC4

PAGE_SIZE = 4096
EXPECTED_MAGIC = b'SQLite format 3\x00'  # SQLite 魔数
DEFAULT_PASSWORD = "[REDACTED_PASSWORD]" # 从程序集提取

def derive_key(password: str) -> bytes:
    """SEE 密钥派生：SHA1(password) → 前 16 字节"""
    return hashlib.sha1(password.encode('utf-8')).digest()[:16]

def decrypt_page(page: bytes, key: bytes) -> bytearray:
    """解密单个 4096 字节页面"""
    assert len(page) == PAGE_SIZE, f"页面大小必须为 {PAGE_SIZE}"
    cipher = ARC4.new(key)
    return bytearray(cipher.decrypt(page))

def verify_sqlite_header(data: bytearray) -> bool:
    """验证解密后的 SQLite 文件头"""
    return data[:16] == EXPECTED_MAGIC

def decrypt_gwdb(input_path: str, output_path: str, password: str = DEFAULT_PASSWORD) -> int:
    print(f"[*] 读取加密文件: {input_path}")
    with open(input_path, 'rb') as f:
        encrypted_data = f.read()

    file_size = len(encrypted_data)
    num_pages = file_size // PAGE_SIZE

    if file_size % PAGE_SIZE != 0:
        print(f"[!] 警告：文件大小 ({file_size}) 不是页面大小 ({PAGE_SIZE}) 的整数倍")

    print(f"[*] 派生密钥 (SHA1 + RC4)")
    key = derive_key(password)
    print(f"    密钥 (hex): {key.hex()}")

    print(f"[*] 逐页解密中... ({num_pages} 页)")
    decrypted = bytearray()

    for i in range(num_pages):
        start = i * PAGE_SIZE
        end = start + PAGE_SIZE
        page = encrypted_data[start:end]
        decrypted_page = decrypt_page(page, key)
        decrypted.extend(decrypted_page)

        # 打印进度
        if (i + 1) % 1000 == 0:
            pct = (i + 1) / num_pages * 100
            print(f"    进度: {i+1}/{num_pages} ({pct:.1f}%)")

    print(f"[*] 验证 SQLite 文件头...")
    if not verify_sqlite_header(decrypted):
        raise ValueError("解密失败！密码错误或文件格式不匹配")

    # 额外校验：检查第 100 页是否有 0x00 大量出现（SQLite 空闲页的典型特征）
    sample_page = bytes(decrypted[100 * PAGE_SIZE : 101 * PAGE_SIZE])
    zero_count = sample_page.count(0x00)
    print(f"[*] 校验页 #100 零字节比例: {zero_count}/{PAGE_SIZE} ({zero_count/PAGE_SIZE*100:.1f}%)")
    # 正常 SQLite 页面通常有 5-30% 的零字节（填充和空闲区域）
    if zero_count < 50:
        print("[!] 警告：零字节比例异常，可能解密不完全正确")

    print(f"[*] 写入解密文件: {output_path}")
    with open(output_path, 'wb') as f:
        f.write(decrypted)

    result_size = len(decrypted)
    print(f"[✓] 解密成功！{file_size/1024/1024:.1f} MB → {result_size/1024/1024:.1f} MB")
    return result_size

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("用法: python3 decrypt_gwdb.py <输入.gwdb> [输出.db] [密码]")
        print("默认密码: " + DEFAULT_PASSWORD)
        sys.exit(1)

    input_path = sys.argv[1]
    output_path = sys.argv[2] if len(sys.argv) > 2 else input_path.replace('.gwdb', '_decrypted.db')
    password = sys.argv[3] if len(sys.argv) > 3 else DEFAULT_PASSWORD

    try:
        decrypt_gwdb(input_path, output_path, password)
    except Exception as e:
        print(f"[✗] 解密失败: {e}")
        sys.exit(1)

六、批量数据导出设计

6.2 全量 JSON 导出

最直接的方式是导出为结构化的 JSON，保留所有字段和关系：

#!/usr/bin/env python3
import sqlite3, json

DB_PATH = 'decrypted.db'
OUTPUT_PATH = 'export.json'

conn = sqlite3.connect(DB_PATH)
conn.row_factory = sqlite3.Row
cursor = conn.cursor()

# 统计信息
cursor.execute("""
    SELECT
        COUNT(*) AS total,
        SUM(CASE WHEN Type=1 THEN 1 ELSE 0 END) AS outline_count,
        SUM(CASE WHEN Type=2 THEN 1 ELSE 0 END) AS sentence_count,
        SUM(CASE WHEN Type=3 THEN 1 ELSE 0 END) AS structure_count,
        SUM(CASE WHEN Type=4 THEN 1 ELSE 0 END) AS collocation_count,
        SUM(CASE WHEN Type=5 THEN 1 ELSE 0 END) AS article_count
    FROM GongWenUnits
""")
stats = dict(cursor.fetchone())

# 导出所有素材
cursor.execute("""
    SELECT UID, Type, Text1, Text2, Tags
    FROM GongWenUnits
    ORDER BY UID
""")

items = []
for row in cursor.fetchall():
    items.append({
        "uid": row["UID"],
        "type": {1: "提纲", 2: "词句", 3: "句式", 4: "词汇搭配", 5: "全文"}[row["Type"]],
        "content": row["Text1"],
        "supplement": row["Text2"],
        "tags": row["Tags"].split("；") if row["Tags"] else []
    })

output = {
    "metadata": {
        "export_time": "2026-06-24",
        "total_count": stats["total"],
    },

6.3 Markdown 导出——分层渲染

按标签分类导出时，需要处理标签的层级关系。数据库中 AllTags 表记录了 ParentTag 字段：

导出算法：

def export_by_tag(cursor, output_dir):
    """按父标签分组导出为 Markdown"""

    # Step 1: 获取所有父标签
    cursor.execute("""
        SELECT ParentTag, COUNT(*) as cnt
        FROM AllTags
        WHERE ParentTag != ''
        GROUP BY ParentTag
        ORDER BY cnt DESC
    """)
    parent_tags = cursor.fetchall()

    for parent in parent_tags:
        parent_name = parent["ParentTag"]

        # Step 2: 获取该父标签下的所有子标签
        cursor.execute(
            "SELECT Name FROM AllTags WHERE ParentTag = ?",
            (parent_name,)
        )
        child_tags = [r["Name"] for r in cursor.fetchall()]

        # Step 3: 收集匹配的素材（用 LIKE 匹配标签）
        all_items = []
        for tag_name in child_tags:
            cursor.execute("""
                SELECT UID, Type, Text1, Text2, Tags
                FROM GongWenUnits
                WHERE Tags LIKE ?
                ORDER BY Type, UID
            """, (f"%{tag_name}%",))
            all_items.extend(cursor.fetchall())

        # Step 4: 去重（同一条素材可能匹配多个子标签）
        seen = set()
        unique_items = []
        for item in all_items:
            if item["UID"] not in seen:
                seen.add(item["UID"])
                unique_items.append(item)

        # Step 5: 写入 Markdown
        md_path = os.path.join(output_dir, f"{parent_name}.md")
        with open(md_path, 'w', encoding='utf-8') as f:
            f.write(f"# {parent_name}\n\n")
            f.write(f"共 {len(unique_items)} 条素材\n\n---\n\n")

            for item in sorted(unique_items, key=lambda x: x["Type"]):
                type_name = {1:"提纲",2:"词句",3:"句式",4:"词汇搭配",5:"全文"}[item["Type"]]
                f.write(f"## [{type_name}] {item['Text1'][:80]}\n\n")
                f.write(f"{item['Text1']}\n\n")
                if item["Text2"]:
                    f.write(f"> **补充：** {item['Text2']}\n\n")
                if item["Tags"]:
                    f.write(f"`{item['Tags']}`\n\n")
                f.write("---\n\n")

6.4 Word 导出

Word 导出使用了 python-docx 库，需要手动设置中文字体：

from docx import Document
from docx.shared import Pt, Inches, RGBColor
from docx.enum.text import WD_ALIGN_PARAGRAPH

def create_document(title):
    doc = Document()

    # 设置默认字体为仿宋（公文标准字体）
    style = doc.styles['Normal']
    font = style.font
    font.name = '仿宋'
    font.size = Pt(12)

    # 设置标题字体为黑体
    for level in range(1, 4):
        heading = doc.styles[f'Heading {level}']
        heading.font.name = '黑体'
        heading.font.color.rgb = RGBColor(0, 0, 0)

    # 添加标题
    doc.add_heading(title, 0)
    return doc

8.2 SEE 加密安全评分

维度 评分 说明
算法选择 ⚠️ RC4 已淘汰，有已知弱点
密钥派生 ❌ 无盐值，SHA1 单轮
完整性保护 ❌ 无 HMAC，可被篡改
密钥存储 ❌ 硬编码在客户端
抗暴力破解 ❌ 每秒可尝试数亿次
透明度 ⚠️ 闭源商业方案，审计困难

总体评价：SEE 提供的与其说是"安全加密"，不如说是"格式混淆"——它能阻止普通用户直接读取数据库，但对于有一定逆向能力的分析者来说，防护几乎为零。

8.3 实践要点

  1. 文件对齐是加密模式的路标——文件大小恰好是某数值的整数倍，大概率是指示页面/块大小
  2. 客户端密码不是秘密——只要程序能自动加解密，该密码一定存在于进程可触及的某处
  3. RC4 跨页加密的陷阱——每页独立的 RC4 意味着密钥流重复，但解密时必须每页新建 cipher 实例
  4. SQLite 魔数是解密成功的黄金标准——看到 SQLite format 3 才算真正成功
