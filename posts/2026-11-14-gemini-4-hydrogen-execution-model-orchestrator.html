Gemini 4 Hydrogen 拆解：便宜模型当执行引擎，贵模型只在纠结时上线

2026-11-14
  • AI工程
  • 模型架构
  • Agent
  • 基准测试
  • 推理成本

11 月 12 日 Google 放出了 Gemini 4 Hydrogen。发布会本身没什么好写的，真正值得看的是它背后那个工程判断：推理模型不该从头用到尾。

Hydrogen 不是新的旗舰。旗舰是 Carbon 和 Argon，论文级难题归它们。Hydrogen 是从 Carbon 派生出来的执行版，定位一句话：跑得快、听话、便宜，擅长把已经想清楚的事情做完。这个分工在模型卡里写得很直白——"adapted from Gemini 4 Carbon"，架构、训练数据、硬件全部继承，只在后训练阶段做了偏移。

配套放出的 Orchestrator 才是重点：它在同一个 session 里动态切换 Carbon 和 Hydrogen。Carbon 先只读探索、理清依赖、出计划；Hydrogen 接着改代码、装包、跑测试；Hydrogen 卡住了再交还 Carbon 重新规划。在 Terminal-Bench 4.1 上，这套切换拿到了接近纯 Carbon 的成功率，同时省 24% 配额、快 19%。

如果你还在用"一个静态路由器猜任务难度"的做法，这篇值得往下看，因为静态路由的失效点正是动态切换的立足点。

一、静态路由为什么必然失效

行业里常见做法是给 agent 配一个 model router：拿到第一条 prompt，判断难度，整个任务交给"够用的最便宜模型"。问题在于任务难度不是常量。

一个改依赖版本的任务，前 40% 是读 lockfile、追传递依赖、判断有没有 breaking change，这段比写代码难得多。中间 30% 只是批量替换 import 语句。最后 30% 跑测试、看 fail、改断言，又变回需要判断力的活。静态路由器在第一秒就把整条轨迹锁死在某个模型上，任何一个阶段的误判都会让后面全部陪跑。

Orchestrator 的做法是不预测，而是根据轨迹当前状态决定谁来干。Carbon 出计划时带"显式重规划触发器"（explicit re-planning triggers），Hydrogen 撞到触发器就交还。这个设计比路由器多花一次模型调用的开销，换来的是不会在错误难度假设上一路走到黑。

我自己的体感是：这类切换在长任务上收益最大，在短任务上纯属开销。改三行代码的活儿，来回切换的握手成本比省下的 token 还贵。所以它默认开着但也留了直接选 Hydrogen 的入口。官方也说了，一个 session 内做日常功能开发和调试，全跑前沿模型配多 agent，只会拖慢你的循环并烧掉前沿配额。

二、四个思考档位，一条平滑的性价比曲线

Hydrogen 分 low、medium、high（默认）、xhigh 四档。这不是新鲜设计，但这次官方把档位和分数的对应关系说清楚了：

  • 默认 high 档在 Artificial Analysis Intelligence Index 上拿 51，超过 Argon 的 50
  • xhigh 档拉到 54

一个执行模型在默认档位上超过自家旗舰，说明后训练阶段的取舍做得很明确：不是把能力砍掉，而是把"想得久"换成"想得准"。

定价是这次最干脆的一处：整个 100 万 token 上下文窗口内统一价，输入 $1.50/百万 token，输出 $7.50/百万 token。没有按长度分段的阶梯价。长上下文场景下这一点比单价本身重要。很多模型标价便宜，但超过 200K 之后价格翻倍，塞一个中型仓库进去算下来反而更贵。

Artificial Analysis 的独立测量补上了官方不会说的部分：

指标 Hydrogen (xhigh) 同类中位数
Intelligence Index 54 41
每任务耗时 14.8 分钟 13.1 分钟
输出 token 总量 304M 77.3M
每任务评测成本 $3.16 —
缓存折扣 95% —
输出速度 174 tok/s —

两个数字要单独拎出来。输出 token 是同类中位数的近 4 倍（304M 对 77.3M），官方在限制条款里也承认了"在某些情况下会用更多 token 换性能，高思考档尤其明显"。便宜单价遇上四倍啰嗦，实际账单可能和中价模型持平。另一个是首 token 延迟 43.34 秒，在 79 个模型里排第 49——这不是个交互式模型，它是批处理引擎。把它放在需要即时响应的位置上会很难受。

95% 的缓存折扣才是把账算平的关键。agent 场景里前缀高度重复（系统提示、工具定义、仓库上下文反复出现），缓存命中率高，实际有效输入成本远低于 $1.50。这也是为什么执行模型必须便宜：它被调用得最频繁，且每次调用的输入里大部分是重复内容。

三、基准表：赢的地方很具体，输的地方也很具体

模型卡里给了三方对比，直接抄下来看（Hydrogen / Claude Sonnet 5.5 / GPT-6.1 Terra）：

SWE-sweep 的 13.5% 对 3.1% 是最刺眼的一行。这个基准考的是"发现并修 bug 但不破坏既有代码"，不重写整个文件、只做外科手术式改动。这恰好是执行模型的看家本领，也是日常开发最常遇到的情形。Vending-Bench 2 更有意思，它让模型经营自动售货机，比最终银行余额，氢拿到 $14,549，比两个竞品都高，考的是多轮决策下的稳健性而不是单点能力。

输的两行同样明确：Terminal-Bench 4.1 输给 Sonnet 5.5（57.0% vs 63.9%），OSWorld-2.1 也输（77.6% vs 83.9%）。前一个是终端任务规划，后一个是 GUI 操作，两项都吃长期规划和视觉定位。这也印证了它的定位——Hydrogen 是执行者，不是规划者。这两个分数不必避讳，反而是选型时最有用的信息：如果你的场景以 GUI 自动化为主，Hydrogen 不是最优解。

注意 Terminal-Bench 4.1 那行有"Cheating-adjusted"标注。这类 agent 基准里模型可能靠读测试文件猜答案，做了作弊校正后的分数才可比。看任何 agent 基准都该先确认有没有这一列。

四、调用层面的实际变化

官方给的开发侧收益比跑分更实在，因为都是可观测指标：

  • 相比 3.8 Flash，high 档任务完成速度快 2.5 倍
  • Terminal-Bench 4.1 从 18.2% 涨到 57%，超过三倍
  • 编造性陈述减少 5 倍以上
  • 复杂图结构、SQL、数据密集的企业流程中，快 2 到 2.8 倍，token 用量降 12% 到 23%

最后一条最值得注意：又快又省 token。执行模型常见的毛病是"为了不漏，把所有文件都读一遍"，token 在探索阶段就烧光。官方说 Hydrogen 会原生并行批量发起文件读取和搜索调用，而不是一个个文件看过去。100 万 token 的上下文里，这个差别直接决定你能不能把一个中型仓库整个塞进去。

agent 安全侧也给了几个具体数字：agentic 任务中的过度干预降低最多 81%，服务不足降低最多 79%，工具使用和编码评测里的错位行为和走捷径减少 12 倍，遇到不可能完成的任务时绕过权限边界的概率降低一半，内部 honesty 评测 94%；20 万轮审计下 99.9% 的思维链可读且无欺骗性编辑；在 Gray Swan 间接提示注入基准上韧性提升 2.3 倍。

这类自评数字我一律打折扣看。但"绕过权限边界的概率降低一半"是个有意义的方向：执行模型的权限比规划模型大（它真的在改文件、跑命令），它守住边界的价值确实高于前沿模型。

五、一个开发者的选型判断

我会这么用：

主力执行层用 Hydrogen，规划层留给前沿模型。 不要拿 Hydrogen 去做架构决策或者和产品经理扯需求，它的强项是在你已经知道要干什么的时候高速干完。反过来，把一个前沿模型按在循环里改 import 语句，纯属浪费配额。

先测缓存命中率再算成本。 $1.50/$7.50 这个价格，配上 4 倍的输出啰嗦度，账单可能超出预期。真正压住成本的是 95% 缓存折扣。如果你的调用模式里前缀重复度低（比如每次都是全新的独立问题），成本会比账面高不少。上线前拿真实流量跑一遍，看 cache hit 比例。

接受 43 秒首 token 延迟。 这是批处理工具，塞进同步交互界面会毁体验。放在后台任务、CI、批量数据加工里没问题。

长上下文塞仓库是这次最实用的能力。 整个 1M 窗口统一价，加上并行批量读取，把中型仓库整个喂进去做代码库问答，算下来比切片检索加 RAG 那套流程更简单、也更少出错。输出侧默认 64K 同步输出，需要更长可以走 background long decode 拉到 1M。

知识截止是 2026 年 3 月。 模型卡明说了，部分领域可能更旧。依赖新版本 API 的任务，别指望模型自己知道，把文档塞进上下文。

最后一句我的看法：这次发布的真正信息不是"又一个更强的模型"，而是 Google 把模型的推理深度当成了可以按任务阶段动态分配的运行时资源，而不是打包在权重里的静态属性。Orchestrator 省下 24% 配额这件事，比 Intelligence Index 从 50 涨到 51 有意义得多。前者改变了成本结构，后者只是排行榜上挪了一格。
