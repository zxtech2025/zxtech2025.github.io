encoding/json 被重写了：Go 1.27 的 json/v2 到底改了什么，Unmarshal 快 10 倍从哪来

2026-11-05
  • Go
  • 标准库
  • 性能优化
  • JSON

encoding/json 是 Go 里被 import 次数最多的包之一，也是被吐槽最多的包之一。它有一堆改不动的问题：大小写不敏感匹配字段、接受重复键名、nil slice 序列化成 null、Decoder.Decode 不检查尾部垃圾数据。这些都能改，但都不能在 Go 1 兼容承诺下改。

Go 1.27 的做法是换一代。encoding/json/v2 和 encoding/json/jsontext 进标准库，同时 encoding/json 自己变成 v2 的一层壳。最反直觉的地方在这儿：v1 的 API 一个字没动，行为一个字没变，但底层跑的已经是全新的实现。

分成两层：语法归语法，语义归语义

v2 把 marshal 和 encode 这两件事切开了。jsontext 只管语法：处理 {、}、字符串转义、数字格式，对应 RFC 8259 里那个字面叫 "JSON-text" 的语法定义，不碰 Go 反射。json/v2 只管语义：Go 值到 JSON 值的映射规则，反射在这里。

底层 API 长这样：

package jsontext

type Encoder struct { ... }
func NewEncoder(io.Writer, ...Options) *Encoder
func (*Encoder) WriteValue(Value) error
func (*Encoder) WriteToken(Token) error

type Decoder struct { ... }
func NewDecoder(io.Reader, ...Options) *Decoder
func (*Decoder) ReadValue() (Value, error)
func (*Decoder) ReadToken() (Token, error)

type Kind byte
type Value []byte          // v1 的 RawMessage 现在就是它的别名
type Token struct { ... }  // 不分配内存就能表示的任意 token

上层则保持熟悉的手感，只是补了 options：

package json

func Marshal(in any, opts ...Options) (out []byte, err error)
func MarshalWrite(out io.Writer, in any, opts ...Options) error
func MarshalEncode(out *jsontext.Encoder, in any, opts ...Options) error

func Unmarshal(in []byte, out any, opts ...Options) error
func UnmarshalRead(in io.Reader, out any, opts ...Options) error
func UnmarshalDecode(in *jsontext.Decoder, out any, opts ...Options) error

MarshalWrite / UnmarshalRead 直接吃 io.Writer / io.Reader，不用先造个 Encoder 再传进去。MarshalEncode / UnmarshalDecode 是它们底下的真实实现。

性能从哪来：别让 json 包替你做两次解析

旧的 MarshalJSON / UnmarshalJSON 接口有个结构性的坑，跟实现质量无关，是接口签名决定的。

MarshalJSON() 返回 []byte，所以要强制分配一次；返回之后 encoding/json 还必须校验它是合法 JSON，再按缩进重新格式化一遍。UnmarshalJSON([]byte) 要求传进来的是一个完整且不含尾部数据的 JSON 值，于是 encoding/json 必须先把整个值解析一遍确定边界，找到边界后调用你的方法，你的方法再从零解析一遍。同一份数据解析两次。

更糟的是递归场景。如果一个 UnmarshalJSON 内部又调用了 json.Unmarshal，复杂度直接变成 O(n²)。这不是理论问题，Kubernetes 就踩了四年。

v2 的做法是加一对流式接口：

type Marshaler interface {
    MarshalJSON() ([]byte, error)
}
type MarshalerTo interface {
    MarshalJSONTo(*jsontext.Encoder) error
}

type Unmarshaler interface {
    UnmarshalJSON([]byte) error
}
type UnmarshalerFrom interface {
    UnmarshalJSONFrom(*jsontext.Decoder) error
}

差别在于：边界判定和格式化交给 Encoder/Decoder，实现方只负责往流里写或从流里读。options 也能顺着传下去，从 Encoder/Decoder 上的 Options() 取，而 v1 的 DisallowUnknownFields 一旦进了自定义 UnmarshalJSON 就失效，这个坑很多人踩过。

一个真实案例：Kubernetes 的 10 倍和 38 倍

kube-openapi 的 issue #315 标题很直白：Deserializing into spec.Swagger is almost 20x slower than deserializing into map[string]interface{}。

原始数据是在 i7-8559U 上测的：

BenchmarkJsonUnmarshalSwagger-8        3    529833040 ns/op
BenchmarkJsonUnmarshalInterface-8     37     29475772 ns/op

529ms 对 29ms。同一个文件，同一个 JSON，只是目标类型不同。根因是 OpenAPI 的 vendor extension（x- 开头的任意字段）实现方式。为了接住所有未知字段，各种类型里递归地重复解析同一份输入，某些路径上同一个输入被解析了 5 次。

Joe Tsai 把 spec.Swagger 改成实现流式 UnmarshalJSONFrom 之后，同一台机器上的 benchstat：

name                       old time/op    new time/op    delta
UnmarshalJSON/Swagger-8       538ms ± 8%      38ms ±25%  -92.93%
UnmarshalJSON/Interface-8    33.5ms ±13%    25.3ms ± 9%  -24.37%

name                       old alloc/op   new alloc/op   delta
UnmarshalJSON/Swagger-8      88.5MB ± 0%    21.7MB ± 0%  -75.53%
UnmarshalJSON/Interface-8    10.6MB ± 0%    10.0MB ± 0%   -5.72%

name                       old allocs/op  old allocs/op  delta
UnmarshalJSON/Swagger-8       1.25M ± 0%     0.11M ± 0%  -91.49%
UnmarshalJSON/Interface-8     164k ± 0%      140k ± 0%  -14.38%

时间降 93%，分配次数从 125 万降到 11 万，降 91%。注意这个收益不是来自"Go 官方优化了 json 包"，而是来自把类型自己的反序列化逻辑改成流式，v2 只是第一次提供了这个接口。你手上那些自己写了 UnmarshalJSON 的类型，是同一类问题。

默认值变严了，这是刻意的

v2 在几个地方故意和 v1 不一样：

行为 v1 v2
非法 UTF-8 接受（静默损坏数据） 报错
对象里重复键名 接受（取哪个由实现决定） 报错
nil slice / map 序列化成 null [] / {}
字段名匹配 大小写不敏感 大小写敏感
omitempty 按 Go 零值判断 按"是否编码成空 JSON 值"（null/""/[]/{}）判断

重复键名那条值得单独说。RFC 8259 没规定怎么处理，所以不同实现会给出不同结果，同一个 JSON 在两个服务里解析出两个意思。这不是理论风险，CVE-2017-12635 就是靠 CouchDB 和 JavaScript 引擎对重复键的解析差异拿到了管理员权限。

omitempty 的变化会影响一批线上代码。以前一个 int 字段是 0 不会省略（因为 v1 看 Go 零值，0 是零值所以省略，但 *int 指向 0 就不省略），现在判断标准换成"编码后是不是空 JSON 值"，0 不算空值，所以带 omitempty 的 int 为 0 时会输出 0 而不是被省略。有下游服务依赖"字段不存在"和"字段为 0"语义区分的，迁移时得逐个字段过一遍。

还有个新行为：序列化 time.Duration 直接报错。因为 Duration 底层是 int64 纳秒，v1 会老实输出个纳秒数，接收方几乎不可能正确理解。v2 让你显式决定怎么表示。

v1 和 v2 能在同一个二进制里共存

这是整个设计里我觉得最巧的部分。官方没有把 v1 冻结在旧代码上，而是用 v2 实现 v1。v1 的行为差异全部由一组 options 描述，v1 就等于"打了全套兼容 options 的 v2"。

结果是双向兼容：

你的包用 v2 marshal 一个结构体，里面某个字段的类型来自另一个仍用 v1 MarshalJSON 的包，v2 认 MarshalJSON，正常工作。反过来，你的包用 v1 marshal，依赖的类型用了 v2 的 MarshalJSONTo，v1 在底层也认，正常工作。生态不需要一刀切迁移。

想逐步迁移也不用一次改完，可以按行为粒度挑：

// 全部用 v2 行为，但允许重复键名
json.Marshal(v, json.DefaultOptionsV2(), jsontext.AllowDuplicateName(true))

// 全部保持 v1 行为，但禁掉重复键名
json.Marshal(v, jsonv1.DefaultOptionsV1(), jsontext.AllowDuplicateName(false))

第二种写法特别适合"我只想先修掉一个安全问题，别的都别动"的场景。

基准数据：Marshal 打平，Unmarshal 大幅领先

官方 jsonbench 仓库在 Ryzen 9 9950X 上跑的结果（数值是相对 v1 的倍数，越低越好）：

场景 v2 相对 v1
Marshal 具体类型 1.4x 快 ~ 1.2x 慢（基本打平）
Marshal interface 类型 1.6x ~ 3.6x 快
Unmarshal 具体类型 2.7x ~ 10.2x 快
Unmarshal interface 类型 2.3x ~ 5.7x 快
Unmarshal 到 RawValue 10.2x ~ 21.1x 快

Unmarshal 到 jsontext.Value（即旧 RawMessage）快了 10-21 倍，这条最能说明问题。这个场景几乎不吃反射开销，纯粹考解码器本身。原因是 v1 的扫描器是词法分析式的，每读一个字节就做一次虚函数调用；v2 换成了迭代式线性解析。

同时要诚实说清楚：v2 比用 unsafe 的第三方库慢。相对 segmentio/encoding 在 Marshal 上最多慢 2.0 倍，相对 bytedance/sonic 在 Marshal 上慢 1.2-3.4 倍（sonic 走 JIT 生成机器码，且不校验 UTF-8）。v2 的目标是默认安全正确，不是绝对最快。它每次都要检查对象键名唯一、都要维护语法状态机，这些都是正确性的代价。

要极致性能就继续用 sonic，但要知道你买的是什么。

一个开发者的看法

给热路径上自己写了 UnmarshalJSON 的类型补一个 UnmarshalJSONFrom，这是我现在就会做的事。纯增量改动，v1 用户也能受益（v1 底层认 UnmarshalJSONFrom）。凡是方法体里 json.Unmarshal 调用自己的类型，都是候选。Kubernetes 那个 93% 就是这么来的，没有魔法。

迁移前先过一遍 encoding/json 包的 v2 对比文档，逐条确认哪些行为你在依赖。重点看 omitempty 和大小写敏感这两条。它们最可能在测试里无声通过、在生产里炸。

go doc encoding/json | grep -A 40 "v2"

GOEXPERIMENT=nojsonv2 记在脑子里当应急开关，别当长期方案。官方明说了这个 opt-out 会在未来版本移除，它是排障用的，不是推迟迁移用的。

至于要不要现在就把新代码写成 v2：很熟悉 v1 的话几乎可以直接写，签名长得一样，只是多了 options 参数。真正需要动脑的是判断哪些默认值变化会影响你的下游，这部分没有工具能替你做。
