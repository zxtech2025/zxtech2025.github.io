1. 漏洞背景与时间线

Budibase 是一个广受欢迎的开源低代码平台，用于快速构建内部工具、工作流和管理面板。作为低代码平台，Budibase 天然具备多租户（multi-tenant）能力，支持多个组织（tenant）在共享基础设施上隔离运行，每个租户内部又存在精细的角色层级。这种复杂的信任模型一旦出现边界失效，影响范围极大。

2026年上半年，Budibase 连续披露多个 Critical 级别的授权边界漏洞，其中两个（CVE-2026-46425 和 CVE-2026-48150）由同一安全研究团队（aisafe.io）在同一天（2026年5月27日）集中披露，加上更早披露的同类型漏洞 CVE-2026-25045，三者共同暴露了 Budibase 在租户隔离与角色授权方面的系统性缺陷。

2. Budibase低代码平台架构与信任边界模型

2.1 架构概览

Budibase 采用微服务式架构，核心包含两个服务：

┌─────────────────────────────────────────────────────────────┐
│                       客户端 (浏览器)                         │
└────────────┬───────────────────────────────┬────────────────┘
             │                               │
     ┌───────▼───────┐               ┌──────▼───────┐
     │  Budibase Server│               │ Budibase Worker│
     │  (app服务)      │               │ (全局/租户服务) │
     │                 │               │                │
     │ • 应用构建器     │               │ • 用户管理      │
     │ • 数据源连接     │               │ • 认证/授权      │
     │ • 自动化工作流   │               │ • SCIM端点      │
     │ • Public API    │               │ • 全局用户CRUD  │
     │ • 角色分配API    │               │ • 租户隔离      │
     └───────┬─────────┘               └───────┬────────┘
             │                                 │
             └──────────┬──────────────────────┘
                        │
              ┌─────────▼─────────┐
              │   CouchDB (集群)    │
              │  ┌───────────────┐ │
              │  │ global_tenant │ │  ← 全局租户数据库
              │  │ us_xxx 用户文档│ │
              │  ├───────────────┤ │
              │  │ app_tenant_A  │ │  ← 应用租户数据库
              │  │ app_xxx 数据   │ │
              │  ├───────────────┤ │
              │  │ app_tenant_B  │ │
              │  └───────────────┘ │
              └───────────────────┘
  • Server（app服务）：处理应用构建、数据源、自动化等业务逻辑。
  • Worker（全局服务）：处理认证、用户管理、租户隔离、SCIM 等全局性操作。

2.2 角色层级模型

Budibase 的角色体系分为两个维度：全局角色（Global Role） 和 应用级角色（App-level Role）。

全局角色层级 (存储在用户文档的 builder/admin 字段):
┌──────────────────────────────────────────────────────────────┐
│  Owner / Tenant Admin                                        │
│  admin: {global: true}                                       │
│  权限: 管理租户内一切 (用户、应用、设置、SCIM配置)              │
├──────────────────────────────────────────────────────────────┤
│  Global Builder                                              │
│  builder: {global: true}                                     │
│  权限: 构建租户内所有应用                                      │
├──────────────────────────────────────────────────────────────┤
│  Workspace-scoped Builder (应用级构建者)                       │
│  builder: {apps: ["app_xxx"], global: false}                 │
│  权限: 仅构建指定应用 (builder.apps数组中的app)                │
├──────────────────────────────────────────────────────────────┤
│  Creator (部分版本中等同于应用级构建者)                        │
│  权限: 构建应用，但无用户管理权限                               │
├──────────────────────────────────────────────────────────────┤
│  BASIC / App Viewer                                          │
│  roles: {"app_xxx": "BASIC"}                                 │
│  权限: 仅查看已发布的应用                                      │
└──────────────────────────────────────────────────────────────┘

应用级角色 (存储在用户文档的 roles 字段):
  roles: {
    "app_aaa": "ADMIN",    // 该应用的管理员
    "app_bbb": "BASIC",    // 该应用的普通用户
    "app_ccc": "POWER"     // 该应用的高级用户
  }

三个Critical漏洞分别击穿了不同层级的信任边界： - CVE-2026-46425：BASIC用户突破"全局管理边界"，通过SCIM操作租户用户 - CVE-2026-48150：应用级Builder突破"全局管理边界"，提升为全局Admin - CVE-2026-25045：Creator突破"全局管理边界"，通过IDOR操纵用户角色

3. 漏洞一：CVE-2026-46425 — SCIM路由缺失授权

3.1 漏洞概述

项目 内容
CVE CVE-2026-46425
CVSS 9.9 (Critical)
CWE CWE-862 Missing Authorization
影响版本 < 3.38.2
修复版本 3.38.2
研究团队 aisafe.io

SCIM（System for Cross-domain Identity Management）是企业级身份管理协议，Budibase 在 Enterprise 版本中支持通过 SCIM 端点管理租户用户和用户组。漏洞在于：SCIM 路由仅检查了功能开关（SCIM是否启用），却完全没有检查调用者的角色权限。

3.2 漏洞根因：中间件链缺失角色校验

// packages/worker/src/api/routes/global/scim.ts  (漏洞代码)
const router: Router = new Router({ prefix: "/api/global/scim/v2" })

// 仅挂载了两个中间件
router.use(proMiddleware.requireSCIM)    // 1. 检查SCIM功能是否启用 (不看角色!)
router.use(proMiddleware.doInScimContext) // 2. 设置SCIM请求上下文 (不看角色!)

// 以下所有路由都没有角色校验
router.get("/users", userController.get)
router.post("/users", userController.create)
router.patch("/users/:id", proMiddleware.scimUserOnly("id"), userController.update)
router.delete("/users/:id", proMiddleware.scimUserOnly("id"), userController.remove)
router.get("/groups", groupController.get)
router.post("/groups", proMiddleware.feature.requireFeature(Feature.USER_GROUPS), groupController.create)

对比非SCIM的用户组路由，可以清楚看到差距：

// packages/worker/src/api/routes/global/groups.ts  (正确的鉴权写法)
router
  .post("/api/global/groups",
        auth.adminOnly,                                          // ← 有角色校验!
        proMiddleware.feature.requireFeature(Feature.USER_GROUPS),
        buildGroupSaveValidation(), controller.save)
  .delete("/api/global/groups/:groupId/:rev",
          proMiddleware.feature.requireFeature(Feature.USER_GROUPS),
          auth.adminOnly,                                        // ← 有角色校验!
          controller.destroy)
  .get("/api/global/groups/:groupId",
       proMiddleware.feature.requireFeature(Feature.USER_GROUPS),
       auth.builderOrAdmin,                                      // ← 有角色校验!
       controller.find)

非SCIM路由的每个用户/组操作都挂载了 auth.adminOnly 或 auth.builderOrAdmin，而SCIM路由的"孪生"端点一个都没有。Worker 的全局认证中间件只检查 isAuthenticated（是否登录），任何拥有 budibaseAccess=true 的账户都能通过——这包括了租户内所有的 BASIC 用户。

3.3 攻击路径

BASIC用户 (App Viewer)
    │
    │ 1. 登录获取session cookie + CSRF token
    │    POST /api/global/auth/default/login
    │
    │ 2. 调用SCIM端点列出所有租户用户 (无需admin角色)
    │    GET /api/global/scim/v2/users
    │    → 200 OK, 返回所有用户列表 (PII泄露)
    │
    │ 3. 通过SCIM创建新用户 (无需admin角色)
    │    POST /api/global/scim/v2/users
    │    → 200 OK, 新用户创建成功 (scimInfo.isSync=true)
    │
    │ 4. 修改现有用户的email (账户接管原语)
    │    PATCH /api/global/scim/v2/users/<id>
    │    → 200 OK, email被改为攻击者控制的地址
    │    → 通过密码重置接管该账户
    │
    │ 5. 将合法用户移入攻击者控制的用户组
    │    POST /api/global/scim/v2/groups
    │    → 继承该组绑定的角色权限
    │
    ▼
完全的租户用户管理权限 (从BASIC用户提升)

3.5 修复方案

官方修复仅添加一行中间件：

// packages/worker/src/api/routes/global/scim.ts (修复后)
router.use(proMiddleware.requireSCIM)
router.use(proMiddleware.doInScimContext)
router.use(auth.adminOnly)    // ← 新增: 与非SCIM路由保持一致

一行代码关闭所有SCIM路由的越权。但这也暴露了一个更深的问题：功能开关（requireSCIM）和授权检查（adminOnly）被混为一谈。开发者认为"SCIM功能启用了"就等于"可以访问SCIM端点"，忽略了"谁可以访问"这一授权问题。

4. 漏洞二：CVE-2026-48150 — Builder角色越权至全局Admin

4.1 漏洞概述

项目 内容
CVE CVE-2026-48150
CVSS 9.0 (Critical)
CWE CWE-915 Improperly Controlled Modification of Dynamically-Determined Object Attributes
影响版本 < 3.39.0
修复版本 3.39.0
研究团队 aisafe.io

这是一个典型的批量赋值（Mass Assignment）漏洞。Workspace-scoped Builder（应用级构建者，builder.apps 有值但 builder.global 为 false）通过 /api/public/v1/roles/assign 接口，可以将自己或任意用户提升为全局 Admin。

4.2 漏洞根因：中间件过宽 + SDK无权限校验

漏洞涉及三个组件的协同失效：

组件1：中间件 builderOrAdmin 过于宽泛

// packages/backend-core/src/middleware/builderOrAdmin.ts
export async function builderOrAdmin(ctx: UserCtx, next: any) {
  if (ctx.internal || isAdmin(ctx.user)) { return next() }
  const workspaceId = await getWorkspaceIdFromCtx(ctx)

  if (!workspaceId && !env.isWorker()) {
    ctx.throw(403, "This request required a workspace id.")
  } else if (!workspaceId && !hasBuilderPermissions(ctx.user)) {
    ctx.throw(403, "Admin/Builder user only endpoint.")
  } else if (workspaceId && !isBuilder(ctx.user, workspaceId)) {
    ctx.throw(403, "Workspace Admin/Builder user only endpoint.")
  }
  // passes — 通过!
}

isBuilder(user, workspaceId) 对任何 builder.apps 数组包含该 workspaceId 的用户都返回 true，即使 builder.global 为 false。这意味着应用级 Builder 也能通过这个中间件。

组件2：控制器直接展开请求体（批量赋值）

// packages/server/src/api/controllers/public/roles.ts
export async function assignAppBuilder(ctx: Ctx) {
  const { userIds, ...assignmentProps } = ctx.request.body
  // assignmentProps 直接包含 builder 和 admin 字段，无过滤!
  await sdk.publicApi.roles.assign(userIds, assignmentProps)
  ctx.body = { data: { userIds } }
}

...assignmentProps 展开了请求体中除 userIds 外的所有字段，包括攻击者注入的 builder: true 和 admin: true。

组件3：SDK无条件赋值全局权限

// packages/pro/src/sdk/publicApi/roles.ts
export async function assign(userIds: string[], opts: AssignmentOpts) {
  if (!(await isExpandedPublicApiEnabled())) {
    throw new Error("Unable to assign roles - license required.")
  }
  const users = await userDB.bulkGet(userIds)
  for (let user of users) {
    if (opts.builder) {
      user.builder = { global: true }    // ← 无条件授予全局Builder!
    }
    if (opts.admin) {
      user.admin = { global: true }      // ← 无条件授予全局Admin!
    }
  }
  await userDB.bulkUpdate(users)
}

SDK 没有检查调用者自身是否已拥有其正在授予的权限。一个应用级 Builder 可以给任意用户（包括自己）授予全局 Admin。

4.3 攻击路径

Alice (Workspace-scoped Builder)
  builder: {apps: ["app_xxx"], global: false}
  admin: {global: false}
    │
    │ 1. 获取自己的API Key
    │    GET /api/global/self/api_key
    │    → {"apiKey": "80f28..."}
    │
    │ 2. 调用角色分配接口，scope到自己的app以通过builderOrAdmin
    │    POST /api/public/v1/roles/assign
    │    Header: x-budibase-app-id: app_xxx (自己的app)
    │    Body: {"userIds": ["us_victim"], "builder": true}
    │    → 中间件: isBuilder(alice, app_xxx) = true → 通过!
    │    → 控制器: assignmentProps = {builder: true}
    │    → SDK: victim.builder = {global: true}
    │    → 200 OK
    │
    │ 3. 给自己授予全局Admin
    │    POST /api/public/v1/roles/assign
    │    Body: {"userIds": ["us_alice"], "admin": true}
    │    → SDK: alice.admin = {global: true}
    │    → 200 OK
    │
    ▼
Alice 现在是全局Admin!
  builder: {apps: ["app_xxx"]}  (保留)
  admin: {global: true}         (新增!)

4.5 修复方案

官方建议在SDK层强制校验调用者权限：

// packages/pro/src/sdk/publicApi/roles.ts (修复后)
export async function assign(userIds: string[], opts: AssignmentOpts) {
  const caller = context.getIdentity()  // 获取调用者身份

  if (opts.builder) {
    // 只有全局Builder或Admin才能授予全局Builder
    if (!caller?.builder?.global && !caller?.admin?.global) {
      throw new HTTPError("Only global builders or admins can grant global builder", 403)
    }
    user.builder = { global: true }
  }
  if (opts.admin) {
    // 只有全局Admin才能授予全局Admin
    if (!caller?.admin?.global) {
      throw new HTTPError("Only global admins can grant global admin", 403)
    }
    user.admin = { global: true }
  }
}

5. 漏洞三：CVE-2026-25045 — Creator角色IDOR越权

5.1 漏洞概述

项目 内容
CVE CVE-2026-25045
CVSS 8.7 (Critical)
CWE CWE-862 Missing Authorization / CWE-639 IDOR
影响版本 多个版本
修复版本 未修复（截至披露时）
研究者 Hasinohacker

这个漏洞结合了垂直越权（Vertical Privilege Escalation）和不安全直接对象引用（IDOR）。/api/global/users 端点缺少服务端RBAC校验，Creator 级别用户（本应只能构建应用，无用户管理权限）可以重放 Owner 级别的请求，操纵租户内任意用户的角色。

5.2 漏洞根因：/api/global/users 缺少服务端角色校验

漏洞的核心是 /api/global/users 端点接受用户修改请求时，不验证请求者的角色是否拥有对应权限。系统依赖前端UI隐藏了Creator不应看到的操作按钮，但后端API本身不做校验。

设计意图 (前端控制):
  Creator UI → 不显示"用户管理"按钮 → Creator无法操作

实际漏洞 (后端无校验):
  Creator用Burp Suite捕获Owner的请求 → 替换为Creator的Cookie/CSRF → 重放
  → 后端接受请求 → 200 OK → 越权操作成功

5.3 攻击路径

Creator用户
  (仅有应用构建权限，无用户管理权限)
    │
    │ 1. 捕获Owner的合法请求 (Burp Suite拦截)
    │    例如: Owner将App Viewer提升为Tenant Admin的POST请求
    │
    │ 2. 用Creator自己的session token替换请求中的Cookie和CSRF
    │
    │ 3. 重放修改后的请求:
    │    POST /api/global/users
    │    Cookie: <creator_session>
    │    X-Csrf-Token: <creator_csrf>

    │
    │ 4. 后端无RBAC校验 → 200 OK → 操作成功!
    │

  ✓ → ✗ 将Tenant Admin降级为App Viewer

7. 低代码平台信任边界失效的系统性根因

三个漏洞虽然具体技术不同，但根因可归结为低代码平台特有的信任边界设计问题：

7.1 功能开关 ≠ 授权检查

CVE-2026-46425 的核心问题是将"功能是否启用"（requireSCIM检查SCIM license）等同于"是否允许访问"（缺少adminOnly角色检查）。低代码平台大量使用功能开关（Feature Flag）控制Enterprise功能，但功能开关只回答"能不能用"，不回答"谁能用"。

错误心智模型:
  requireSCIM() = true → "SCIM可用" → "允许访问SCIM端点" ✗

正确心智模型:
  requireSCIM() = true → "SCIM功能已启用" (功能层)
  auth.adminOnly()     → "调用者是Admin"  (授权层)
  两者都通过 → "允许访问SCIM端点" ✓

7.2 应用级角色与全局角色的混淆

CVE-2026-48150 的核心是 isBuilder(user, workspaceId) 对应用级 Builder 和全局 Builder 一视同仁。低代码平台中，应用级权限和全局权限是两个不同信任域，但中间件实现中往往用一个函数同时处理，导致应用级角色"逃逸"到全局域。

角色信任域:
  应用级 (App-scoped):     builder.apps = ["app_xxx"]  → 仅app_xxx的构建权
  全局级 (Global-scoped):  builder.global = true       → 所有app的构建权

混淆点:
  isBuilder(user, workspaceId) 对两者都返回true
  → 应用级Builder通过了本应只有全局Builder能通过的中间件
  → 应用级Builder获得了操作全局属性的入口

7.3 前端控制代替后端校验

CVE-2026-25045 的核心是依赖前端UI隐藏功能按钮来"防止"低权限用户操作，但后端API不做独立校验。低代码平台的拖拽式UI构建器天然倾向于在前端做权限控制（显示/隐藏组件），这容易让开发者产生"前端不可见=后端不可达"的错觉。

低代码平台的权限控制陷阱:

  前端 (UI Builder):
    if (user.role !== "ADMIN") hideButton("userManagement")
    → 看似安全: 非Admin看不到按钮

  后端 (API):
    POST /api/global/users → 无caller角色校验
    → 实际不安全: 任何人可直接调用API绕过UI

  根因: 前端控制是"用户体验"层面的，后端校验才是"安全"层面的
        两者不可互相替代

7.4 批量赋值与对象展开的滥用

CVE-2026-48150 中 const { userIds, ...assignmentProps } = ctx.request.body 的对象展开模式将用户可控的全部字段传入SDK，是 Mass Assignment 漏洞的典型成因。低代码平台大量使用动态字段（用户自定义应用结构），开发者习惯性地信任请求体结构，导致敏感字段（admin、builder）可被注入。

8.1 租户隔离强化

// 1. 所有租户级操作强制携带tenant上下文校验
export async function enforceTenantIsolation(ctx: UserCtx, next: any) {
  const callerTenantId = ctx.user.tenantId
  const targetTenantId = ctx.params.tenantId || ctx.request.body.tenantId

  if (targetTenantId && targetTenantId !== callerTenantId) {
    ctx.throw(403, "Cross-tenant access denied")
  }
  await next()
}

8.2 RBAC统一审计框架

// 建立统一的授权中间件注册表，消除"遗漏挂载中间件"的问题
const ROUTE_REGISTRY = new Map<string, RouteSecurityConfig>()

interface RouteSecurityConfig {
  method: string
  path: string
  requiredRole: 'admin' | 'builder' | 'basic' | 'public'
  scope: 'global' | 'app' | 'tenant'
  featureFlag?: string  // 可选的功能开关
  middlewares: Middleware[]  // 必须显式列出所有中间件
}

// 注册时强制声明安全配置
function registerRoute(config: RouteSecurityConfig) {
  // 自动校验: 有featureFlag的路由必须同时有role中间件
  if (config.featureFlag && config.requiredRole === 'public') {
    throw new Error(
      `Route ${config.method} ${config.path} has feature flag but no role check!`
    )
  }
  ROUTE_REGISTRY.set(`${config.method}:${config.path}`, config)
}

// SCIM路由正确注册
registerRoute({
  method: 'POST',
  path: '/api/global/scim/v2/users',
  requiredRole: 'admin',        // ← 显式声明需要Admin
  scope: 'tenant',
  featureFlag: 'SCIM',
  middlewares: [requireSCIM, doInScimContext, auth.adminOnly]
})

8.3 API网关鉴权层

在所有路由之前部署统一的API网关鉴权层，作为最后一道防线：

// packages/worker/src/api/index.ts — 全局授权网关
app.use(async (ctx, next) => {
  // 1. 认证: 所有非public路由必须通过认证
  if (!isPublicRoute(ctx.path) && !isAuthenticated(ctx)) {
    ctx.throw(401, "Authentication required")
  }

  // 2. 授权: 根据路由的安全配置校验角色
  const routeConfig = ROUTE_REGISTRY.get(`${ctx.method}:${ctx.path}`)
  if (routeConfig) {
    const user = ctx.user
    switch (routeConfig.requiredRole) {
      case 'admin':
        if (!user?.admin?.global) {
          ctx.throw(403, "Global admin required")
        }
        break
      case 'builder':
        // 全局Builder或应用级Builder(仅限对应app)
        if (!user?.builder?.global &&
            !isAppBuilder(user, getWorkspaceId(ctx))) {
          ctx.throw(403, "Builder permission required")
        }
        break
    }
  }

  // 3. CSRF校验: 所有写操作
  if (['POST', 'PUT', 'PATCH', 'DELETE'].includes(ctx.method)) {
    if (!verifyCSRF(ctx)) {
      ctx.throw(403, "Invalid CSRF token")
    }
  }

  await next()
})
